# 用語集

システムで使用する用語の定義です。
設計書・コード内で用語を統一するために参照してください。

## ビジネス用語

| # | ビジネス用語 | 説明 |
|---|-------------|------|
| 1 | 内部ID | トレーニング機関内で使用する会員の識別番号。DBの主キーとは別に、業務上で使う番号として保持する。新規登録時は現在の最大値+1で自動採番、編集画面で手動変更も可能 |
| 2 | 所感 | トレーナーが記録する所見・気づき。トレーナー間で共有するが会員には非開示。お客様に開示する「トレーナーからのノート」（No.21）と対をなす |
| 3 | 音声ファイル | 録音またはアップロードされた音声の実ファイル。音声記録の一種で、文字起こしの入力となる |
| 4 | 文字起こし | 音声ファイルをテキストに変換すること。Whisper APIを使用 |
| 5 | 要約 | 文字起こしテキストをAIで短くまとめたもの。Claude APIを使用 |
| 6 | 電話番号 | 会員の連絡先。緊急時に最初に連絡する番号 |
| 7 | 緊急連絡先（ご家族等） | 会員本人に連絡がつかないときの、ご家族などの電話番号。続柄（例：母、夫、娘）を添えられる。列は `phone2`（**2026-10-17 変更**：その前は「電話番号（予備）」で、2 つ目の電話番号として用途を問わなかった） |
| 8 | メールアドレス登録用 URL | トレーナーが発行し、会員自身にメールアドレスを登録してもらう URL。有効期限は発行した日から 7 日後の日の終わり（23:59:59）まで（**2026-10-18 変更**：その前は発行から 3 日〔発行した時刻で切れる〕）。**この期限が初回設定完了までの全体の期限**となる |
| 9 | ログイン用リンク | 登録されたメールアドレスに届く、初回設定用のリンク。**リンクを開くと会員がログインした状態になる**（ログインさせる働きを持つ）。有効期限は独立して持たず、**対応するメールアドレス登録用 URL の期限をそのまま引き継ぐ**（お客様がメールアドレスを登録した時点から数え直さない） |
| 10 | 初回設定 | 会員がログイン用リンクから、パスワードと基本情報（氏名・連絡先・住所）を設定し、マイページを使える状態にすること。**愛犬（トレーニー）の情報は扱わない**（受付アンケート No.30 で集める。**2026-10 変更**：それまでは愛犬の情報〔1 頭目〕も初回設定で入力していたが、アカウントの開設と愛犬の情報の登録を分けた）（詳細は screen-design.md S-1403 / requirements.md 6-15-5 参照） |
| 11 | メールアドレス確認リンク | メールアドレス変更画面（S-1409）からメールアドレスを変更する際、**新しいアドレスに送る**リンク。**メールアドレスを切り替えるだけの役割**で、ログインさせる働きは持たない。ログイン用リンク（No.9）とは性質が異なる別のもの。他のトークンとは無関係に発行されるため、**独立した有効期限**（3 日）を持つ |
| 12 | メールアドレスなし | 会員の状態のひとつ。メールアドレスが未登録で、有効なメールアドレス登録用 URL もない状態。メールアドレス登録用 URL を発行するとメールアドレス登録待ちに遷移する。**画面のバッジでは「未登録」と表示する**（**2026-10 変更**。それまで「なし」と表示していたが、状態がより伝わる文言に差し替えた。バッジはラベル「メールアドレス」の内側にあるため、対象を重ねずに状態だけを短く表す） |
| 13 | メールアドレス登録待ち | 会員の状態のひとつ。有効なメールアドレス登録用 URL が発行済みで、まだお客様がメールアドレスを登録していない状態。お客様がメールアドレスを登録すると初回設定待ちに遷移する。**画面のバッジでは「登録待ち」と表示する**（バッジはラベル「メールアドレス」の内側にあるため、対象を重ねずに状態だけを短く表す） |
| 14 | 初回設定待ち | 会員の状態のひとつ。メールアドレスは登録済みだが、パスワードがまだ設定されていない状態。お客様が初回設定を完了すると利用中に遷移する。**（判定ルール：メールアドレスがあり、かつ有効なメールアドレス登録用 URL もあるケースはこちらを優先）** |
| 15 | 利用中 | 会員の状態のひとつ。メールアドレスとパスワードの両方が登録済みで、会員が閲覧機能にログインできる状態。トレーナーはこの状態で会員詳細画面の「マイページ登録を削除」ボタンから登録を消せる（初回設定待ちでも同ボタンから消せる） |
| 16 | 登録情報 | ログイン中のお客様が、自分の登録内容（氏名・住所・電話番号・メールアドレスなど）を確認・変更する画面群。**登録情報画面（S-1406、確認画面）** を入口として、そこから登録情報の変更（S-1411）・パスワードの変更（S-1410）・メールアドレスの変更（S-1409）の 3 つの独立画面へ遷移する。登録情報画面の「愛犬の情報」の欄からは、愛犬ごとに愛犬の情報の変更（S-1417。名前・犬種・性別・誕生日・去勢・避妊）へ遷移する（**2026-10-18 追加**）。メールアドレスの変更は新しいアドレスへ「メールアドレス確認リンク」（No.11）を送り、リンクが開かれた時点で切り替える |
| 17 | パスワード再設定リンク | パスワードを忘れたお客様がログイン画面（S-1401）の「パスワードを忘れた方」から申し込みを行った際、登録アドレスに届く**新しいパスワードを設定するためのリンク**。**ログインさせる働きは持たない**（ログイン用リンク No.9 との違い）。**メールアドレスも変えない**（メールアドレス確認リンク No.11 との違い）。他のトークンとは無関係に発行されるため、**独立した有効期限**（3 日）を持つ |
| 18 | マイページ | お客様が自分のトレーニング記録やメディアを見るためにログインして使う場所を指す、お客様向けの呼び名。トレーナーがお客様に「マイページに登録してもらいます」のように口頭で使う言葉でもある。**プロダクト名（`config('app.client_portal_name')`、既定値「トレーニング記録」）とは別の呼称**で、ログイン画面などのワードマークにはプロダクト名を出し、案内の文章の中では「マイページ」と呼ぶ。トレーナー側の操作ボタン（「マイページ登録の案内を発行」「マイページ登録の案内を表示」）や、印刷ページ・お客様側の案内文でこの呼び名を使う |
| 19 | マイページ登録案内 | お客様にマイページへ登録してもらうために渡す一連の案内（QR コード・URL・手順・有効期限を載せた紙面／画面。**2026-10-18 変更**：紙には出さず、LINE・メールで送る文面か、その場で読み取ってもらう QR コードで渡す。S-0307）。トレーナーが S-0305 で「マイページ登録の案内を発行」を押すと、内部的に「メールアドレス登録用 URL」（No.8）が作られ、その URL を載せた S-0307 印刷ページとして「マイページ登録の案内を表示」ボタンから開ける。**「メールアドレス登録用 URL」がトークンそのものの識別**であるのに対し、**「マイページ登録案内」はお客様に渡す案内の呼び名**として使い分ける。発行済みの案内は、状態が「メールアドレス登録待ち（期限内）」のとき「取消」ボタン（マイページ登録の案内の取消）で取り消せる（6-3-7） |
| 20 | トレーニング記録 | データの単位。日付・担当・ノート（No.21）・所感（No.2）・メディアを含む記録全体を指す。画面名・メニュー名・エンティティ名でもこの語を使う（「トレーニング記録一覧画面」「トレーニング記録詳細画面」など） |
| 21 | トレーナーからのノート | トレーニング記録（No.20）の中で、お客様に見せる文章（`record_content`）。設計書内では短く「ノート」と呼ぶ。お客様に非開示の「所感」（No.2）と対をなし、事実を客観的に記録する。**画面に出るラベルは「トレーナーからのノート」で統一**し、括弧補足は付けない |
| 22 | 会員 | トレーニング機関に登録されたお客様（飼い主）。マイページの利用有無を問わない（メールでのやりとりをしないお客様も含む）。内部名は client（テーブル名・クラス名等は client のまま） |
| 23 | トレーニー | トレーニングの対象。当面は犬。会員に1対多で紐づく（複数頭は稀）。画面表記もそのまま「トレーニー」で統一する。**トレーニング記録（No.20）は会員単位であり、トレーニー単位ではない**（どのトレーニーの話かは記録の本文に書く。この方針は「トレーニー別に記録を分けると入力が煩雑になる」というトレーナーの要望に基づく）。将来の対象拡張を見据え、テーブル名・クラス名は犬に限定しない `trainees` を使う。**名前は任意**（トレーナーが名前を入れずに登録し、受付アンケート案内〔No.31〕だけを先に発行する運用のため）。名前・犬種などの空欄の項目は、受付アンケート（No.30）の回答で埋まる。誕生日は年・月・日を別々に、分かるところだけ持つ（詳細は requirements.md 6-16「年齢の表示規則」・D-0700 参照） |
| 24 | 計測値 | トレーニーごとの計測記録（現状は体重のみ）。トレーニング記録（No.20）とは独立したデータで、`training_records` とは紐付けない。基本的に毎朝計測、1日2回計測することもある。4日間・8日間コースなど預かり期間ごとに計測日が飛ぶ運用に対応する |
| 25 | コース | 4日間・8日間コースなど、トレーニングの預かり期間の総称。**システムはコースをエンティティとして持たない**（コース期間外の計測に対応できなくなるため）。計測値のグラフは**横軸を時間軸**にし、コース期間の切れ目は「計測日時が離れている＝横軸上で空白ができる」形で自然に表れる（線は 1 本の連続した折れ線で結ぶ。詳細は screen-design.md S-1402「横軸を時間軸に変更した経緯」参照）。当初は「一定日数以上空いたら線を分割する」方式だったが、2026-09 に廃止した（間隔の不正確さのほうが問題だったため）。**「4回コース」など回数で結ぶ契約は本項の「コース」ではなく「契約」（No.27）を参照** |
| 26 | トレーニング日 | トレーニング記録の日付（`training_records.training_date`）。**トレーナー側画面のラベル・列見出し・検索条件で「トレーニング日」に統一**する（**2026-09**）。従前は画面ごとに「日付」「最終記録日」などとばらついていた。計測値の「**計測日**」（No.24 参照）と区別するため、また記録の種別（`training_types`）が 2026-09 に廃止されて `training_records` に入るのがすべてトレーニングの記録という前提に揃ったため、DB カラム名 `training_date` と一致する呼称に統一した。**会員の最終のトレーニング記録日**（会員一覧 S-0304 の列名・検索条件）は **「最終トレーニング日」**。**会員側の画面ではラベル語を出さず**、「○月○日（曜）の記録」（詳細画面）や日付ブロック（縦帯・横帯）で日付そのものを見出しとして扱う流儀（詳細は client-portal-design-plan.md §6 の書き換え表参照）。詳細な適用範囲は screen-design.md §2-6 参照 |
| 27 | 契約 | 会員と回数で結ぶ契約（「4回コース」「8回コース」など）。契約日・回数・有効期限（任意）・メモを持つ。**No.25「コース」（預かり期間）とは別物で、回数の契約には「コース」という語を使わない**（「4回コース」などの呼び名は契約のメモに書く）。有効期限は残り回数（No.29）の計算や利用の割り当てには使わない（期限を過ぎていて残りがある契約は、会員詳細で有効期限の日付を赤字にする。当日は赤字にしない）。金額・支払いは持たない。利用（No.28）は、登録・編集のときにどの契約の分かを選んで割り当てる。契約ごとの残りは「契約の回数 − 割り当てた利用の件数」。内部名は client_contracts |
| 28 | 利用 | 契約回数のうち使った 1 回分の記録。利用日・メモを持つ。**1 件で 1 回分**。2 回分使ったとき（例：トレーニー 2 頭）は 2 件登録する。**どの契約（No.27）の分かを選んで割り当てる**（「契約なし」〔未割り当て〕も可。残りのない契約には割り当てられない。契約を削除すると、その契約の利用は「契約なし」に戻る）。**トレーニング記録（No.20）とはひも付けない**（トレーニング記録の件数と利用の件数は一致しないため）。内部名は client_usages |
| 29 | 残り回数 | 会員ごとの「契約（No.27）の回数の合計 − 利用（No.28）の件数」（利用 1 件は 1 回分）。**マイナスも許す**（利用の登録は止めない）。契約も利用も 1 件もない会員は表示しない（会員一覧では空欄、会員詳細の「回数」カードの見出しではラベル「ご利用回数」だけを出し、数字は空欄）。契約・利用が 1 件でも登録されていれば回数管理の対象の会員として数を出し（契約がなく利用だけならマイナス）、使い切った会員（0）と区別する。会員詳細（S-0305）と会員一覧（S-0304）に表示する。**画面には、トレーナー側・会員側とも「ご利用回数　あと n回」の言葉で出す**（「残り回数」は計算・用語としての名前。トレーナー側はマイナスを赤字の「契約 n回分不足」〔n は絶対値〕で出す）。会員側では、マイページの「ご利用回数」の画面（S-1412）で見るだけできる（会員向けの表示は「あと n回」。マイナスは数ではなく「ご契約の回数を n回超えてご利用中です」の文で伝える。契約・利用のメモは会員には出さない） |
| 30 | 受付アンケート | トレーニー 1 頭ごとに、お客様がログインせずに答える初回のアンケート。基本情報（名前・犬種・性別・誕生日・去勢・避妊）と自由記述 4 欄からなる。基本情報はトレーナーが入れた値を初期値にした入力欄で出し、お客様の回答でトレーニーの値を上書きする（空・未選択の項目は変えない。2026-10 変更：当初はトレーニーの空欄の項目だけに反映していた）。送られてきた内容は回答として残す（詳細は requirements.md 6-15-17 参照） |
| 31 | 受付アンケート案内 | 受付アンケート（No.30）に回答するための QR コード・URL・手順を載せた紙面／画面。トレーニーごとに発行し、有効期限はなく、回答の送信で使い切り。「マイページ登録案内」（No.19）と同じく、お客様・トレーナーが扱う対象を指す呼び名（詳細は requirements.md 6-16-8・6-16-9 参照） |
| 32 | 受付アンケート用 URL | 受付アンケート案内（No.31）の実体であるトークン付き URL を、設計書・DB 上で指す呼び名（「メールアドレス登録用 URL」〔No.8〕と「マイページ登録案内」〔No.19〕と同じ使い分け） |
| 33 | 愛犬性格診断 | トレーニー 1 頭ごとに、お客様がログインせずに答える 50 問（7 カテゴリ）の診断。カテゴリごとの平均とタイプを出す。受付アンケート（No.30）とは独立し、**何回でも**受けられる（**2026-10 追加**。詳細は requirements.md 6-15-18・6-16-11〜6-16-13 参照）。**名前の対応**：画面に出す正式名称は「愛犬性格診断」（**2026-10-18 変更**：正式名称に決まった。その前は「性格診断」）。元になったトレーナーさんの診断の名前は「愛犬パーソナリティ＆ウェルネス診断」。コード上の名前は personality diagnosis（`personality_diagnosis`・`PersonalityDiagnosis…`。画面に出ないので変えない）。画面の文字は `lang/ja/messages.php` の `personality_diagnosis_name` 1 か所から読む。名前はファイルの中で「愛犬」「性格診断」の 2 つに分けて持ち（`personality_diagnosis_name_parts`）、ふつうの名前はつなげたもの、狭い場所のラベル用（会員詳細 S-0305 の行のラベル）は間に折り返しの印（`<wbr>`）を入れたもの（`App\Support\PersonalityDiagnosisName::labelHtml()`。各部分は逃がしてからつなぐ）を、同じところから作る（**2026-10-18 追加**） |

| Whisper API | OpenAIが提供する音声文字起こしAPI。日本語を含む多言語に対応 |
| Claude API | Anthropicが提供する大規模言語モデルAPI。要約に使用（Haiku 4.5） |

| キュー（Job） | Laravelの非同期処理の仕組み。バックグラウンドでAPIの処理を実行する |
| MediaRecorder API | ブラウザ標準のAPIで、マイクからの音声をリアルタイムで録音する機能 |
