## 1. 方向性

犬の成長を記録するアルバムとして設計する。飼い主が毎週開くたびに「うちの子、また新しいことができるようになった」という発見が届く場所であり、業務ツールでも管理帳でもない。**写真が画面の主役**で、色と組版はそれを引き立てる額縁として、**明るく元気だが写真の邪魔を絶対にしない静けさ**を同時に持つ。

### 1-1. お客様向けの呼び名「マイページ」

お客様が自分の記録を見るためにログインして使う場所は、**お客様向けには「マイページ」と呼ぶ**。トレーナーが「マイページに登録してもらいます」のように口頭で使う言葉でもあり、案内の文章の中で自然に馴染むことを狙う。用語集参照。

**プロダクト名（ワードマーク）とは別の呼称**であることを明確にする：

- **プロダクト名**（`config('app.client_portal_name')`、既定値「トレーニング記録」）は、ログイン画面・初回設定画面などの**ワードマーク（大きな見出し）**と、`layouts/client` の `navbar-brand`、ブラウザタイトルのサフィックスに使う（詳細は §9-1）
- **「マイページ」**は、**案内の文章の中で使う呼び名**。印刷ページの見出し「マイページ登録のご案内」、お客様側 S-1402 の見出し「マイページのご登録」、完了メッセージ「マイページ登録案内を発行しました」、およびトレーナーが口頭・文章で使う機能名（「マイページ登録案内の発行／取消」など）で用いる。**トレーナー側の S-0305 の操作ボタン**（旧「マイページ登録案内を発行／表示／取消」）は、状態バッジ隣に移動した際に「登録案内を発行／表示／取消」と短縮しているため「マイページ」を含まない — 列名で対象が伝わるための例外（詳細は screen-design.md S-0305「操作ボタンの配置」）
- 結果として、**「トレーニング記録」という名前の仕組みの中に、お客様用のマイページがある**、という関係になる。ワードマークは「トレーニング記録」、案内で語られるものは「マイページ」で、両者を混同しない

## 2. カラー

> **経緯注記（2026-09）**：2026-09 のユーザーレビューにより、基調をオレンジ二色（terracotta / orange-bright）から紺二色（brand-deep / brand-bright）に変更した。トークン名は色ではなく役割で付ける（今後色が変わっても改名しなくて済むように）。本書の判断メモ・失敗事例・学びの節（§7 自己批評）にあるオレンジ・terracotta・orange-bright の記述は、変更前の経緯としてそのまま残している。

Bootstrap 既定の `#fd7e14`（.bg-client-nav）は破棄する。以下 7 色を新設する。**基調は紺二色**：`brand-deep`（深い紺）を**ヘッダー帯・見出し・成功メッセージの枠線と文字**に、`brand-bright`（明るい紺）を**主要ボタン・日付ブロック帯**（面 + `mat` 文字）**およびリンクの文字色**に置く。エラー・破棄は `madder`、補助面は `driftwood`、面・文字は `paper` / `mat` / `ink` で担当する。

コントラスト比は WCAG 2.2 に基づく（1.4.3 テキスト = AA 4.5:1 / AAA 7:1、1.4.11 非テキスト = 3:1 が基準）。値は実測済み（本節および §2-1「鮮色同士の隣接禁止」の表を参照）。**鮮やかな色を細線・小さな図形・フォーカスリングに割り当てない規律を、初版の tennis 事故（1.4〜1.5:1）を反省点として組み込む**（詳細は §7）。

**お客様側の画面は紺二色で構成する**。**深い紺（`brand-deep`）**をヘッダー帯・見出し・成功メッセージの枠線と文字に、**明るい紺（`brand-bright`）**を主要ボタン・日付ブロック帯（いずれも面 + mat 文字）およびリンクの文字色に使う。紺面上の文字は `mat`（白）で統一する。パレットの他の色（`paper` / `mat` / `ink` / `madder` / `driftwood`）は面・文字・状態表示の役割で保持する。

**リンクの文字色に `brand-bright` を採用した理由**：本文の文字色 `ink`（#0F1A2E）と `brand-deep`（#162D66）はコントラスト比が **1.33:1** しかなく、リンクを `brand-deep` にすると本文と色で区別できない（`$link-hover-color: $ink` との差もほぼ見えない）。`brand-bright` なら本文との差が **2.07:1** になり、色相の近い紺同士でも階層が付く。色だけに頼らないよう、本文中のリンクには下線を付けて識別性を担保する（詳細は §2-1）。

**カードの輪郭**: `paper` × `mat` のコントラスト比は約 **1.03:1** と極めて小さく、**面差だけではカードの輪郭が判別できない**。境界は**罫線（ink 8%）＋影の 2 段掛け**で作る（実装仕様は §2-1「カード境界の作り方」参照）。純白 `mat` を選んだ理由（写真の色が最も正確に見える）は維持する。

**白文字と `brand-bright` の可読性**：
`mat`（白）on `brand-bright`（#2A4A94）のコントラスト比 **8.38:1** は、WCAG 2.2 の AA テキスト基準（4.5:1）・AAA テキスト基準（7:1）のいずれも通過する。主要ボタン・日付ブロック等、面 + 白文字で運用する要素はすべて可読性の余裕を持って成立する。

**紺二色の対比**：ヘッダー帯（`brand-deep`）とボタン・日付帯（`brand-bright`）を明度差で対比させることで、画面の中で「案内の額縁」と「操作する場所／時間の目印」を視覚的に区別する。色相は共通なので画面全体は落ち着いた紺基調にまとまり、明度でだけ役割が動く構成になる。

**廃止した色**：以前は日付ブロック帯を独立した鮮橙 `persimmon`（#F97316）+ 焦茶 `bister`（#422714）で構成していたが、二色方針に統合したため両者とも定義から外した（オレンジ二色→紺二色の変更後も、この整理は同じく維持する）。

### 2-0. 写真と喧嘩させない規律（このパレットの中核ルール）

アルバム方向で最も陥りやすい失敗は、鮮やかな色を面で多用して**写真の色と衝突させる**こと。以下を設計上の禁止事項として明文化する。

- **鮮やかな色（`brand-deep` / `brand-bright` / `madder`）は「構造」に使う** — ヘッダー帯、主要 CTA、日付ブロック帯、状態表示、エラーの持ち場に限定
- **写真の周囲・カード本体・写真グリッドの背景には彩度の高い色を絶対に敷かない**。カード面は常に `mat` (#FFFFFF)、ページ背景は `paper` (#FAF7F0) の無彩色に固定
- 純白のマットは、写真の色が最も正しく見えることが選定理由。**アプリの主役は写真であり、UI は額縁**
- vivid な色を「面」として使うのは**ヘッダー帯 (`brand-deep`)**、**主要ボタン (`brand-bright`)**、**日付ブロック帯 (`brand-bright`)** の 3 用途のみ（当初は成功トースト (`brand-deep`) を加えた 4 用途としていたが、2026-09 にナビ帯との同色重複が指摘されて成功メッセージを「面」から外した — §2-1「成功系メッセージ」参照）

**基調を紺に戻したことによる前提の回復（要注記）**: 一時的にオレンジ二色に振っていたが、紺二色に戻したことで「暖色系の犬写真に対して寒色が補色的に効く」という初期案（cobalt 時代）の前提が再度成立する。ただし **§5-7 の分離規定は緩めない**：色相差に頼ると、写真の中の紺・青・グレー系の被写体・空・水などとぶつかったときに帯が沈む恐れがある。帯と写真グリッドの分離は、色相差だけを前提にせず余白と輪郭でも担保する（設計判断としては初版オレンジ時代と同じ規律を維持する）。

### 2-1. 色の使用制約（アクセシビリティ由来）

机上計算の結果、以下を設計上の**禁止事項**として明文化する。実装時に迷わないための約束。

#### brand-bright の使用範囲
- **面の色としては主要ボタン（.btn-primary）と日付ブロック帯に限定する**（使い道を広げない）。この 2 用途は「面 + mat 文字」のペアで運用する
- **文字色として使ってよいのはリンク（本文中）に限る**（paper / mat 上）。他の本文・見出し・キャプション等に brand-bright の文字色を使わない — 見出しは `brand-deep`、本文は `ink` が持ち場であり、色数を増やすと役割の識別が薄れる
- **役割の識別を保つため**の制限であり、コントラストの不足に由来する制限ではない（新色では `mat` on `brand-bright` = 8.38:1 で AAA 通過、`brand-bright` on paper = 7.83:1 で AAA 通過。可読性は AA/AAA いずれも満たす）
- brand-bright 面上に長文テキストを載せない（面 + 白文字は「短文ボタンラベル・日付のような短い一文」に限る。ダッシュボード等での長文表示は `paper`/`mat` 面 + `ink` 文字が担う。この規約は色の可読性ではなく「面の役割」の観点で残す）

#### リンクの規約
- **本文中のリンクは下線を付ける**（`text-decoration: underline`）。色相の近い紺二色では色だけで本文と区別しづらいため、下線を必須の識別手段とする
- **リンクの hover 色は `ink`**（`$link-hover-color: $ink`）。触れたときに本文と同じ濃さに落として反応を示す
- **下線を外してよいのは、置き場所や形で押せると分かるリンクだけに限る**（ヘッダー帯内のナビリンク・ボタンの形をした要素・カードの見出しリンクなど、周辺の見た目で押せることが伝わるもの）
- **カードの末尾やフッターに単独で置く文字のリンクは、本文中のリンクと同じ扱いにする**：`brand-bright` の文字色 + 常時下線、hover 時は `ink`。対象は次の 3 か所：
  - 記録カード末尾の「続きを読む →」（`.c-session-cta`）
  - フッターの「HOME」（`.c-footer-home`）
  - 詳細画面の「HOME」（`.c-detail-back`）
  - **理由**：紺二色への変更後の実機確認（2026-09）で、これらを `brand-deep`・下線なしで置くと本文の `ink` とほぼ同じ濃さ（`ink × brand-deep` = 1.33:1）になり、押せるように見えなかったため。単独で置かれる文字のリンクは、周辺の枠や形で押せることが伝わらないので、本文中リンクと同じ手がかり（明るい紺 + 下線）で識別を担保する

#### 主要ボタン（.btn-primary）の hover / active
- **`shade-color($brand-bright, 15%)`（hover）・`shade-color($brand-bright, 20%)`（active）で求める**。Bootstrap 慣習の 15% / 20% shade（`mix(#000, $brand-bright, N%)` と等価）を踏襲し、直書きせず関数で導く
- 変数値のみの上書きで hover / active が自動追随することを担保するため、`--bs-btn-hover-bg` / `--bs-btn-hover-border-color` / `--bs-btn-active-bg` / `--bs-btn-active-border-color` に `#{shade-color(...)}` を渡す

#### madder の配置制約
- **madder をテキストとして使うとき、`mat` 面上（カード内・入力欄内・入力欄直下の invalid-feedback）にのみ配置する**
- `paper` 上でも 9.02:1、`mat` 上でも 10.02:1 でどちらも AAA を通過するため可読性の観点では paper 配置も可能だが、**エラーは常にカード内で語られるべき**（ユーザーが「どこの入力に問題があるか」を明確に見せる文脈が要る）ため、`mat` 面限定の規約は据置する。理由が可読性ではなく文脈だったため、色を変えても規約は変わらない
- ページ全体に対するエラーが必要な場合は、まず `mat` のバナー（カード）で包み、その中に madder テキストを載せる

#### madder を面として使う場合の文字色（.btn-danger 等）
- **文字は `mat`（白）に限る**（mat on madder = 10.02:1 ✓AAA）
- **`ink` を madder 面に載せない**（ink on madder = 1.74:1、AA 不合格。可読性が担保できない）
- **SCSS 実装時の注意**: client.scss には `$min-contrast-ratio: 4.5` が既に設定済みのため、Bootstrap の `color-contrast()` は madder 面に対して確実に `mat` を選ぶ。ただし**閾値近傍の色を追加する事故を防ぐ保険**として、`.btn-danger` の文字色を明示的に `$mat`（白）に上書きする指定は残す

#### driftwood の配置制約
- **driftwood は面として使い、載る文字は `mat`（白）に限る**（ink on driftwood は 2.87:1 で不合格）
- **driftwood 面を `brand-deep` 面に直接隣接させない**（比 1.16、ΔE 50.0 だが輝度差がほぼないため境界が視認できない）。両者を並べる場合は `mat` / `paper` の緩衝帯を挟む

#### 補助ボタン（.btn-outline-secondary）の反応
- **面を塗らない**（Bootstrap 既定の「hover 時に $secondary で塗って白文字に反転」は使わない）
- **hover / active では、枠線と文字を driftwood より少し濃い色に変えるだけ**にとどめる（枠線・文字：hover は driftwood 15% shade `#5B5248`、active は 25% shade `#504940`。面は `transparent`）
- **判断の理由**：補助ボタンは「主要な行動を進める」役割ではなく、「戻る」「検索する」など画面内の副次的な操作を担う。Bootstrap 既定の「面を塗って白文字に反転」は主要ボタン相当の視覚重量を持ち、これを補助ボタンに使うと灰茶色（driftwood）のブロックが画面の中で浮いて見え、主要ボタンより主張してしまう。**触れたこと・押していることが分かれば足りる**という位置づけに合わせて、反応の強度を落とす
- **実装**：`.btn-outline-secondary` の Bootstrap 5.3 CSS 変数（`--bs-btn-hover-*` / `--bs-btn-active-*`）のみを上書きする。主要ボタン `.btn-primary` は別スコープの変数を持つため影響しない
- 対象箇所：メールアドレス登録の完了画面「メールアドレス入力に戻る」・パスワード再設定申し込み画面「← ログイン画面に戻る」・初回設定／登録情報の変更画面の郵便番号「検索」など、お客様側の枠線だけのボタン全般

#### プレースホルダーの色（お客様側）
- **指定**：`$input-placeholder-color: rgba($ink, .4)`（Bootstrap 既定は `rgba($body-color, .75)` = 75% 不透明度、これを **40%** に薄める）
- **実効色**（`mat` 面上）：約 `#9FA3AB`（`#0F1A2E` を 40% で白背景に重ねた合成色）
- **コントラスト比**：
  - **`mat` 背景に対して約 2.6:1**（**AA 大文字基準 3:1 を下回る**。承知のうえで採用。理由は下記）
  - **入力済みの値（`ink`）との差が約 6.0:1**（一目で明確に区別できる）
- **この値を選んだ理由**（**基準を下回ることを承知で採用**）：
  - **プレースホルダーは読めなくても入力できる種類の文字**。郵便番号の場合、ラベルに「郵便番号」と書いてあるので何を入れるかは分かる。プレースホルダーが伝えるのはハイフンの位置（`123-4567`）という補助的な情報だけで、**読めれば助かるが、読めなくても入力の妨げにはならない**
  - **WCAG のコントラスト基準（1.4.3 / AA テキスト 4.5:1、AA 大文字 3:1）は本来「読ませる必要がある文字」に対する基準**。プレースホルダーを基準の対象と見るかどうかは解釈が分かれる。ここでは補助的な文字と見なして基準の対象外として扱う
  - **入力済みの値との差を明確にすることを優先**した。これが今回の一連の変更の目的（75% では入力済みと本文と同等の濃さで見分けが付かなかった）
  - **基準を下回ることを隠さずに記録した上で採用する**判断。設計書は「なぜその値を選んだか」の理由（要素の性質・文字量など）を残す方針であり、ここでもプレースホルダーの補助的な役割を根拠として明示する
  - お客様側の色方針（`brand-deep` / `brand-bright`、いずれも面 + `mat` 文字）とは競合しない。プレースホルダーは主色を持たず、本文色を薄めた形
- **`$body-secondary-color` は変えない**。これを変えると `.text-muted` や `.form-text`（`.form-control` 直下の補足文、例：S-1403 の「8 文字以上で…」）にも波及する。**今回はプレースホルダーだけを薄くする**。補足文は「読ませたい情報」なので現状の 75% の濃さを維持する
- **トレーナー側には波及しない**。`client.scss` と `app.scss` は Vite の別バンドルで、`client.scss` 内の Bootstrap 変数上書きはトレーナー側の CSS に影響しない。トレーナー側のプレースホルダー（30 箇所超で使用中）は従来どおり Bootstrap 既定の 75% で表示される
- **実装方針**：CSS セレクタで `::placeholder { color: ... }` を書くのではなく、**Bootstrap 変数 `$input-placeholder-color` を上書き**する。Bootstrap import の前に置く。Bootstrap の作法に沿っており、`.form-control` / `.form-select` などの form 系コンポーネント全体に一貫して反映される
- 対象箇所（お客様側で `placeholder=` 属性を使っているすべて）：S-1403 初回設定の郵便番号「123-4567」、S-1411 登録情報の変更の郵便番号「123-4567」の 2 箇所。他の入力欄には `placeholder` を付けていない
- **経緯**（同じ検討を繰り返さないため）：
  1. Bootstrap 既定の 75% では本文と同等の濃さ（白背景 7.6:1）で、**入力済みと見分けが付かなかった**
  2. **50% に変えた**（白背景 3.4:1、AA 大文字基準 3:1 を満たす、入力済みとの差 4.6:1）
  3. 実物を見て**まだ濃いと判断**し、**40% にした**（白背景 2.6:1 で AA 大文字基準を下回る、入力済みとの差 6.0:1）
  4. 「40% では薄すぎて読めなくなる」という当初の見立ては撤回。**実物を見て、用途上は問題ない（プレースホルダーは補助的な情報で、読めなくても入力できる）と判断**

#### フォーカスリング（設計書の中核）
初版で tennis に割り当てて失敗した部分。今回は**二重輪郭**で「どの背景色の上でも見える」ことを机上で保証する。仕様は据置。

- **定義**: `box-shadow: 0 0 0 3px $mat, 0 0 0 5px $ink;`
  - 内側 3px = `mat` (#FFFFFF)
  - 外側 2px（合計 5px - 3px）= `ink` (#0F1A2E)
- **各背景での可視性**（実測）:
  - `paper` 上: 外側 ink リングが **15.66:1** で可視。内側 mat リングは背景に溶ける
  - `mat` 上: 外側 ink リングが **17.39:1** で可視。内側 mat リングは背景に溶ける
  - `brand-deep` 面上（ヘッダー帯内のナビリンク・ログアウトボタンの focus 時）: **内側 mat リングが 13.11:1 で可視**、外側 ink リングは brand-deep 上で 1.33:1 と溶けるが、内側 mat が担保するため合格
  - `brand-bright` 面上（主要ボタン・日付ブロック帯の focus 時）: **内側 mat リングが 8.38:1 で可視**、外側 ink リングは brand-bright 上で 2.07:1 と溶けるが、内側 mat が担保するため合格
  - `madder` 面上（破棄アクションの focus 時）: **内側 mat リングが 10.02:1 で可視**、外側 ink リングは madder 上で 1.74:1 と溶けるが、内側 mat が担保するため合格
  - `driftwood` 面上（補助アクションの focus 時）: **内側 mat リングが 6.06:1 で可視**、外側 ink リングは driftwood 上で 2.87:1 と溶けるが、内側 mat が担保するため合格
- → 全面で合格。単色のフォーカスリングでは「明色地」と「vivid CTA 面」を両立できないため、**二重輪郭が必然**

#### 鮮色同士の隣接禁止（境界が消える組み合わせ）

鮮やかな色・面色同士を並置したときのコントラスト比と色差 ΔE76 の実測値：

| 隣接組み合わせ | 比 | 判定 |
|---|---|---|
| brand-deep × brand-bright | **1.56:1** | ✗（深い紺と明るい紺は同じ色相で最も近い） |
| brand-deep × madder | **1.31:1** | ✗ |
| brand-bright × madder | **1.20:1** | ✗ |
| brand-deep × ink | **1.33:1** | ✗（本文色 ink とヘッダー帯／見出しがほぼ同色。§2 の「リンクの文字色に `brand-bright` を採用した理由」参照） |
| brand-bright × ink | **2.07:1** | ✗テキスト（本文中でリンクを判別するために下線が必須） |
| driftwood × brand-deep | **2.16:1** | ✗ |
| driftwood × brand-bright | **1.38:1** | ✗ |
| driftwood × madder | **1.65:1** | ✗ |
| driftwood × ink | **2.87:1** | ✗ |

**役割識別可能性についての注記**: 基調を紺二色に絞ったことで、`brand-deep` × `brand-bright` が最も近い組み合わせ（1.56:1）になっている。これは同じ紺色相の明度差でしかないため、面差だけでの分離は不可能で、**必ず `mat` (#FFFFFF) または `paper` の緩衝帯を挟む**ことが要件になる。加えて、**本文色 `ink` と `brand-deep` のコントラスト比が 1.33:1** と極めて低く、本文中の文字色として `brand-deep` を使うと本文と見分けが付かない（このため §2 の方針でリンクの文字色を `brand-deep` ではなく `brand-bright` に振っている。本文中のリンクは下線を併用して識別を担保する）。破棄アクション（madder）は色相の差で区別できるが、それでも隣接禁止のルールは同じく適用する。**破棄アクションはラベル文言と配置でも区別を担保すること**。

以下を禁止事項として明文化する：

- **鮮やかな色（`brand-deep` / `brand-bright` / `madder`）および `driftwood` 面を直接隣接させない**（境界が視認できず、UI コンポーネント間の分離が失われる）
- 特に **`brand-deep` の帯と `brand-bright` の面（ボタン・日付帯）を直接隣接させない**（1.56:1、同じ色相のため面差だけでは境界が視認できない）
- 鮮色を並べる必要がある場合は、**必ず `mat` (#FFFFFF) または `paper` (#FAF7F0) を 1px 以上の枠または余白として挟む**（mat / paper が担う「無彩の緩衝帯」の役割）
- **`ink` は `brand-deep` 面・`brand-bright` 面上でテキストとして使えない**（それぞれ 1.33:1・2.07:1）。テキストは常に `mat`（白）を載せる。境界として並置する場合も、ink × brand-deep = 1.33 では境界が見えないため mat / paper の緩衝を挟む

具体的な設計判断への影響：
- 日付ブロック（brand-bright）に「今日」ピル（brand-deep / madder 等）を重ねたい場合は、ピルの下に **2px 以上の mat 枠を敷く**（例: `border: 2px solid $mat` を pill に付ける）
- 主要ボタン（brand-bright 面）を brand-deep 帯の直下に置く場合は、帯とボタンの間に最低 8px の余白（mat/paper が見える隙間）を確保する
- 破棄アクションボタン（madder 面）を主要 CTA（brand-bright 面）の直近に置く場合、両者の間に mat/paper の余白を必ず入れる

#### brand-bright 面の境界（日付帯・ボタンの周辺）
日付ブロックの brand-bright 帯は、隣接するカード本体（mat）との輝度コントラスト差が **8.38:1** で、WCAG 1.4.11 の 3:1 を大きく超えて満たす。帯の内部には日付テキストという**それ自体で意味を伝える情報**が入っており、面差だけで境界が視認できる。追加の外枠・落ち影は不要。

#### カード境界の作り方（paper × mat = 1.11:1 への対応）

`paper` (#FAF7F0) と `mat` (#FFFFFF) のコントラスト比は約 **1.03:1**。色差でカード・入力欄の輪郭を作ることは不可能なため、以下の方針で境界を作る。

**WCAG 1.4.11 との関係（判定）**: カード内部にはテキスト・写真という**それ自体で意味を伝える情報**が入っている。したがってカード境界は「コンポーネントを識別する唯一の視覚情報」ではなく、**装飾的境界**に分類される。WCAG 1.4.11 の 3:1 を厳密に満たすことは要求されない。ただし輪郭がまったく見えないと視覚的な「まとまり」の情報が失われるため、以下を規約として実装する：

**カード・入力欄の境界仕様**:

- **細罫線**: `border: 1px solid rgba(15, 26, 46, 0.08);`（`ink` を 8% 不透明度で使用。paper 上での実効コントラストは約 1.1:1 で 3:1 未達だが、下の影と併用することで境界を perceivable にする）
- **落ち影**: `box-shadow: 0 1px 4px rgba(15, 26, 46, 0.06), 0 6px 20px rgba(15, 26, 46, 0.05);`（`ink` を 5〜6% で 2 段影。写真アルバムの「印画紙を貼った」感覚に寄せる。ぼかし半径を広く取り不透明度を抑えることで、輪郭の硬さを避けつつ浮きを保つ）
- **合成の効果**: 罫線単独では 3:1 を満たさないが、罫線 + 影の組み合わせで**輪郭を知覚できる状態**を作る。装飾的境界としての設計判断

**依存関係の明示**（設計者への注意）:

- 純白 `mat` を選んだ理由（写真の色が最も正確に見える）を維持する代償として、**カード境界の実装が必須**になる
- 実装時に「罫線か影のどちらかを外して単純化する」判断をしてはいけない — 単独ではどちらも境界の役割を果たせない
- 影の不透明度を下げる調整をする場合、**罫線を同時に弱めてはならない**。影が弱まるほど罫線が境界を担う比重は上がる。両方を同時に弱めると輪郭が知覚できなくなり、本節の前提が崩れる
- 将来的にカード面色を変える判断をする場合（例: mat → 薄いクリーム色に変更）は、その色と paper のコントラスト比を再計算し、色差だけで境界が作れるかを再判定する

**入力欄も同じ扱い**: `.form-control` は `mat` 背景で入力欄の輪郭を持たないと入力可能領域が不明瞭になる。Bootstrap 既定の border（`$input-border-color`）を上記の細罫線値に置き換える。フォーカス時は §2-1 のフォーカスリング（mat + ink 二重輪郭）が発火する

#### 角丸の規約

柔らかい印象を角丸で作る。3 段階に統一し、個別値のベタ書きを禁止する。

| 用途 | 変数 | 値 | 適用先 |
|---|---|---|---|
| カード | `$radius-card` | 0.875rem | `.c-session` / `.c-empty-card` |
| メディア | `$radius-media` | 0.5rem | サムネイル・バッジ・「+N」 |
| Bootstrap 基準 | `$border-radius` | 0.5rem | `.btn` / `.form-control` / `.alert` |
| Bootstrap 小 | `$border-radius-sm` | 0.375rem | `.btn-sm` 等 |
| Bootstrap 大 | `$border-radius-lg` | 0.75rem | `.btn-lg` 等 |

**規約**:
- 角丸は上記の変数を参照する。セレクタに数値をベタ書きしない
- 以下は上記の対象外とし、独立した定数として扱う:
  - フォーカスリングの内側形状（2px）— カードの角丸と連動させない
  - ピル形状（999px）・円形（50%）— 形状を作る定数であり調整対象ではない
- `.c-session` は `overflow: hidden` を持つため、`$radius-card` を変えると日付ブロック帯（`.c-date-block`）の左角も追随する。これは意図した挙動であり、`.c-date-block` に個別の `border-radius` を与えてはならない（与えると二重管理になり、カードとの追随が壊れる）

**判断の理由**:
§1「明るく元気だが写真の邪魔をしない」の「柔らかさ」を、装飾ではなく形状で作る。§7 で却下した装飾（イラスト・手描き風・足跡）に頼らずに柔らかさを出す手段が、角丸・影・余白の 3 つである。本節はそのうち角丸を規定する。

#### 影の規約

| 用途 | 変数 | 値 |
|---|---|---|
| カード静止時 | `$card-shadow` | `0 1px 4px rgba(15,26,46,.06), 0 6px 20px rgba(15,26,46,.05)` |
| カードホバー時 | `$card-shadow-hover` | `0 2px 8px rgba(15,26,46,.09), 0 12px 28px rgba(15,26,46,.07)` |

**規約**:
- 影は上記の変数を参照する。セレクタに数値をベタ書きしない
- **フォーカスリング（`0 0 0 3px $mat, 0 0 0 5px $ink`）は影とは別系統**。`$card-shadow` 系と混同して同時に変更しない。フォーカスリングはアクセシビリティ要件であり、装飾的な調整の対象ではない
- 影の色は常に `ink` の低不透明度とする。他の色相の影を使わない（暖色の影は「汚れ」に見え、写真の色を濁らせる）

#### 余白の規約

柔らかさを作る 3 手段（角丸・影・余白）の 3 つめ。カード内の余白は以下を基準とする。

| 対象 | デスクトップ（≥576px） | モバイル（<576px） |
|---|---|---|
| セッションカード本体 | `1.25rem 1.5rem` | `1rem 1.25rem` |
| セッションカード（hero） | `1.5rem 1.75rem` | `1.25rem 1.5rem` |
| 日付ブロック | `1.25rem 0.5rem` | `0.625rem 1.25rem` |
| 日付ブロック（hero） | `1.75rem 0.625rem` | `0.625rem 1.25rem` |
| 空状態カード | `1.75rem 1.5rem` | 同左 |

**規約**:
- hero は通常カードより 1 段大きい余白を持つ。「最新の 1 件」の存在感をサイズではなく余白で作る（フォントサイズの拡大に頼らない）
- 日付ブロックはデスクトップで縦帯・モバイルで横帯となるため、padding の縦横比が反転する。両形態で個別に値を持つ
- 以下はカード内余白とは別系統であり、本規約の対象外とする:
  - ページ外周の余白（`.c-login` の padding-top/bottom）
  - 入力欄・ボタンの高さを決める padding（Bootstrap 変数 `$input-btn-padding-y: 0.5rem` で一括指定。`.form-control` / `.form-select` / `.btn` に適用され、理論高さ 46px）。`-sm` / `-lg` は別系統の変数のため影響を受けない。トレーナー側の `app.scss` は情報密度を優先して 0.25rem であり、値が異なるのは意図的。詳細は §4-3・§7-17
  - リストマーカー用インデント（`.c-next-list` の padding-left）
  - バッジ・ピルの padding（形状を作る値）

**角丸との依存関係**:
`$radius-card` を上げると、カード内の要素と角の実効距離が縮む。角丸を上げる調整をしたときは、**余白も併せて見直すこと**。片方だけを動かすと、角に近い要素が窮屈に見える。

#### 成功系メッセージ（`tennis` の代替）

**現行の配色（2026-09 確定分）**：

| 要素 | 色 | 実測値の目安 |
|---|---|---|
| 背景 | `shade-color($paper, 8%)` | ≈ `#E6E3DD`（`paper` を 8% 黒で暗くした派生色） |
| 枠線（1px） | `shade-color($paper, 25%)` | ≈ `#BCB9B4`（同じく 25% 黒で暗くした派生色） |
| 文字 | `$ink`（#0F1A2E） | 本文と同じインク色 |

**性質**：
- **面・枠・文字がすべて同色相**（`paper` 系＋`ink`）で統一され、`.alert-danger` の「薄い茜面 + 濃い茜文字」と同じ「同色相の濃度差だけで表現する」構造になる（エラーとの見た目の系統が揃う）
- **既存パレット 7 トークンに新色を追加していない**：背景・枠線は `$paper` を Bootstrap 関数 `shade-color()` で派生させた値、文字は既存の `$ink`
- **穏やかな見た目**：paper 面からわずかに濃い面と、少しだけ濃い枠で構成される。色で主張せず、**文言で伝える**（「登録しました」等）
- Bootstrap 既定の緑は導入しない（前案で使っていた `tennis` は新パレットに存在しない）

**コントラスト**（実測概算）：

| 組み合わせ | 比 | 判定 |
|---|---|---|
| `$ink` on 背景（`shade-color($paper, 8%)`）| ≈ 13.4:1 | ✓AAA |
| 背景 on `paper` | ≈ 1.21:1 | 面差は小さいが、枠線が輪郭を担う |
| 枠線 on 背景 | ≈ 1.51:1 | 3:1 UI 基準は下回るが、装飾的な内側輪郭として容認 |
| 枠線 on `paper` | ≈ 1.83:1 | 装飾的な外側輪郭として容認 |

**枠線の 3:1 未達を許容する理由**：この枠は「アラートの状態を伝える UI コンポーネント」ではなく「面より少し濃い装飾的な縁取り」であり、成功メッセージであることは**文字（文言）**で伝わる。3:1 UI 基準は「意味の伝達を色に頼るコンポーネント」向けであり、装飾的な縁は対象外。「穏やかな見た目」を優先した設計判断であり、実機で「枠が消えて面が paper に溶ける」ように見えるなら 25% を 30% 前後まで上げる余地がある。

**閉じるボタン（`.btn-close`）**：Bootstrap 既定の黒 X をそのまま使う（`paper` 系の明るい面上で読める）。

| 3 | `tint-color($brand-deep, 85%)` 面（≈ `#DCE0E8`）+ `brand-deep` 枠 + `brand-deep` 文字 | 同色相 3 段濃度で palette 統一の面では成立したが、**紺（青系）を白で薄めるとグレーに寄る**性質があり、暖色寄りの `paper` と色温度が真逆で調和しない |
| 4 | `#FFF3CD` 面（試行）+ `brand-deep` 枠 + `brand-deep` 文字 | 暖色系の背景で温度感は出たが、**面（黄色）と枠（紺）の色相が違って枠が浮く**。加えて `#FFF3CD` は Bootstrap で `alert-warning` に使われる色で、**警告色を成功に使う意味の混線**リスクも残った |
| 5 | **`paper` 系（現行）** | 面と枠を同色相にまとめ、パレットも広げず、穏やかな見た目で「色ではなく文言で伝える」方針に着地 |

---

**各段階で分かったこと（学びの集約）**：

- **数値制約（コントラスト・AAA）を満たすことは必要条件だが十分条件ではない**：段階 1→2→3→4 のいずれも AA / AAA は通過していたが、実機で見て感覚的な違和感が続いた。§7-16 の第二の失敗（数値制約は満たしたが実機で見ていなかった）と同じ構造の問題で、実機評価を段階ごとに繰り返すことで着地に至った
- **同系色の 3 段濃度は色相によって成立する / しない**：`paper` 系（暖色）や `madder` 系（茜、`.alert-danger` の例）では成立する。`brand-deep` 系（青系）は白で薄めるとグレーに寄るため、暖色寄りの背景色（paper）との組み合わせで温度感が齟齬する（段階 3 の学び）
- **面と枠の色相が違うと枠が浮く**（段階 4 の学び）：`.alert-danger` が同色相で自然にまとまるのと対照的で、色相を揃えることが視覚的な統一の必要条件
- **Bootstrap 既定の意味を横取りしない**：`alert-warning` の色（`#FFF3CD`）を成功に使うと意味の混線リスクが生じる。UI の一般的な色記号（黄色 = 注意）は尊重する
- **同系色の派生でパレット拡張を回避できる**：`tint-color()` / `shade-color()` で既存トークンから派生することで、新トークンを追加しなくても複数の濃度が使える。新色を足したくなったとき、まず既存トークンから派生できないか検討する

**段階 1 → 2 の判断（面塗りをやめた理由）を保存**：
1. **パレットを変えずに済む**（緑の再導入や `tennis` 復活を伴わない）
2. **`brand-bright` への振り替えを避ける**（§2-1「brand-bright の使用範囲」の「面としては主要ボタンと日付帯に限定する」に抵触するため）
3. **§2-0 の「vivid な色を面として使う用途を絞る」原則がより明確になる**（面の用途が 4 → 3 に減り、面としての `brand-deep` はヘッダー帯だけになる。「ナビ帯 = 唯一の `brand-deep` 面」という一対一対応が成立する）
4. **§7-16 の原則を面と枠の二値で表現する**（色相を共有する色同士は本来「明度」で区別する規定だが、可動域が狭い場合は「面か枠か」という別の軸で区別できる。当時はナビと成功で「面 vs 枠」の対比を採用した。段階 5 では成功が色で目立たない方向へ振ったため、この対比は必要なくなった）

---

**今回の判断（段階 5 = `paper` 系）を選んだ理由**：

1. **パレットを広げない**：`shade-color($paper, ...)` で既存の `$paper` から派生する。新規トークンの追加判断（採用の重み、命名、他要素との整合）を持ち越さない
2. **温度感を保つ**：`paper` そのものが暖色寄りの off-white で、その shade も暖色系に留まる。段階 3 のグレー化を回避
3. **面と枠が同色相**：段階 4 で見えた「別色相の枠が浮く」問題を回避。`.alert-danger` と同じ「同色相の濃度差」の作りで、エラーとの見た目の系統が揃う
4. **色で主張しない、文言で伝える**：「登録しました」等の**言葉が主役**で、色は「メッセージであることを穏やかに示す縁取り」に徹する。§1 の「明るく元気だが写真の邪魔をしない静けさ」に沿う方針

**ヘッダー帯との関係**：ヘッダー帯（`brand-deep` 100% 面）と成功メッセージ（`paper` 系の面 + 枠）は色相自体が異なり、明度も大きく離れているため識別に迷いはない。段階 3 で目指した「同色相の 3 段濃度でナビと明度で対比」は撤回する形になるが、成功メッセージが**色で目立たない方向**へ振ったため、そもそもナビとの視覚的競合が起きない。

**変更しなかったもの**：
- エラーメッセージ（`.alert-danger`）の配色：Bootstrap の tint / shade 自動生成のまま（`madder` の薄い茜面 + 濃い茜文字）。エラーは注意を惹くべき役割で、面塗りの視覚的重みが意味論的に妥当。成功が「穏やかな縁取り」でエラーが「薄い茜面塗り」となり両者は表現手法が異なるが、意味の違い（完了 vs 要対応）に合致するため許容
- ナビゲーションバー、主要ボタン、日付ブロック帯、トレーナー側（`app.scss`）、パレットの 7 トークン定義：すべて据置

### 2-3. 情報表示のレイアウト（お客様側の確認・表示画面の標準）

**お客様側の確認・表示画面は、ラベルを上・値を下に置く縦一列を標準とする**。**項目と項目の間だけに罫線を引き**、上から順に読ませる。カードの枠が外周を担当するため、**カード内側の上端・下端には罫線を引かない**（役割が重複するため）。罫線は項目の区切りにだけ使う。

**理由**：**お客様側の画面はスマートフォンでの閲覧を想定している**ため、横に並べると視線が横に飛んで読みにくい。項目数も少ない（S-1406 で 6 項目程度）ので、1 画面に収まる範囲であり、縦一列で並べても長くなりすぎない。

**トレーナー側との住み分け**：トレーナー側のクライアント詳細画面（S-0305）などは、情報量が多く一覧性が要るため **3 列グリッド**（`x-detail-cell` コンポーネント）を使う。用途が違うため実装を分けており、`x-detail-cell` はトレーナー側専用として扱う。同じ検討を繰り返さないよう、この住み分けを本節で明示する。

**未入力値の扱い**：**ラベルを残し、値を空にする**（`min-height` で行高を保つ）。確認画面なので「登録されていない」ことが分かる必要があり、行ごと消すと未登録なのか項目自体がないのかを区別できないため。§2-4「未入力値の表示」（`screen-design.md`）のセル形式と同じ扱い。

**適用範囲**：S-1406（登録情報の確認画面）が代表例。今後、お客様側で「登録済みの情報を確認するだけ」の画面を新設する場合も、この形式に揃える。変更フォーム（S-1409／S-1410／S-1411）はフォームの見た目に従うので、本節の対象外。

## 3. タイポグラフィ

**Web フォントは一切使わない。見出しも本文もシステム日本語スタックで組む**。方針を実測結果に基づき修正した（前案では Zen Maru Gothic を採用していたが撤回した — 詳細は下記）。

### 候補比較（丸みのある日本語書体）— **全て不採用**

前案では「丸みのある日本語 Web フォント」を見出しに使う方針で、以下 4 候補を比較していた。**実装後の実測により方針を撤回**。比較表は履歴として残す。

| 候補 | Google Fonts | 動的サブセット (`unicode-range`) | 想定実効サイズ（JP、1 ウェイト） | ウェイト展開 | モバイル本文の可読性 | 判定 |
|---|---|---|---|---|---|---|
| Zen Maru Gothic 500 | ○ | ○ | 前案では実効 40〜80KB と見積もり | 300 / 400 / 500 / 700 / 900 | 高い | **不採用**（下記） |
| M PLUS Rounded 1c 500 | ○ | ○ | 実効 50〜90KB | 100〜900（8 段階） | 高い | 不採用（同じ理由） |
| Kosugi Maru 400 | ○ | ○ | 実効 40KB | 400 のみ | 中 | 不採用（同じ理由） |
| Klee One 400/600 | ○ | ○ | 実効 60〜100KB | 400 / 600 | 中 | 不採用（同じ理由） |

**撤回の理由（実測値）**: Zen Maru Gothic を実装してブラウザで初回読み込み時の転送量を実測した結果、以下だった：

| 内訳 | サイズ |
|---|---|
| CSS（`css2?family=Zen+Maru+Gothic` 応答） | 29.0 kB |
| woff2 × 5 サブセット | 61.9 kB |
| **合計** | **90.8 kB** |

前案の「実効 40〜80KB」見積もりは **CSS 分（29KB）を含めていなかった**。29KB の CSS は動的サブセット `@font-face` 宣言が 100 個以上並ぶ構造的なコストで、**使用箇所を絞っても減らない**。計測ページは文字数が少なく、飼い主名・犬名・トレーナーのノート本文などが入る実運用では 100KB を超える見込み。

読者はモバイル主体・週 1 回程度の訪問という前提に対して、100KB 前後の追加転送は釣り合わない。「使用箇所を絞れば実効サイズが小さい」という論理が CSS 分を数えないと成立しない、という**見積もり側の甘さ**が根本原因（§7 自己批評参照）。

他候補（M PLUS Rounded 1c / Kosugi Maru / Klee One）も同じ Google Fonts の仕組みを使うため、**CSS 分の 20〜30KB は同様に発生**する。個別書体固有の可読性議論以前の理由で全候補が不採用になる。

### 書体の役割（最終決定）

| 役割 | 書体 | 採用可否 | 理由 |
|---|---|---|---|
| 見出し・本文・UI テキストのすべて | システム日本語スタック（下記「フォントスタックの定義」参照） | **採用**（唯一） | Web フォント無し、ダウンロードコストゼロ。見出しと本文の階層は**書体差ではなく、ウェイト・サイズ・letter-spacing・色**で作る（下記「型スケール」）|
| Zen Maru Gothic / M PLUS Rounded 1c / Kosugi Maru / Klee One | 各種 Web フォント | **不採用** | 上記実測理由 |
| Noto Sans JP | Web フォント | **不採用** | 一貫性は上がるが、モバイル読者に対して 100KB+ のコスト（Zen Maru Gothic と同じ罠） |
| 数字・データ用 mono | JetBrains Mono 等 | **不採用** | 桁揃えは `font-variant-numeric: tabular-nums` で解決。mono の投入は AI 既定の「テック風の格好つけ」でこのブリーフに合わない |

### フォントスタックの定義

前案のスタック `-apple-system, BlinkMacSystemFont, "Hiragino Kaku Gothic ProN", "Yu Gothic", "Meiryo", sans-serif` には Windows 特有の問題がある：

- **Windows で `"Yu Gothic"` を CSS で明示指定すると「Yu Gothic Light（ウェイト 300）」が当たる**既知の問題があり、極端に細く描画される
- 本文サイズ（1rem）で Light ウェイトになると可読性が低下

したがって以下のスタックに変更する：

```
system-ui, -apple-system, BlinkMacSystemFont, "Segoe UI",
"Hiragino Sans", "Hiragino Kaku Gothic ProN",
"Yu Gothic Medium", "Meiryo", sans-serif
```

**各要素の役割**:

| 要素 | 対象 OS / ブラウザ | 効果 |
|---|---|---|
| `system-ui` | モダンブラウザ全般 | OS のシステム UI フォントを取得。Windows なら Segoe UI（Latin）+ Yu Gothic UI（JP はグリフ単位フォールバック、**Yu Gothic Light 問題を回避**）／ macOS/iOS なら San Francisco + Hiragino Sans／ Android なら Roboto + Noto Sans CJK |
| `-apple-system`, `BlinkMacSystemFont` | 古い macOS / iOS の Safari / Chrome（`system-ui` 未対応時） | SF フォント fallback |
| `"Segoe UI"` | 古い Windows Chrome | Latin フォントの明示 fallback |
| `"Hiragino Sans"` | macOS 10.11+ / iOS 9+ | 現行 macOS/iOS の日本語フォント（新しい名前） |
| `"Hiragino Kaku Gothic ProN"` | 古い macOS / iOS | ヒラギノ角ゴ（旧名） |
| `"Yu Gothic Medium"` | Windows | **`"Yu Gothic"` ではなく `"Yu Gothic Medium"` を明示**。「Medium」は独立ファミリ名でウェイト 500 で描画される — Light 問題が発生しない |
| `"Meiryo"` | 古い Windows | Yu Gothic 未搭載環境での fallback |
| `sans-serif` | 絶対 fallback | 全て失敗時の汎用 sans |

**判断の根拠**:
- `system-ui` を最初に置くことで、モダン環境では OS がグリフごとに最適なフォントを選ぶ（Windows なら Latin=Segoe UI・JP=Yu Gothic UI Regular で Light 問題を発生させない）
- 明示的な JP フォント指定は「モダン `system-ui` が効かない旧ブラウザ」用の保険。その場合でも `"Yu Gothic Medium"` を先に置くことで Yu Gothic Light を避ける
- 見出し（ウェイト 700）でも同じスタックを使う。system-ui が効く環境では Yu Gothic UI Bold が当たる。旧環境では Yu Gothic Medium ファミリに対して browser がボールドを合成（synthesized bold）— 完全ではないが機能的

### 型スケール（書体差を失った分をウェイト・サイズ・letter-spacing・色で補う）

Bootstrap の rem を維持する。行間は日本語のため 1.5〜1.8。**見出しと本文の階層を書体で作れなくなったため、以下の 4 手段で明確化する**：

1. **ウェイトの落差**: 見出し = 700、本文 = 400（Bootstrap 既定より大きな段差）
2. **サイズの落差**: Display / H1 / H2 を前案より一段大きく引き上げる
3. **字間**: 見出しに letter-spacing を効かせて存在感を作る
4. **色による階層**: 見出しに `brand-deep` を使い、本文の `ink` と分ける（brand-deep on paper = **12.26:1** ✓AAA、brand-deep on mat = **13.11:1** ✓AAA）。深い紺なので paper / mat の上で AAA を通過し、本文（`ink`）との視覚的な段差は色相の近さでは失われず、ウェイト・字間との合わせ技で見出しが本文の上に立つ

**設計判断の付記**:
- **見出しの色 = brand-deep**: これで見出しが本文（ink）と一目で区別できる。brand-deep はヘッダー帯・見出し・成功メッセージの枠線と文字で使う「構造の色」として palette 内で意味が統一される
- **Display / 詳細タイトル / H1 の色も brand-deep**: 詳細画面の日付見出し「8月2日（金）の記録」も brand-deep になり、ヘッダー帯との視覚的つながりが生まれる
- **letter-spacing は日本語でも効く**（Latin 用語ではあるが、和文でも字送りが広がって落ち着いた印象になる。過度に広げると読みにくくなるため 0.01〜0.02em に抑制）
- **カード内見出し (H3) の色は ink のまま**: カード内には既に `brand-bright` の日付ブロック帯があり、そこに `brand-deep` の見出しを加えると 1 カード内に鮮色が 2 種並ぶ。brand-deep × brand-bright は比 **1.56:1** で境界が視認できないため、§2-1 の隣接禁止に抵触するリスクがある。原則として **1 カード内の鮮色は日付ブロック帯 (`brand-bright`) だけ**にとどめる
- **H1 と eyebrow のサイズ差**: 当初 2rem 対 0.75rem（2.7 倍）で、挨拶がページ内で最も目立つ要素になっていた。§1「写真が主役、UI は額縁」に反するため 1.5rem 対 0.875rem（1.7 倍）に詰めた。いずれも表内の既存の段（H2 = 1.5rem、Meta = 0.875rem）を流用しており、型スケールにサイズ値を増やしていない。当時、**挨拶を見出しとして成立させる前提**で eyebrow 側を 1rem（Body と同サイズ）まで上げる案も試したが見出しとして成立しなかった（**サイズは見出しらしさの主要な手がかりであり、太字・字間・色では代替できない**）ため、eyebrow は 0.875rem に戻し、H1 は 1.5rem に留めた。**2026-09 の方針変更**：挨拶は毎週見る言葉で情報の重みが軽く、そもそも見出しとして立たせる必要がない — グラフや記録が主役に見えるよう、H1 を体重グラフのカード見出し「○○ちゃん」と同じ 1.1rem に揃えた。結果として eyebrow との比は 1.1rem 対 0.875rem = **1.26 倍**となり、当時「詰めた」1.7 倍よりさらに近づいた。当時 1rem 案を却下した論拠（見出しとして成立させる）は前提そのものが変わっており、今回の 1.1rem はほぼ同じ場所に着地しているが目的が異なる（**見出しとして立てないための着地点**）。当時の「サイズは見出しらしさの主要な手がかり」という発見自体は他の見出し（H2・詳細タイトル）には引き続き当てはまるため、規則としては残す
- **eyebrow の色 = `ink`（不透明度を下げない）**: 当初 `ink` 65% としていたが、これは Meta（副次情報）と同じ薄さであり、見出しが本文より弱くなっていた。**見出しの階層は「薄くする」ことでは作れない**。サイズを上げる調整（0.75 → 0.875 → 1rem）を 2 回試して解決しなかったのは、原因がサイズではなく色だったためである。 → **規則**: 見出しに `ink` の不透明度を下げた値を使わない。不透明度を下げるのは Meta（時刻・件数・キャプション）のように本文より情報の優先度が低い要素に限る
- **画面ごとのページタイトルのサイズ**: ダッシュボードの挨拶（H1 **1.1rem**）、記録詳細の日付（1.75rem）、ワードマーク（**1.25rem** — 帯の中）と幅がある。同じ `<h1>` でもサイズが異なるのは、**見出し階層（タグ）とサイズは別物**であり、各画面でその見出しが担う役割の重みに応じて決めているため。挨拶は「毎週の挨拶」（§6）で情報としての重みは軽く、2026-09 に**見出しとして立たせない**方針へ変更した（詳細は前項）、詳細の日付はその記録を識別する唯一の情報、ワードマークは**帯の中で案内元を識別する要素**（画面の主役ではなく、上端の額縁）。**挨拶（1.1rem）がワードマーク（1.25rem）より小さいことは意図した結果**である — サイズの大小関係でヒエラルキーを示すのではなく、それぞれが担う役割に応じたサイズを選んでおり、ワードマークは帯の中で Bootstrap `.navbar-brand` 既定の 1.25rem が自然に収まる値、挨拶は「見出しとして立たせない」方針で体重グラフのカード見出しと同水準に落とした結果である（両者は異なる面上に置かれ隣接しないため、直接比較される関係にはない）
- **ワードマークの位置・サイズ変遷**: 「プロダクトの顔として大きく見せる」方針で 2.75rem → 2.5rem と調整してきたが、実機で訓練所名が入ると**カード内見出し（1.5rem）や入力欄より目立ち、ページの主役になっていた**。§1「写真が主役、UI は額縁」の考え方は pre-auth の入力画面にも当てはまり、そこでの主役は**お客様がやること（入力）**である。まず本文と同じ 1rem まで下げた（前段階）が、今度はページ上部が寂しくなったため、**ヘッダー帯を導入して帯の中に置き直した**（現段階）。帯の中では Bootstrap 既定 1.25rem が自然に収まり、色も帯背景 `brand-deep` 上で読める `mat` に変わっている。「案内元がわかる」役割は変わらず、位置づけと文脈が「カード上に単独で置く見出し」から「帯の中のブランド」に移った

### 数字の扱い

初版では `font-variant-numeric: tabular-nums` を body 全体に適用していたが**範囲が広すぎた**（和文中の「3 匹」「12 月」まで桁位置が固定され、意図しない副作用があった）。**適用範囲を以下の要素に限定する**：

- **日付ブロックの日の数字**（`.date-block .day` 相当）— 大きく表示するため桁位置固定が読みやすさに直結
- **記録件数の表示**（例: 「全 **N** 回」の N）— 数字が増減するため桁位置固定
- **時刻**（詳細画面「10:00」）— 桁揃えで読みやすい
- **入力欄の郵便番号・電話番号**（`input[type="tel"]` / `#postal_code` / `#phone1` 等）— 入力中の桁ずれ防止

body 全体には適用しない。実装時は上記の要素に対して個別に `font-variant-numeric: tabular-nums` を効かせる（`.num-tabular` ユーティリティか、要素セレクタで直接指定）。

## 4. レイアウト

各画面のワイヤーフレームを ASCII で示す。特にダッシュボードは現状案と改善案を並べる。

### 4-0. 全画面共通のナビゲーション

各画面のワイヤーフレームに入る前に、複数画面にまたがる共通要素を先に確定する。以下の各画面（§4-1 以降）ではナビ内部の詳細は繰り返さず、この節を参照する。

#### 適用範囲

| レイアウト | ナビの有無 | 備考 |
|---|---|---|
| `layouts.client`（認証済み: ダッシュボード・記録詳細・登録情報および各変更画面 + 例外的に login） | あり | 本節の仕様を適用。S-1406 クライアント登録情報画面（確認）と S-1409/1410/1411 の各変更画面もダッシュボードと同じレイアウトで表示する。login は pre-auth だが本レイアウトに載る（`@auth`/`@else` で post-auth／pre-auth のナビを切り替える） |
| `layouts.client-public`（初回設定・メールアドレス登録・トークン切れ・パスワード再設定申し込み・パスワード再設定） | あり | pre-auth 画面。**ヘッダー帯（`.c-nav`）は載せる**（見た目をログイン前後で揃えるため）。右側のメニュー（登録情報／ログアウト）は出さず、左のブランドのみを表示する |

**帯を pre-auth にも載せる理由**：
以前は pre-auth ではワードマークをカード上部に中央配置していたが、ワードマーク自体を本文サイズまで縮小したところ画面上部が寂しくなり、締まりを欠いた。ヘッダー帯を導入すると画面に枠ができ、内容が収まって見える。加えて **ログイン前後で帯があり／なしの不揃いが解消**され、ブランドの立ち位置が一貫する。

#### 見た目

| 項目 | 値 |
|---|---|
| 実装クラス | `.c-nav`（Bootstrap の `.navbar` と組み合わせ）|
| 背景色 | **`brand-deep`**（旧 `mat`）|
| 文字色 | **`mat`（純白）**（`.c-nav` 内で `--bs-navbar-color: $mat` を設定。旧 `ink`）|
| 罫線 | 下端 1px、`rgba(255, 255, 255, 0.20)`（帯上で沈まない mat 20% の明側輪郭）|
| 影 | 付けない |

**共通 partial**：`layouts.partials.client-nav` に単一実装を置き、`layouts.client` と `layouts.client-public` の両方から `@include` する。`authed` フラグで右側メニューの有無だけを切り替える（構造とスタイルは共有）。

**判断の理由**（背景を brand-deep にした経緯）：
段階2 では `mat` 面 + ink 文字で「面より薄い区切り線」に留めていたが、pre-auth 画面のワードマークを本文サイズまで縮小した結果、画面上部が「額縁」を欠いて素朴すぎる状態になった。ヘッダー帯を明色のまま入れても輪郭が弱いため、**基調の主要色 `brand-deep` を帯に置く**ことで枠を作り、pre-auth と post-auth の統一感も同時に確保する。§1「写真が主役、UI は額縁」の考え方は保つ（帯は上端のみで、下方向にはカードとしての面が広がる）。`brand-deep` は §2 でヘッダー帯・見出し・成功メッセージの枠線と文字として使う「構造の色」であり、その方針の一部としてヘッダー帯に置いている。**見出しと帯で同色が呼応する**か、**過剰に濃色が繰り返されて疲れる**かは、実装後の実機確認で判断する予定（本節ではまず「作って見て次で調整」の段階）。

#### ワードマーク（左端）

- `config('app.client_portal_name')` から供給する（§9-1 と同じキー）
- Blade にハードコードしない
- **`layouts.client`（認証後）のワードマークはダッシュボードへのリンクにする**。`<a class="navbar-brand" href="{{ route('client-portal.dashboard') }}">` とし、`<span>` にしない
- **pre-auth のワードマーク（帯の左）はリンクにしない**（`.navbar-brand` を `<span>` として置く）。ログイン前はダッシュボードに到達できず、画面自身のヘッダを兼ねる役割だけを持つ
- **ロゴ画像への差し替えに対応**：`config('app.client_portal_logo')` に URL が設定されている場合は `<img class="c-nav-brand-img">` を出力し、設定がなければテキスト（`client_portal_name`）を出力する。切り替えは partial 内の 1 分岐で完結（設計書 §9-3 の「将来ロゴ画像が確定した場合の再導入」を実装）。`.c-nav-brand-img` は `max-height: 32px` で帯の高さに収める

**判断の理由**：
プロダクト名は現時点で未確定（§9-1）であり、将来の変更に耐える構造を担保するため。段階4-2 以降のログイン画面ワードマークと供給元を統一することで、名称変更時の修正箇所が config 1 か所に収束する。

**リンク化の判断理由**：
認証後の画面（ダッシュボード・記録詳細）には、記録詳細からダッシュボードへ戻る導線が `.c-detail-back`（「HOME」）しかない。ワードマークは Web の慣習としてトップへ戻る導線であり、飼い主が迷ったときに最初に押す場所である。`.c-nav` には既に `--bs-navbar-brand-hover-color: $brand-deep` が設定されており、`<a>` にすることで初めてホバー時の色変化が機能する。`<span>` のままではこの変数が無駄になっていた。

#### 右端（登録情報・ログアウト）

- **ユーザー名は表示しない**
- 右端に置くのは **「登録情報」と「ログアウト」の 2 リンクのみ**
- どちらも **文字リンク**（Bootstrap `.btn-link .btn-sm`）
- 枠線ボタン・塗りボタンにしない
- スマートフォン幅では折りたたみメニューの中に、登録情報とログアウトを並べて置く（横幅の狭いデバイスでも両方の到達性を保つため）

**回遊要素は原則置かないが、この 2 つは例外として置く**：
- **ログアウト**：ログイン状態を離れる手段はナビ以外に存在せず、記録詳細からも直接アクセスできる必要がある
- **登録情報**：メールアドレス・パスワード・連絡先の変更は他画面のフローに紛れないよう独立させたい。ダッシュボード内に配置するとメディアやトレーニング記録のフローの中に紛れる

**判断の理由**（§6 のログアウト行と整合）：
飼い主にとってログアウトも登録情報も主要な行為ではない。週1回訪れて記録を見る場所であり、退出や設定変更を促す設計にしない（§6「主要な行為ではないため面積を落とす」）。装飾レベルを主要 CTA と揃えると視覚重量が競合するため、文字リンクに落とす。

当初はユーザー名 + `さん` を `navbar-text` として表示していたが、ダッシュボードの H1「○○ さん、こんにちは」と名前が重複し、実機確認で「しつこい」と判断されたため撤去した（H1 の呼称は「さん」→「様」→「さん」と変遷している。詳細は §6 書き換え表の該当行「呼称の経緯」参照）。挨拶（H1）が「誰の画面か」を伝える役割を兼ねる。**トレーナーが飼い主に画面を見せる運用がない**ため、「誰としてログインしているか」を明示する必要もない。ログアウトリンクが残るためログイン中であることは分かる。H1 を残してナビ側を消したのは、ダッシュボードの H1 がこれだけであり、消すとページに H1 がなくなるため（次の見出しは `<p class="eyebrow">` で見出し階層に入らない）。

#### フッター（認証後のみ）

| 項目 | 値 |
|---|---|
| 実装クラス | `.c-footer` |
| 適用範囲 | `layouts.client` の `@auth('client')` 内のみ |
| 要素 | `<footer class="c-footer">` |
| 内容 | 「HOME」リンク（ダッシュボードへ）+ コピーライト |
| 文字色 | `ink` 65%（§3 Micro の規定）。リンクは `brand-bright` + 常時下線、hover 時は `ink`（§2-1「リンクの規約」参照） |
| 背景 | 敷かない（`paper` のまま） |
| 罫線 | 上端 1px、`$border-color`（ナビ下端と対称） |

**規約**:
- **`@auth('client')` の内側に置く**。`layouts.client` は `login.blade.php`（`guest:client`）からも extends されるため、ガードなしではログイン画面に到達不能な HOME リンクが出力され、かつ同画面の `.c-login-footer` とコピーライトが二重になる
- **HOME リンクは常に表示、コピーライトは `@if(config('app.client_portal_company'))` でガードする**。会社名が未供給でも HOME リンクは機能するため、`<footer>` 全体をガードしない（§9-2 の pre-auth 向け規定とは扱いが異なる）
- ラベルは「HOME」とする。記録詳細冒頭の `.c-detail-back` も同じ「HOME」に統一し、**矢印は付けない**（§6 参照）。矢印は「一つ前の画面へ戻る」方向を示す記号として「← 戻る」にだけ使う（§4-10 参照）。「HOME」は戻る方向ではなく**行き先を名指しするリンク**なので、置き場所（画面上部・フッター）にかかわらず矢印を付けない。**2026-09 のユーザーレビューの要望**を受けて、以前は矢印を付けていたのを外した。詳細は §4-10 の「S-1404 の『HOME』を統一しない理由」を参照
- **タップ領域を確保する**。フッターのリンクは文字サイズが小さいため、上下 padding で高さ 44px 相当を確保する（§4-3・§7-17 と同じ基準）
- 実装クラス名 `.c-detail-back` の "back" はラベル変更後も据置とする。リネームは SCSS・Blade の両方に波及し、得られる整合性に対してコストが見合わない

**判断の理由**:
認証後の画面ではワードマーク（§4-0）と `.c-detail-back`（記録詳細のみ）がダッシュボードへの導線を担うが、ダッシュボードを長くスクロールした末端には戻る手段がない。フッターの HOME はその位置を埋める。コピーライトを同じ行に置くのは、フッターという定型位置に情報を集約して本文フローの装飾を増やさないためである（§2-0 の規律）。

#### 実装上の禁則

- `!important` を使わない。段階2 の `.bg-client-nav` は Bootstrap の `navbar-dark`（白文字前提）を打ち消すため `!important` を多用していたが、段階4-6 で Blade から `navbar-dark` を除去したことで、Bootstrap 5.3 の CSS カスタムプロパティ（`--bs-navbar-color`、`--bs-navbar-brand-color` 等）の素直な上書きだけで意図した色になる。詳細度を上げる必要がなくなった
- Blade 側で `navbar-dark` / `bg-client-nav` / `text-white` / `btn-outline-light` を使わない（すべて段階2 の暫定コード。段階4-6 で除去済み）
- `.c-nav` は `layouts.client` と `layouts.client-public` の両方で使う。個別 Blade で独自の帯を書かず、必ず `layouts.partials.client-nav` を経由する

**ポイント**:

- メディアはカード内グリッド。件数の縦スクロールは持たない（数十件を超える運用は現時点で想定外）
- 「未記入」の代わりに、そのセクション自体を非表示にする（空セクションを見せない）

**タイトル下の並び**：タイトル（「8月2日（金）の記録」）の直下に、時刻と担当を**1 行に並べる**（時刻 → 担当の順）。タイトルの日付に続けて時刻を置くことで「いつ（日付・時刻）→ 誰が（トレーナー）」の順で読めるようにするため（2026-09 ユーザーレビュー）。時刻と担当の間は**記号を入れず、余白（会員詳細トレーナー画面 S-0305 の見出し行と同じ 8px）で区切る**：担当どうしの区切りにすでに「／」を使っているため、別の記号を足すと区切りが 2 種類になって紛らわしいため。画面幅が狭く 1 行に収まらないときは自然に折り返してよい。時刻が未登録なら時刻を、担当が未登録なら担当を出さない扱いは変わらない（両方無ければ行ごと非表示。§6 空値の扱い）。以前は「トレーナー → 時刻」の 2 行だったのを、まず順番を「時刻 → 担当」に入れ替え、次に 2 行だと縦の余白が大きいことが実機確認で分かったため（2026-09）、本節の 1 行にまとめる形にした。

**種別（training_type）タグを詳細画面から削除する理由**（前案では表示していたが撤回した）:

1. **情報ではなく装飾になる**: 種別は `training_types` マスタで「事前相談 / トレーニング / その他」の 3 種のみ。多くの記録が「トレーニング」になるため、ほぼ全画面に同じタグが並ぶ。§7 の「装飾を情報に見せかけない」規律に反する。**ただし「大半がトレーニング」という当初の前提は修正した** — 事前相談などトレーニング以外の記録も実運用で発生するため、画面のラベルは「記録」に統一した（§6）。種別タグを置かない判断は下記 2・3 の理由で支えられており変わらない
2. **§2-1 の禁止事項に抵触する**: 詳細画面のタイトル（`c-detail-title`）は brand-deep であり、その直下に brand-bright のタグを置くと**鮮色が隣接**する（brand-deep × brand-bright = **1.56:1**、同じ色相のため境界の視認は原理的に不可）。種別タグを置かない判断の根拠となる
3. **ダッシュボードと扱いを揃える**: ダッシュボード §4-2 でも同じ理由で種別タグを廃止済み。同じ記録が 2 画面で違う見え方をすると飼い主が混乱する

なお `training_types` 自体は 2026-09 に廃止した（ユーザーレビューでトレーナーが分類は不要と判断したため）。

**画面構成の考え方**（S-1406 / S-1411 と揃える）：
- **見出しはカードの外**（`<h1 class="mb-4">初回設定</h1>` を `.card` の直前に置く）。S-1406「登録情報」・S-1411「登録情報の変更」と同じ位置
- **装飾付きのセクション見出し（旧「── パスワード ──」等）は置かない**が、**装飾のない太字の小見出しは置く**（下の「入力欄のまとまりの小見出し」参照）。装飾を外したのは横線付きの `.eyebrow` がお客様側の他画面にない形で浮くためで、見出しがあること自体を否定したわけではない。装飾を外すことと小見出しを置くことは両立する
- **説明文（旧「○○@example.com のパスワードとご連絡先を設定します」）は置かない**。代わりに**カード先頭に「メールアドレス」のラベルと値の行**を置く。理由：（1）S-1406 でもメールアドレスは表示項目の先頭にあり位置が対応する、（2）初回設定はログイン ID を確認する場面でもあり、行として立っている方が目に入る、（3）説明文をやめることで「ご連絡先」という語がこの画面から消える。マークアップは **S-1411 の「お名前」表示行と同じ**（`text-muted small` のラベルの下に値を置く形。同じ役割の要素が二画面で違う書き方になるのを避ける）
- **姓・名、せい・めいは横二列のまま維持**（`.row.g-2` + `.col-sm-6` の 2 列グリッド）。理由：**姓名は対で入力するもので横に並ぶのが自然**。スマートフォンでも項目 2 つなら収まる。**縦一列の標準（§2-3）に対する意図的な例外**であり、後から縦に直さないこと

**カード内に 3 本の区切り線を引く**（定義：**入力欄のまとまりの境目に引く**）：
- 位置：① パスワード（確認）の下、② めいの下、③ 建物名・部屋番号の下（＝パスワード／氏名の境目、氏名／連絡先の境目、連絡先／愛犬の情報の境目）
- **メールアドレスの表示行の下には引かない**。メールアドレスは**入力欄ではなく表示のみ**の行で、他の入力欄（`.form-control`）と見た目が違う（小さいラベルと枠のない値）ため、線がなくても区切られて見える。境目の性格も「まとまりの切り替わり」ではなく「読む部分と書く部分の切り替わり」
- **パスワードの下・氏名の下・連絡先の下に引く理由**：入力欄と入力欄の境目で、**見た目が同じ要素（`.form-control`）が続くため、線がないと切れ目が分からない**
- **愛犬の情報まとまりの下（最終まとまり）には引かない**。カードの枠が外周を担当するため、カード内側の下端に線を引くと役割が重複する（S-1406 で決めた考え方と同じ）。**2026-09 に愛犬の情報ブロックを追加する前は連絡先まとまりが最終まとまりだった**が、ブロック追加で最終位置が愛犬の情報に移った
- **S-1406 の罫線とは役割が違うので、混同・統一しないこと**：
  - **S-1406 の罫線** = 項目と項目の間を区切る（一項目ごとに一本）。1 行 = 1 項目の確認画面向け
  - **S-1403 の区切り線** = **入力欄のまとまり**とまとまりの間を区切る（複数項目をひとまとめにして境目に一本）。項目数が多い入力フォーム向け
- **経緯**（同じ検討を繰り返さないため）：
  1. セクション見出し（旧「── パスワード ──」等）を外し、項目を素直に縦に並べた
  2. まとまりの境目が分かりにくいため、いったん**「4 つのまとまりを等しく区切る」として 3 本の線**（メール／パスワード／氏名の下）を引いた
  3. 実物を見て、メール下の線は「まとまりの切り替わり」ではなく「読む部分と書く部分の切り替わり」で線の役割が薄いと判断
  4. **定義を「入力欄のまとまりの境目に引く」に変更**し、メールアドレス（入力欄ではない）を対象外にして **2 本にした**
  5. 愛犬の情報ブロックを追加（2026-09）したことで最終まとまりが後ろにずれ、線を 3 本に戻した（連絡先／愛犬の情報の境目に 3 本目を追加）
  6. **2026-09、「区切りが分かりにくい」指摘を受けて濃さを `ink` 8% → 15% → 20% に段階的に変更**。カードの罫線と同じ濃さ（8%）ではまとまりの境目としての強度が足りなかった。まず 15% に濃くしたが、それでも「切れ目」として弱かったため、**さらに 20% まで上げて着地**（paper 上のコントラスト比は 1.10:1 → 1.22:1 → 1.34:1）。**S-1403 に限って**濃くする（`.c-login--wide` スコープで `.border-bottom` を上書き）
- **実装**：入力欄まとまり最後の要素に `pb-3 border-bottom` を追加（`mb-3` は元々の下余白として維持）。**濃さは `.c-login--wide .border-bottom` を `border-bottom-color: rgba(15, 26, 46, 0.20) !important;` で上書き**（`client.scss`）。他画面のカード罫線・入力欄枠には影響させない

**入力欄のまとまりの小見出し**（装飾のない太字）を **4 か所**に置く：
- 位置：① **ログイン情報**（メールアドレス表示行の直前、**2026-09 追加**）、② **お名前**（姓・名 二列グリッドの直前）、③ **ご連絡先**（電話番号入力欄の直前）、④ **愛犬の情報**（愛犬の名前入力欄の直前）
- **文言「お名前」にした理由**：S-1406 の表示項目・S-1411 の表示行が「お名前」で統一されているため、お客様側の他画面と語彙を揃える
- **「ログイン情報」の小見出しを追加した経緯**：当初は**「パスワードのまとまりには小見出しを置かない」**方針だった。理由は「『パスワード』『パスワード（確認）』というラベル自体がまとまりの内容を表しており、その上に『パスワード』という見出しを重ねると同じ語が二回続く」ため。しかし 2026-09 のレビューで「**入力欄のまとまりの区切りが分かりにくい**」との指摘があり、他 3 か所（お名前・ご連絡先・愛犬の情報）に見出しがあってパスワード側だけ無いという非対称が構造把握を難しくしていることが判明した。**文言を「ログイン情報」にすれば**：（1）「パスワード」の語との重複は起きない、（2）**メールアドレスの表示行もこのまとまりに含める**ことで内容としても実態に合う（メールアドレス = ログイン ID、パスワード = 鍵）。4 まとまり全てに小見出しが付き、非対称が解消した。**当時の判断（パスワードに見出しを置かない）を消さず**、覆した理由を併記して残す
- **線と小見出しの役割分担**（両方置く）：
  - **区切り線** = 「ここで切れる」ことを示す（分割）
  - **小見出し** = 「次が何か」を示す（内容の予告）
  - 役割が違うので両方が必要。片方だけにしないこと
- **実装**：`<h2 class="fs-6 fw-bold mb-2">お名前</h2>` の形（Bootstrap ユーティリティのみ）。SCSS 変更なし
  - **見出しタグ `<h2>` を使う理由**：**読み上げソフトに画面の構造を伝えるため**。見た目だけの太字（`<p class="fw-bold">`）では視覚上は見出しに見えるが、読み上げソフトからは段落として認識され、構造が伝わらない
  - **`<h2>` にした理由**：主見出し「初回設定」が `<h1>` なので、その直下の階層は `<h2>`。`<h3>` にするとレベルを飛ばすことになる
  - **`fs-6` の理由**：Bootstrap の `<h2>` は本プロジェクトでは 1.5rem に上書きされている（`client.scss` L136-137 の `$h2-font-size`）が、それでも本文より大きい。`fs-6` は 1rem（`$h6-font-size = $font-size-base`）で本文と完全一致。フォントサイズの装飾を強めると旧 `.eyebrow` を外した経緯を繰り返すため、本文相当まで落とすのが必須
  - **`fs-6` を外してはいけない**。後から「不要なクラス」と見て消されると `<h2>` の 1.5rem に戻り、旧 `.eyebrow` と同じ「浮く見出し」に逆戻りする
  - **文字色は見出し色（`#162D66` = `$brand-deep`）**が付く。`client.scss` L188-191 の `h2 { color: $brand-deep; }` が効くため（`<h1>` と同じ色、ヘッダー帯とも同じ）。当初「太字にするだけで色は変えない」方針で `<p class="fw-bold">` を使ったが、読み上げソフト対応で `<h2>` に変えた結果、見出し色が効いた。**実物を見て「色が付いた方が画面全体で色の階層が整う（ヘッダー帯・`<h1>` と同じ紺で並ぶ）」と判断し維持**。色を外しに来ないこと
  - 太字（`fw-bold`）＋ 見出し色（`$brand-deep`）＋ 本文相当サイズ（`fs-6`）の 3 点で構成。これ以上の装飾（枠線・背景色・下線など）は加えない。旧 `.eyebrow` の失敗を繰り返さないため
- **経緯**（同じ検討を繰り返さないために残す）：
  1. 元は「── パスワード ──」等の横線付きセクション見出しがあった → 装飾が他画面にない形で浮くため外した
  2. 見出しを外した後、項目数が多いためまとまりの境目が分かりにくかった → 区切り線でまとまりを示すことにした
  3. 区切り線だけでは「次のまとまりが何か」の予告がなく構造把握しにくい部分があった → 装飾のない太字の小見出しを 2 か所に追加した（`<p class="fw-bold mb-2">` で色は本文と同じ）
  4. 読み上げソフトに構造を伝えるため `<h2 class="fs-6 fw-bold mb-2">` に変更した → `h2 { color: $brand-deep; }` の指定が効いて文字色が紺になった。実物を見て「見出し色が付いた方が画面全体で色の階層が整う」と判断し維持
  5. **旧の装飾付き見出しには戻さない**。線と小見出しの分業（線＝切れ目、小見出し＝内容予告）で役割を分けている
  6. **「色は変えない」の当初方針は撤回**。見出しタグを使うなら見出し色が付くのが自然で、実物を見て問題ないと確認済み
  7. **2026-09 に愛犬（トレーニー）の情報ブロックを 4 番目に追加**した。線と小見出しの規則（まとまりの境目に線を引く／内容の予告として小見出しを置く）はそのまま適用し、区切り線を 2 本 → 3 本、小見出しを 2 か所 → 3 か所に拡張しただけ。新しい規則は増やしていない。文言は「愛犬の情報」（お客様側の丁寧語体系。トレーナー側の「トレーニー」ではなく、飼い主にとっての呼び方に合わせる）。詳細は screen-design.md S-1403 の設計方針を参照
  8. **2026-09、「区切りが分かりにくい」指摘を受けて 2 点変更**：（a）**パスワードのまとまりに小見出しを追加**（文言「ログイン情報」）→ 小見出し 3 か所 → 4 か所に拡張。（b）**区切り線の濃さを `ink` 8% → 15% → 20% に段階的に変更**（`.c-login--wide` スコープで上書き、他画面には影響させない）。15% を一度試したが、それでも切れ目として弱かったため 20% に上げた。3 の「パスワードには見出しを置かない」・「色は変えない」の当初判断はいずれも撤回するが、判断の履歴として残す

**愛犬の情報ブロック**（**2026-09 追加**、詳細は screen-design.md S-1403 参照）：
- トレーナーはトレーニーの名前だけを登録する運用のため、犬種・性別・誕生日・備考は飼い主に入力してもらう
- 既存トレーニーが 1 件以上あれば **1 頭目**（`id` 昇順の先頭）の値を初期表示、なければ空欄で表示（新規登録）。**2 頭目以降のレコードには一切手を触れない**
- 多頭飼いは備考の案内文「2頭目以降がいらっしゃる場合は、こちらにご記入ください」で対応（動的な行追加はしない。多頭は稀）
- 会員がトレーニーを編集できるのは初回設定のときと、写真の登録・削除（S-1402、要件定義書 6-15-15）のときだけ。それ以外の属性（名前・犬種・性別・誕生日・備考）についてはマイページに編集導線は作らない
- 検討して採らなかった案（ウィザード化・全頭入力欄・0 頭許容）と理由は screen-design.md S-1403 の設計方針を参照

**カード幅の拡張が必要**。既存のログイン画面用の `.c-login-card` は max-width 26rem 相当で、パスワード 2 欄しか載らない。初回設定は氏名 4 欄・電話 2 欄・住所 6 欄に加えて**愛犬の情報 5 欄**が加わるため、`.c-login--wide` モディファイアで md 以上 40rem に拡張する（S-1406 / S-1411 の `.c-settings` と同じ幅）。モバイルでは container 幅で自然に縦積みになる。

**パスワード強度メーターは今回のスコープから外す**。理由：デザイン改良ではなく機能追加であり、JavaScript を要する。強度可視化は独立課題として、JS 実装方針が決まった時点で別枠で扱う（既存の判断を継承）。

### 4-7-1. プライバシーポリシー同意文（S-1403・S-1405 共通）

お客様が最初に個人情報を預ける画面（メールアドレス登録画面・初回設定画面）では、**送信ボタンの手前に控えめな同意文を置く**。個人情報を扱うサービスの慣習に沿い、他社の pre-auth 画面（Booking.com 等）と同じ位置づけ。

**見た目**：

| 項目 | 値 | 補足 |
|---|---|---|
| クラス | `.c-consent-note` | 共通パーシャル `layouts.partials.privacy-consent` に集約 |
| 文字サイズ | 0.8125rem（13px 相当） | 本文 1rem より小さく |
| 色 | `ink` 65%（`rgba(15, 26, 46, 0.65)`） | Meta 相当の副次情報の階層 |
| 揃え | 中央 | カード内フォームの中心軸に合わせる |
| 位置 | 送信ボタンの直前 | 「送信する動作」に紐づけて読ませる |
| リンク | `brand-bright`（既定の `$link-color`） | 本文中の `<a>` は既定の `$link-color`（brand-bright）で描画される。同意文は下線付きで表示され、色 + 下線でリンクとして識別できる。**`target="_blank"` で別タブ**（入力中の内容が消えないため） |

**表示制御**：`config('app.client_portal_privacy_url')` が空のときは、**同意文のブロックごと出力しない**（§9-2 のフッター会社名と同じ扱い）。設定値に URL が入った時点で表示に切り替わる。

**判断の理由**：
- お客様は主に**入力する**ためにこの画面に来ている。同意文を大きく出すと入力の主役を奪う
- 一方、個人情報を預ける前に確認する内容としては読まれる必要があるので、送信ボタンの直前に置く
- リンクを別タブで開くのは、既存の入力を守るため（同一タブ遷移は入力途中の値を破棄させる）
- 訓練所のプライバシーポリシーが確定するまでは URL が空 = 何も表示しない（現状の画面と一切変わらない）状態を保つ

**現行の文言**：「送信することにより、お客様は[プライバシーポリシー]に従って個人データを取り扱うことに同意したものとします。」（フォーマルな表現。事業者の呼称は入れない。角括弧の部分がリンクで、別タブで開く）

**将来「利用規約」を追加する場合**：同じパーシャル内にリンクを並べる（例：「送信することにより、お客様は[利用規約]および[プライバシーポリシー]に同意し、[プライバシーポリシー]に従って個人データを取り扱うことに同意したものとします。」など）。設定値も `client_portal_terms_url` を並べて追加する。

### 4-8. 無効なトークン（メールアドレス登録用 URL・ログイン用リンク・メールアドレス確認リンク・パスワード再設定リンク共通）

```
┌──────────────────────────────────────────┐
│                                          │
│         [wordmark]                        │
│                                          │
│         この案内は開けません              │  ← $title
│                                          │
│         リンクの有効期限が切れています。  │  ← $message（既存の変数）
│                                          │
│         ── 次にできること ────            │  ← 追加ブロック
│                                          │
```

「なぜ入れないか」だけで終わらせず、「次にどうすればよいか」を必ず 1 ブロック分添える。$title と $message はコントローラから渡ってくる既存の変数を尊重し、周りだけデザインで補強する。

**適用範囲**（段階 4-1 で拡張、段階 4-3・4-4 で追加）：
- **メールアドレス登録用 URL（S-1405）** の無効・期限切れ・使用済み時
- **ログイン用リンク（S-1403 = 初回設定画面のトークン）** の無効・期限切れ・使用済み時
- **メールアドレス確認リンク（S-1406 派生）** の無効・期限切れ・使用済み・重複時（段階 4-3）
- **パスワード再設定リンク（S-1408 = パスワード再設定画面のトークン）** の無効・期限切れ・使用済み時（段階 4-4）

両者は同じ `$title` / `$message` 変数構造とデザインを共有する（判断は「pre-auth の説明カード」で一貫させる）。次にできることの文言も共通で 2 項目（トレーナーへの新しい案内依頼／別メールの確認）を掲載する。

### 4-9. メールアドレス登録

トレーナーから受け取ったメールアドレス登録用 URL から開く、認証不要の pre-auth 画面。入力状態と完了状態を同一 URL 上で切り替える（別画面にしない）。

カード幅は既存の `.c-login-card`（26rem 相当）で足りる（項目 1 つのため）。

### 4-10. 登録情報（S-1406 / S-1409 / S-1410 / S-1411）

**四画面に分けた構成**。登録情報（S-1406、確認画面）を入口とし、登録情報の変更（S-1411）・メールアドレスの変更（S-1409）・パスワードの変更（S-1410）の 3 つの変更フォームを、それぞれ独立画面として開く。認証後レイアウト（`layouts.client`）の中に、ダッシュボードや記録詳細と同じ回遊要素（§4-0 のナビ・フッター）を継承する。

**画面を「確認」と「変更（3 つ）」の二階層に分けた理由**：旧設計では、ヘッダーの「登録情報」をクリックするといきなり変更フォームが表示されていたが、**自分の登録内容を確認するだけの用途に応えられない**という課題があった（変更画面には表示のみの項目やパスワードのマスクが混ざり、確認用には情報が読み取りにくい）。**確認画面と変更フォームを分ける**ことで、確認だけしたいときと変更したいときの両方に応える。

**S-1406 を確認画面側に据えた理由**：確認画面と変更フォームのどちらに新番号（S-1411）を割り当てるかで、**確認画面側を S-1406 のままにする**判断をした。**ヘッダーの「登録情報」というリンク名が指す先の画面 ID が S-1406 のまま**になり、画面名と画面 ID の対応関係がねじれないため。逆に、変更フォームを S-1406 に残して確認画面を新番号にすると、「登録情報」という画面名の指す先が新番号側に移り、後から設計書を読む人が混乱する。

**変更フォームを 3 つに分けた理由**（前段階の作業で決定済み、経緯）：三つの操作（メール変更・パスワード変更・基本情報変更）を同時に行うことはないため、一画面にまとめる必然性がない。まとめると、送信後にページ先頭へ移動する挙動と相まって、**下側セクションのエラー・完了メッセージが画面外になり見えない**問題が生じる。一画面一フォームに分割することで、**エラー・完了とも画面上部に自然に載せられる**（フォームが一つなので位置に迷いがない）。

**補足説明を先頭に置く理由**：確認メール経由の 2 段階の流れ（申し込み → 確認リンク → 切替）は他の変更操作より珍しい。押す前に長い説明があるとかえって迷わせるため、入口ボタン（S-1406 側）ではなく画面を開いた後にその場で説明する。文言は簡潔に「新しいアドレスに確認メールを送ります。メールのリンクを開くと、メールアドレスが切り替わります。」の 2 文。

**戻る導線**：`.c-detail-back` で**「← 戻る」**を左上に置く（3 変更画面 S-1409 / S-1410 / S-1411 で共通のマークアップ）。矢印は `<span aria-hidden="true">←</span>` で装飾扱い、後ろに「戻る」の文字を置く。

**「← 戻る」にした理由**：
- **記号だけでは押せることが分かりにくい**。「戻る」の文字を添えると動作が明確になる
- **画面名を書かない**（「登録情報に戻る」等にしない）：将来この画面への入口が増えても文言を直さずに済む
- **一度「記号のみ」も試したが「← 戻る」に変えた**。同じ検討を繰り返さないため経緯を残す：矢印記号のみに変えた（`aria-label="登録情報に戻る"` を付ける・`.c-detail-back` に `padding` を追加して当たり判定を確保する対応を伴っていた）が、実物を見て「押せることが分かりにくい」と判断し、文字を添える形に戻した。文字が付くことで `aria-label` と当たり判定の追加 padding は不要になり、`.c-detail-back` の SCSS も文字リンク前提の状態に戻した

**S-1404 の「HOME」を統一しない理由**：お客様側の戻りリンクにはもう一つ S-1404（トレーニング記録詳細）→ S-1402（ダッシュボード）の「HOME」がある。これは今回の 3 画面と**文言を分ける**：
- 「← 戻る」は「一つ前の画面へ」を意味する（戻り先は履歴の直前）。**矢印は「戻る方向」を示す記号として付ける**
- 「HOME」は「特定の場所へ」を意味する（戻り先はダッシュボード＝ HOME に固定）。**行き先を名指しするリンクなので矢印を付けない**（フッターの HOME と同じ形。2026-09 のユーザーレビューの要望で、以前付けていた矢印を外した）
- S-1404 からダッシュボードへ行くのは「HOME に行く」性格が強く、フッターの HOME リンクとも対応しているため、あえて別文言にする
- お客様側に 2 種類の戻りリンクが並ぶが、これは**意図した区別**（後から統一しようとしないこと）。区別の手段は「文言（『戻る』／『HOME』）＋矢印の有無」の 2 つ

**エラー・完了メッセージ**：エラー・完了とも同画面（S-1409）自身のフォーム上部に表示する（成功時は自分自身に `redirect()` で戻り、共通レイアウトの `session('success')` 受け皿で表示する）。フォームが 1 つなので名前付きエラーバッグは使わない。

**現在のメールアドレスは表示しない**：この画面には現在値の再掲を置かない。理由：
- **直前の S-1406（登録情報）で見たばかりの情報の再掲になる**。S-1406 ではメールアドレスがログイン ID を兼ねるため表示項目の先頭に置いており、お客様はその値を見てからこの画面へ来る
- **フォームの入力項目が「新しいメールアドレス」「現在のパスワード」の 2 つだけ**なので、上に表示のみの行があると、どれが入力欄なのかが一瞬分かりにくくなる

**S-1411 に氏名・かなが表示のみで残るのは意図した違い**（項目の性格が異なる）：
- S-1409 の「現在のメールアドレス」は**変更できる項目の現在値**の再掲。同じ画面に「新しいメールアドレス」を入れる欄があるので、現在値を出さなくても用は足りる
- S-1411 の氏名・かなは**変更できない項目**を示している。表示を消すと「この画面では氏名は変えられない」ことが伝わらなくなる
- よって「変更フォームで現在値を出すか出さないか」は項目の性格ごとに判断する。一律に揃えるべきではない

- **「基本情報を保存」は避ける**：「基本情報」は画面分割前に三つのフォームを区別するための呼び名で、分割後は区別の必要がない。ここだけ「基本情報」が出るとお客様側の他の画面にはない呼び名が浮く

- **完了メッセージは操作の後に目に入る**ため、何が変わったのかを明示した方がお客様が安心できる
- 一見ちぐはぐだが、置き場所と役割の違いに応じた自然な使い分けで、揃えるべきではない

**S-1409（メールアドレスの変更）のボタン「確認メールを送る」は揃えない**：S-1410 / S-1411 は「変更する」に統一したが、S-1409 の送信は**「変更を完了する」操作ではなく「確認メールを送る」操作**で動作の性格が違う（実際の切替はメールのリンクを開いた時点で起きる）。押した瞬間の動作を正しく表す文言として「確認メールを送る」を維持する。

## 5. シグネチャー

**日付ブロックを維持する**（初版からの引き継ぎ）。**表示形態は画面幅で切り替える**（下記「表示形態の分岐」参照、実装後の実機確認で必要と判明した）。色は `brand-bright`、文字は `mat`（白）、書体はシステムサンス（本文書体）ウェイト 700。mat 文字 on brand-bright 面は **8.38:1** で AA / AAA テキスト基準を通過する。主要ボタンと同じ色・文字色で構成することで、「操作する場所」と「時間の目印」が紺二色方針の中で揃う。カードの本体は mat 面で、写真とノートが並ぶ。

### 5-1. 表示形態の分岐（デスクトップ / モバイル）

| 画面幅 | 形態 | 配置 | 表記例 |
|---|---|---|---|
| **≥ 576px**（Bootstrap `sm` 以上） | **brand-bright 縦帯** | カードの**左端**、日本語**縦組み** | `8月` / `2` / `（金）`（縦に 3 段） |
| **< 576px**（Bootstrap `sm` 未満、スマートフォン想定） | **brand-bright 横帯** | カードの**上部**、日本語**横 1 行** | `8月 2日（金）`（横一列） |

日の数字はどちらの形態でもシステムサンス 700、大きめの font-size で組む。

### 5-2. なぜ分岐が必要か

初版〜前案では**モバイルでも縦帯を維持**する想定でワイヤーフレームを描いていたが、**実装後の実機幅（400px 前後）確認で以下の問題が判明**：

- モバイル幅ではカード本体（date-block の右）の写真が **2 列以上に折り返し**、カードが縦に伸びる
- 日付ブロックの高さはカード全体に追随（`.c-session` の `align-items: stretch`）するため、brand-bright の縦帯も一緒に縦に伸びる
- 結果、**文字のない brand-bright の柱**がカード左に長く残り、「日付が視覚のリズムを作る」という本節の意図が「橙の柱が並ぶ装飾」の印象に変わる

**根本原因**: モバイル幅では写真の折り返しにより「日付ブロックとカード本体の縦横比」が縦帯の想定を超える。縦帯は「カード高さ ≒ date-block 高さ」を前提としており、写真が横 1 列で収まる幅（≥ 576px）でのみ成立する。

### 5-3. 横帯にしても §5 の効果が損なわれない理由

- **「この写真はいつのものか」を語る効果**: カード上部の横帯は写真グリッドの直前に日付を置くため、視線の流れ「日付 → 写真」が自然。むしろ写真より先に日付が来ることで「これはいつのトレーニング」がより明確に伝わる
- **スクロール時のリズム効果**: 縦フィード全体で見たとき、brand-bright の横帯が**カード上端に等間隔で並ぶ**ため、リズムは水平線として維持される（縦帯が縦に連続していたリズムの水平版）。「成長の連なり」を反復で示す構造は残る
- 縦帯・横帯どちらも「brand-bright の色帯 + 日本語 + カード内の一意な位置での反復」という §5 の 3 要素を満たす

### 5-4. デスクトップ側の維持

デスクトップ（≥ 576px）は写真が横 1 列に収まり、date-block の高さがカード全体の高さを支配する。縦帯が縦組み日本語で機能する条件が揃っているため、**デスクトップ側は縦帯を維持**する。

### 5-5. 別要素に変更しない判断の理由（引き継ぎ）

- アルバム的方向でも「この写真はいつのものか」を写真の隣で語る役割は変わらず必要
- 別案として「写真オーバーレイの日付」「縦線タイムライン装飾」「各セッションで日付ブロックの色を回転」を検討したが、
  - 写真オーバーレイは記録によって写真が無い場合成立せず
  - 縦線タイムラインは装飾要素（線）の追加を必要とし、
  - 色の回転は色が持つ意味を消し「装飾のためだけの色使い」になる（制約5 に抵触）
- 日付ブロックを維持する選択が最も少ない装飾で最大の構造効果を生む

### 5-6. 日本語表記の維持

「8月 / 2 / 金」の日本語表記を維持する（初版で決定した論理はそのまま有効）。英語 `AUG / 2 / FRI` は欧米カレンダーチップ UI の借用で「一目で他と区別する要素」というこの節の主張と矛盾する、という理由が引き続き有効。**モバイル横帯でも英語表記に切り替えない**（「8月 2日（金）」の日本語横書き）。

**曜日は括弧で囲む**。縦帯・横帯・記録詳細タイトルのいずれでも全角括弧を付ける（`（日）`）。当初デスクトップの縦帯だけ素の 1 文字（`日`）としていたが、**「日」が日曜日の意味なのか日付の単位（2日）なのか区別できない**という指摘があった。横帯と記録詳細タイトルは当初から括弧付きだったため、縦帯を揃える形で解消した。

土曜を青・日曜を赤にする色分けも検討したが採用しなかった。brand-bright 帯の上では赤らしい赤が AA を満たすほど暗くしないと成立せず、暗くすると帯とほぼ同じ焦茶になって「今と同じ色」に見える。**赤と橙は色相を共有しているため、橙の面の上で赤を赤として成立させることは原理的にできない**。

### 5-7. 構造で成立させる規律（制約5・§2-1 との整合）

- 装飾（封筒・ハンコ・破線・足跡・パーティー装飾・シール）は一切入れない
- brand-bright の色帯 + システムサンス（ウェイト 700）の日本語 + 反復 の 3 要素だけでシグネチャーを成立させる
- 犬の名前・写真を将来受け取る余地は、日付ブロックの**下段**（縦帯時）／**右端**（横帯時）に確保する（現状は非表示、将来「タロウ」等が入る）
- **§2-1 制約との整合**（横帯形態でも維持）：
  - brand-bright 面の文字は `mat`（白）のみ（8.38:1、AA / AAA テキスト基準を通過。ボタンと同じ組み合わせで統一）
  - 鮮色同士を直接隣接させない — 横帯（brand-bright）と写真グリッド（背景 mat）の間は横帯の下 padding で分離。**日付帯 (brand-bright) の周辺に `brand-deep` / `madder` の面を配置しない**（brand-deep × brand-bright 比 1.56 で最も近い）
  - カード境界は罫線 + 影の両方（横帯化しても `.c-session` の border と box-shadow は不変）

**画面の文言の句点**：会員側画面（`resources/views/client/` 配下）に表示される**文**（主語と述語がある文章）には句点（「。」）を付ける。**ラベル・見出し・ボタン・プレースホルダ・eyebrow** など**文でないもの**は対象外。**箇条書き（`<li>`）も、文であれば句点を付ける**（箇条書きに句点を付けない流儀もあるが、会員向け画面は下記の丁寧語体系で「〜します。」「〜ください。」の文が並ぶため、揃えるほうが落ち着く）。

判断の根拠：
- 会員向け画面は**丁寧語体系**で、「ご覧いただけます。」「ご記入ください。」のような文が並ぶ。句点の有無が混ざると落ち着かない
- 「短文だから句点なし」は書き手の感覚に依存する。**どこからが短文かの線引きが人によって変わり、次に書く人がまた迷う**。「文なら句点を付ける」なら判断に迷わない
- 「付ける」に統一した場合の修正箇所と「外す」に統一した場合の修正箇所がほぼ同数（5 箇所 vs 3 箇所）で、どちらでも実装コストは変わらないため、統一の観点で判断に迷わない前者を採った

**2026-09 に統一**：それ以前は句点の有無が不揃いだった。特に `.form-text`（フォーム補足文）の中でも、強度要件のヘルプ文（「8 文字以上で…入れてください。」）は句点あり、多頭飼い案内（「2頭目以降がいる場合も、こちらにご記入ください」）は句点なしで混在していた。**画面に出る文はすべて句点あり**で統一した。トレーナー側画面（`resources/views/` の `client/` 以外）は別の文体で運用しており、本方針の対象外。

### 6-1. お客様に送るメールの件名

**件名は `【事業者名】○○○` の形に統一する**。

- 事業者名は `config('app.client_portal_company')` から取る
- 事業者名が未設定・空の場合は角括弧を出さず、下地の題名（`○○○`）だけを出す（例：「マイページのご登録手続き」）
- 各 Mail クラスの `envelope()` からは共通ヘルパー `App\Mail\ClientMailEnvelope::build('題名')` を呼ぶ形にして、件名・差出人・返信先の組み立てを 1 か所に集約する（§6-1-1 参照）

**題名の書き方の指針**：

- **内部の呼び名を使わない**（「ログイン用リンク」「メールアドレス確認リンク」「パスワード再設定リンク」などは設計書上の呼称。件名では使わない）
- お客様が受信箱で見て**何のメールか分かる言葉**にする
- 「マイページ」という呼び名は件名でも使ってよい（用語集参照の通り、お客様向けの呼び名として定着）
- **通知系は能動態**にする（「変更されました」→「変更しました」）。事業者側からお客様への通知として自然

|---|---|---|
| `ClientLoginLinkMail` | メールアドレス登録後のログイン用リンク送信 | マイページのご登録手続き |
| `ClientSetupCompletedMail` | 初回設定完了の通知（ログインURL案内） | マイページのご登録が完了しました |
| `ClientEmailChangeConfirmMail` | メールアドレス変更の確認リンク | メールアドレス変更のご確認 |
| `ClientEmailChangedMail` | メールアドレス変更の完了通知（古いアドレスへ） | メールアドレスを変更しました |
| `ClientPasswordChangedMail` | パスワード変更の完了通知 | パスワードを変更しました |
| `ClientPasswordResetMail` | パスワード再設定リンク | パスワード再設定のご案内 |

**判断の理由**：
- 事業者名を先頭に置くのは、受信箱でお客様が「どこから来たメール」かをまず判別できるようにするため
- 内部呼称の排除は、§6 表全体で貫いている「内部語彙を露出させない」規律の延長線
- 通知系の能動態化は、事業者側が主体で通知しているという文脈を明確にするため

### 6-1-1. お客様に送るメールの差出人・返信先

**差出人（From）**：

- **アドレス**：`MAIL_FROM_ADDRESS`（`noreply@inmylife1965.com`）を使用。値そのものは変えない
- **表示名**：`config('app.client_portal_company')` を使う。**空の場合は表示名を付けず、アドレスのみ**を From に載せる
- **空のときにプロダクト名や `MAIL_FROM_NAME` にフォールバックしない**：既存の `MAIL_FROM_NAME` は `${APP_NAME}` = 「トレーニング記録管理システム」で、これはトレーナー側の管理システム名。お客様の受信箱に見せると「なぜ管理システムから届くのか」の困惑を生む。**確定するまで勝手に名を付けない**（件名の「事業者名なしなら角括弧を出さない」と同じ考え方）

**返信先（Reply-To）**：

- **設定値**：`config('app.client_portal_reply_to')`（env `CLIENT_PORTAL_REPLY_TO`）を使う。**空の場合は Reply-To ヘッダを付けない**（返信は From アドレスに届く）
- 従前は開発会社（インマイライフ）のアドレスがハードコードされていたが、**お客様の返信は事業者に届くべき**。事業者側の問い合わせアドレスが確定するまでは空にしておき、確定後に env に設定するだけで切り替わる形にする
- 空でも From アドレス自体に返信が届くため、返信経路が完全に絶たれるわけではない（`noreply` は運用上返信を受けない前提だが、返信を送信した側にはエラーが返る）

**共通化**：件名・差出人・返信先の 3 要素を、単一の共通ヘルパー **`App\Mail\ClientMailEnvelope::build($topic): Envelope`** に集約した。各 Mail クラスの `envelope()` は 1 行の呼び出しになる：

```php
public function envelope(): Envelope
{
    return ClientMailEnvelope::build('マイページのご登録手続き');
}
```

事業者名や返信先アドレスが変わっても、`.env` を書き換えるだけで 5 通のメールすべてに反映される。設定値を追加する場合（例：BCC、追加の Reply-To）も、`ClientMailEnvelope::build()` を拡張すれば全メールに一括で行き渡る。

### 6-2. お客様に送るメールの本文（末尾の案内）

**リンク付きの案内メール**（ログイン用リンク・メールアドレス変更確認リンク・パスワード再設定リンク）では、末尾を **2 行に分けて書く**：

```
有効期限を過ぎた場合は、担当のトレーナーにご連絡ください。
心当たりがない場合は、このメールは無視してください。
```

- 期限切れは連絡が必要（お客様は困っているはず）
- 心当たりがないケースは第三者がアドレスを入れただけの可能性で、リンク自体は本人が使わなければ効果を持たない。**無視で済む**という誘導が正しい

**通知系メール**（メールアドレス変更完了・パスワード変更完了）では、心当たりがない場合の扱いが違う：**変更はすでに起きた**あとの通知なので、心当たりがなければ第三者による不正の可能性がある。**担当トレーナーに連絡**する経路を残す（維持）。

**通知系のバリアント（`ClientSetupCompletedMail`）**：初回設定完了の通知はログインURLを案内するためリンクを持つが、URL は「保存しておいて次回以降ログインに使う」恒常リンクであり有効期限を持たない。そのためリンク付き 3 通の「有効期限を過ぎた場合〜」の 1 行は載せない。加えて、通知系 2 通と違って**末尾の「心当たりがない場合は、担当のトレーナーにご連絡ください。」も持たない**。理由は次の 3 つ：（1）このメールはお客様自身がパスワードと基本情報を入力し終えた**直後**に届くため、「心当たりがない」という状況がそもそも成立しない。（2）仮に第三者が勝手に設定していたのならログイン用リンク自体が漏れていたという話で、この一文では救えない（不正の兆候を検知する意味を持たない）。（3）このメールは**お客様に保存してもらうことが目的**であり、末尾に不安を与える文を置くのは目的と逆行する。よって本文の最後は「このメールは保存しておいてください。」で終わる形にする。

**通知系メールの本文の形**は、リンク付き 3 通と同じく 3 パーツで揃える：

```
[何が起きたか]。

変更日時：{{ Y年n月j日 H:i }}

心当たりがない場合は、担当のトレーナーにご連絡ください。
```

例（パスワード変更完了）：

```
パスワードを変更しました。

変更日時：2026年9月13日 15:00

心当たりがない場合は、担当のトレーナーにご連絡ください。
```

例（メールアドレス変更完了）：

```
メールアドレスを変更しました。

変更日時：2026年9月13日 15:00

心当たりがない場合は、担当のトレーナーにご連絡ください。
```

**日時を載せる理由**：
- 変更が発生してから通知が届くまでの時間差で、お客様が「自分でやったのか記憶が曖昧」になる場合がある。**日時があれば身に覚えを確認する手がかりになる**
- 第三者による不正変更を疑う場合、時刻から「自分がその時刻に何をしていたか」を思い出せる
- リンク付きメールの「有効期限：Y年n月j日 H:i まで」と表記形式を揃えることで、お客様がメール全般で日時表記に慣れる

**日時の取得方法**：
- コントローラ側で `$changedAt = now()` を **トランザクション開始直前** に取得する（`SettingsController::updatePassword` / `EmailChangeController::confirm`）
- Mail クラスのコンストラクタで `CarbonInterface $changedAt` を受け取り、Blade に `with` で渡す
- `$client->updated_at` を使う手もあるが、「変更が行われた時刻」を明示的に取得する方が意図が伝わる

**「ログイン用パスワード」→「パスワード」**：マイページのパスワードは 1 種類しかないため、「ログイン用」の限定は不要。単に「パスワード」と表記する。

### 6-2-1. 本文で内部の呼び名を使わない

**メール本文に内部の呼び名（設計書上の呼称）を露出させない**。件名で採用した規律（§6-1）を本文にも適用する。

**内部の呼び名の例**（用語集に定義されている設計書上の識別）：
- 「ログイン用リンク」（用語集 No.9）
- 「メールアドレス確認リンク」（同 No.11）
- 「パスワード再設定リンク」（同 No.17）
- 「メールアドレス登録用 URL」（同 No.8）
- 「初回設定」（同 No.10）— 用語としては登録済みだが、「初回設定画面」の形にすると画面 ID 感が残る

**本文での書き換え方針**：
- URL の手前に置いていた見出し（「ログイン用リンク：」「確認リンク：」「再設定リンク：」）は **削除する**。直前の説明文（「下記の URL を開くと…」）で URL の存在が伝わるため、見出しを付けても情報として重複するだけ
- 「初回設定画面」のような画面 ID 感の残る言葉は、**動作で言い換える**（「パスワードと基本情報を設定してください」など）
- 本文に「URL」を表示する場合の書き方は **「下記の URL を開くと…」** に統一（「下記のリンクを開くと…」も可だが、`URL` 表記に揃える方が短く読みやすい）

**判断の理由**：
- お客様が読んで**何をすればよいか分かる**ことを最優先する。内部呼称は設計書やコードでは有用でも、お客様には伝わりにくい
- 内部呼称と対応する動作をお客様目線の言葉で表現することで、メールを開いた直後の行動が迷わない

**設計書・コード側での扱い**：
- 用語集の呼称（No.8〜No.11・No.17 等）と、Mail クラス名（`ClientLoginLinkMail` 等）・ルート名・DB テーブル名は **引き続き使う**（内部の識別として必要）
- お客様に届く文言（件名・本文）に限って、内部呼称を露出させない

## 7. 自己批評

方向性が「便り」から「アルバム・成長記録」へ、配色が中間色から vivid へ、書体は明朝から丸ゴシックを検討したが最終的に**システム日本語スタックのみ**（Web フォント無し）へ着地した。この新方向に対して**どこが凡庸か・何を変えたか・何を失ったか**を書く。

### 新方向で AI が反射的に出す答え（それを避けた記述）

1. **「ビビッドな色で楽しさを出す」ブリーフに対して AI が反射で選ぶのは、子供向けアプリのようなカラフル配色**（primary red-yellow-blue、または pastel rainbow）。今回はこれを避け、**オレンジ二色**（`terracotta` = 暗いオレンジ = ヘッダー帯・リンク・見出し、`orange-bright` = 明るいオレンジ = ボタン・日付帯、`madder` = 破棄）に絞った。色数を絞って構造に集中させる規律で、幼稚さを回避しつつ「元気さ」を作る。

2. **絵文字・イラスト・手描き風装飾・足跡・パーティー要素で「楽しさ」を作るのは AI 既定パターン**。制約5 で明文化・すべて却下。楽しさは色・組版・余白・構造で作る。この規律は初版の「便り」でメタファーを装飾に堕させないと決めた原則の延長線上にある。

3. **犬シルエット・足跡アイコン・骨のモチーフ**は制約5 で明文化・却下。すべての犬関連サービスに存在する定番であり、独自性がない。犬の存在は、日付ブロック下段の予約領域（将来の犬名・犬写真）で構造として表現する。

4. **丸ゴシックとして真っ先に選ばれがちなのは M PLUS Rounded 1c または Kosugi Maru**。前者は Google Fonts で最頻出、後者は 1 ウェイトのみ。→ 使用頻度が抑えめで階層作りに耐える **Zen Maru Gothic** を一度選んだが、後日**実測サイズが 90.8KB**と判明して撤回（詳細は下記 13 番）。丸みのある書体自体は全て却下し、システム日本語スタックのみに着地した。

5. **鮮やかな色を全面に敷くと写真が死ぬ**。アルバム方向で最も陥りやすい失敗。→ 「色は構造に、面は静か」を **§2-0 の規律として明文化**。vivid colors を面として敷くのは**ヘッダー帯 (`terracotta`)・主要ボタン (`orange-bright`)・日付ブロック帯 (`orange-bright`)・成功トースト (`terracotta`) の 4 用途だけ**に絞り、カード本体・写真グリッドの背景は `mat` (#FFFFFF) と `paper` (#FAF7F0) の無彩色に固定。純白のマットは写真の色を最も正しく見せるため、写真アルバムの伝統をそのまま踏襲する。

6. **成長のグラフ・進捗バー・スター評価・アチーブメントバッジ**は「成長記録」ブリーフで AI が出しがちなゲーミフィケーション装飾。→ 数値可視化には走らない。トレーニングの「回数」ではなく「その日何をしたか」の積み重ねを見せるアプリの本質を尊重する。ダッシュボードの hero も「進捗指標カード」ではなく、単に最新のセッションカードそのもの（初版から維持）。

### 初版から失ったもの（自覚しておくべきトレードオフ）

7. **静けさ・大人の落ち着き**: 初版の「明朝 + meadow + forest」の組み合わせが持っていた**書物のような品**は消えた。今は「terracotta + システムサンス（ウェイト・サイズ・色による階層）」の**元気さ**を主人格にした。方向転換の代償として明示的に受け入れる。ブリーフが変わった以上、「静けさ」を守ることは新方向と両立しない。

8. **中間色の絶妙さ**: `meadow #EEF1E8` の緑寄り中間色は palette の独自性を担っていた。今の `paper #F5F3EC` はより一般的な紙色に近く、その独自性は弱くなった。

    **補色配置による独自性**: `cobalt` + `persimmon` の 2 極構造は色相差を持ち、palette の独自性と役割識別性を同時に担っていた。オレンジ単極化により両方を失った。独自性は色相の対比ではなく「鮮色を帯・ボタン・日付帯だけに集中させる規律」（§2-0）で担保する形に変わった。

9. **書体固有の個性**: 初版で Zen Old Mincho（明朝）を選んだ理由は「手紙を書いた人の肌温度」を出すため、改訂版で Zen Maru Gothic を選んだ理由は「丸みで元気を出す」ためだった。**今回はどちらも失い、システム日本語スタックの中庸な字形になった**。書体の個性が担っていた「らしさ」は、色（terracotta）・ウェイト（700）・letter-spacing・サイズ で代替する（§3 型スケール）。書体で語れる情緒は失うが、モバイル読者に対して 90.8KB の追加転送を強いる方が UX の損失として大きい、と判断した。

### 初版の失敗を教訓として組み込んだ点

10. **アクセシビリティを事前計算した**。初版では `tennis` をフォーカスリング・新着ピップに割り当てて 1.52:1 / 1.39:1 で WCAG 1.4.11 未達を後から指摘され撤回した。今回は palette 設計段階で全ての主要組み合わせのコントラストを机上計算し、明るいオレンジ（`orange-bright` 相当）が明色地上で 3:1 前後と初版 tennis と同じ罠を持つことを事前に発見。**用途を「面 + 白文字のペア専用」に限定**して罠に陥らない構造にした（§2-1）。「vivid な色は面としてのみ、短文の白文字と組んで使う」という規約は、tennis 事故の一般化した教訓。

11. **フォーカスリングは二重輪郭**。単色では「明色地」と「vivid CTA 面」を両立できないという初版で学んだ事実を、机上計算で確認した上で `box-shadow: 0 0 0 3px $mat, 0 0 0 5px $ink` の二重輪郭を採用。terracotta / orange-bright / madder / driftwood のいずれの面上でも、**内側 mat リングまたは外側 ink リングのいずれかが 3:1 以上で可視**であることを事前保証した（terracotta: 内側 mat 5.18 / orange-bright: 内側 mat 3.21・外側 ink 5.85 で二重に担保 / madder: 内側 mat 10.02 / driftwood: 内側 mat 6.06）。この二重輪郭の仕様は基調色の変更を経ても据置。

12. **tabular-nums を body 全体に適用しない**。初版では body に適用して和文の数字にまで作用させていた。今回は日付・件数・時刻・電話番号の要素に限定（§3 数字の扱い）。適用範囲を絞ることも「装飾を最小限にする」規律の一部。

13. **Zen Maru Gothic の実効サイズを 40〜80KB と見積もったが、ブラウザ実測で 90.8KB（CSS 29KB + woff2 61.9KB）だった**。見積もりの立て方が甘かった — Google Fonts の CSS 分（動的サブセットのために `@font-face` 宣言が 100 個以上並ぶ 29KB）を数えていなかった。CSS 分は使用箇所を絞っても減らない構造的なコストで、他の丸ゴシック候補（M PLUS Rounded 1c / Kosugi Maru / Klee One）も同じ Google Fonts の仕組みを使うため 20〜30KB は同様に発生する。→ 全候補を不採用に切り替え、システム日本語スタックのみで組む方針にした。**初版で `tennis` のコントラストを実測せず 1.5:1 の失敗をした構造と同じ**（数字を確かめずに設計判断をした）。今回も「見積もり値をブラウザで測る」プロセスを設計段階に組み込まなかったのが原因。次回は Web フォント採用の判断で**必ず実測してから決める**規則を追加する。

14. **モバイル向けワイヤーフレームを「写真が横 1 列に収まる前提」で描いていた**。実装後、実機幅（400px 前後）で確認して初めて、写真が 2 列以上に折り返し・カードが縦に伸び・日付ブロックの cobalt 縦帯も一緒に間延びし、「日付が視覚のリズムを作る」（§5）意図が「青い柱が並ぶ装飾」に変質してしまうことが判明した。→ **モバイル（< 576px）は cobalt 横帯 に切り替え**、日付をカード上部に横 1 行で置く形態に修正した（§5-1）。デスクトップ側は縦帯を維持。**tennis の 1.5:1（数字を確かめず色を選んだ）・Zen Maru Gothic の 90.8KB（数字を確かめずサイズを見積もった）と同じ構造**の失敗（**実物・実測を確かめずに設計判断をした**）。次回はモバイル向けワイヤーフレームを描く際に**実機幅で写真の折り返しを検証してから決める**規則を追加する。

### 別種の失敗: 判断の波及と検証の取りこぼし

上記 10〜14 は「実物・実測を確かめずに設計判断をした」失敗だった。以下はそれとは**別種の失敗**であり、2 つの系統がある。ひとつは「1 箇所を直したときに、同じ判断が及ぶ他の箇所を点検しなかった」失敗（15・17・18）。もうひとつは「検証の方法そのものを取り違えた」失敗（16）である。

15. **ダッシュボード（§4-2）から種別タグを廃止した際、同じ判断が及ぶ他の箇所を点検せず、設計書内に複数の自己矛盾を残した**。具体的には以下 5 箇所が古い前提（種別タグを表示する）のまま残っていた：
    - §3 型スケール表: H3 の用途例に「セッションカード内のトレーニング種別」
    - §3 表下注記: H3 を ink にする理由として「トレーニング種別を cobalt にすると」
    - §4-2 構造の変更: 「カード内に日付・種別・写真数枚・ノート冒頭を同居させる」
    - §4-4 ワイヤーフレーム + ポイント欄: 「服従訓練 ← タグ（鮮色面 + 文字）」・「日付・種別・トレーナー・時刻はヘッダーブロックに統合」
    - §6 文言書き換え表: 「（日付と種別を主役に）」

    この失敗は 10〜14 の「実測を怠った」パターンとは構造が異なる。数字は正しく測っていたし、設計判断（種別タグ廃止）自体も正しかった。**問題は「その判断が波及する範囲を検索しなかった」こと**。§4-2 だけを直して満足し、他節を確認しなかった。実装（`show.blade.php`）が §4-4 と食い違ったことで、レビュー時に初めて発覚した。

    再発防止として以下の**規則を追加**する：**「設計上の判断を変更したときは、その判断が参照されている全箇所を検索して点検する」**。具体的な運用：
    - 廃止・変更するトークン、要素、規約について、その名前で設計書全体を grep する
    - 見つかった全参照が新方針と整合しているかを確認する
    - 整合していない箇所は同じ turn で全て修正する（部分修正で止めない）
    - 実装（コード）と設計書の両方を対象とする

16. **色の選定において、測る指標を取り違え、さらに測れない性質があることを見落とした**。基調色を cobalt からオレンジへ変える判断を、当初「トークンの値の差し替え」と見積もった。実際には役割間の識別可能性という構造そのものが変わる判断であり、確定までに 3 回の実機確認を要した。

    **第一の失敗 — コントラスト比だけを見ていた**。濃オレンジ `#C2410C` と当時の破棄色 `ember #B2311C` は比 1.21 で、輝度差の観点では「どちらも面として使える」としか読めない。色差 ΔE を測って初めて **12.7**、つまり人間の目には「同じ色」であることが分かり、破棄アクションの色を動かさざるを得ないと判明した。

    → **規則を追加**する：**「2 つの色を役割で区別させる設計判断をするときは、コントラスト比だけでなく色差 ΔE も測る」**。コントラスト比は「文字が読めるか」の指標であって「2 色を見分けられるか」の指標ではない。§7-10（tennis のコントラスト未計測）・§7-13（フォントサイズの未実測）と同じく「測るべき数字を測らなかった」失敗だが、今回は**測る対象の指標を取り違えていた**点が異なる。

    **第二の失敗 — 数値制約を満たした色を実機で見ていなかった**。全ての数値制約を満たした値が、実機では「オレンジではなく茶色」に見えたり、AA を満たすはずの文字色が色相を共有しないため浮いて見えたりした。

    → **規則を追加**する：**「色の選定は数値で候補を絞り込んだあと、必ず実機で見てから確定する」**。ΔE も「区別できるか」の指標であって「何色に見えるか」の指標ではない。「色相の温度感」「文字と面の一体感」は数値化しにくく、実機の目視で初めて判定できる。第一の失敗が**測る指標を取り違えた**ものだったのに対し、これは**測れない性質があることを見落とした**失敗である。

    **第三の失敗 — 制約が一方向にしか働かないことを踏まえていなかった**。数値で絞り込んだ初期値が実機で「暗い／地味」側に寄っていた。原因は、AA 4.5:1 を満たすには前景と背景の輝度差を大きくする必要があり、**鮮色側は常に輝度を下げる方向に押される**ためである。制約の下限ぎりぎりを選ぶと、必ず暗い側の端に着地する。

    → **規則を追加**する：**「暖色・鮮色の初期値を決めるときは、制約の下限ぎりぎりの候補だけでなく、実機で一段明るい候補も併せて用意する」**。

    **第四の学び — ペア運用のトークンは可動域が連動する**。面色を明色化するとペアの文字色に可動域の余裕が生まれる。**1 つのトークンを動かすと、それとペアで使うトークンの可動域も変わる**。

    → **規則を追加**する：**「面と文字のようにペアで運用するトークンは、片方を変えたらもう片方の再検討も同時に行う」**。

    **第五の失敗 — 同じ制約が後日もう一度効いた**。日付帯の曜日を土曜は青・日曜は赤にする案が出たが、橙帯の面の上では成立しなかった。**色相を共有する色同士は、面の上で明度を使って区別するしかなく、可読性を満たす明度まで落とすと元の文字色に収束する**。解決は色ではなく表記（括弧を付ける）で行った。

    → **規則を補足**する：**「情報の区別を色で行う案が出たら、その色が載る面の色との色相関係を先に確認する」**。同系色相の面の上では、色による区別は原理的に成立しない。

    **第六の学び — 明るさと可読性のトレードオフを段階的に探る**。ボタンの色を暗いオレンジから明るいオレンジへ振る過程で、白文字コントラストが 5.18 → 2.80 → 3.51 → 3.21 と揺れた。**「AA を満たす暗い側」「AA を満たさないが明るい側」の両端を実機で見比べる**ことで最終値を決めた。判断の根拠は「太字・短文であれば AA 大文字基準 3.0:1 で実用上は読める」という設計上の割り切り。この判断は §2 のパレット表と §2-1 の orange-bright 規則に恒常化して記録した。

    → **規則を補足**する：**「基準未達を承知で選ぶ色は、その理由（要素の性質・文字量など）を設計書に併記する」**。「基準を下回った」だけの記述は次に読む人が判断を再構築できない。

17. **判断の波及を追い切れず、同じ取りこぼしを 3 回繰り返した**。いずれも「1 箇所を直したとき、同じ判断が及ぶ範囲を洗い出さなかった」失敗である。

    **一度目 — 「見た目を変えない」移行が、設計判断を無効化したまま固定した**。`client.scss` を `app.scss` から分離したとき（f891de7）、段階1の方針を「app.scss と同一の内容を持たせ、見た目を変えない」とした。分離作業そのものとしては正しい判断だが、その結果**トレーナー側の値がすべてクライアント側の既定値になった**。入力欄の上下 padding 0.25rem は管理画面の情報密度を優先した値であり、飼い主がスマートフォンで入力するポータルには適さない（理論高さ 38px で、Apple HIG の 44pt にも Material の 48dp にも届かない）。設計書 §4-3 は「`app.scss` の指定は `client.scss` には持ち込まない」と明記していたが、実装は段階1のコピーを保持したまま以降の段階に進み、食い違いが残った。SCSS のコメントも「app.scss 由来の保持ルール」と**出自**を書くだけで、なぜその値なのかという**理由**を書いていなかったため、後から読んでも判断の妥当性を検証できない状態になっていた。

    → **規則を追加**する：**「見た目を変えない移行をしたときは、移行元の値のうちどれが移行先でも妥当かを、移行完了後に必ず点検する」**。また、**値を保持する判断をコメントに書くときは、出自ではなく理由を書く**（「app.scss 由来」ではなく「情報密度を優先するため」）。理由が書けない値は、そもそも検証されていない値である。

    **二度目 — セレクタ名で洗い出し、対象の性質で洗い出さなかった**。`.form-control` を 0.5rem に直した時点では `.btn` が Bootstrap 既定の 0.375rem（42px）のまま残り、同一フォーム内で入力欄 46px・ボタン 42px という不揃いが生じた。`.input-group .btn` だけは以前の高さ揃え修正（7f5baa1）の副産物として 0.5rem になっていたため、**同じ画面の中でボタンの高さが 2 種類ある**状態だった。ボタンは入力欄よりも明確なタップ対象であり、44px 基準はそちらにこそ効く。

    → **規則を追加**する：**「タップ領域に関わる修正をするときは、セレクタ単位ではなく『指で押す対象』単位で洗い出す」**。

    **三度目 — フレームワークが用意した仕組みを確認せずに上書きした**。`.btn` に `padding-top` / `padding-bottom` をロングハンドで上書きしたところ、Bootstrap の `.btn` がショートハンド `padding` を使っているため同詳細度・後勝ちとなり、**`.btn-sm` の変数上書きが無効化された**。正しくは Bootstrap 変数 `$input-btn-padding-y` を import より前で上書きする。この変数は `.form-control` と `.btn` の両方を駆動し、`-sm` / `-lg` は別系統のため影響を受けない。結果としてロングハンド 3 規則が変数 1 行に置き換わった。

    → **規則を追加**する：**「Bootstrap のコンポーネントの寸法を変えるときは、セレクタを上書きする前に、同じことをする変数が用意されていないか必ず確認する」**。変数があるのにセレクタで上書きすると、フレームワークが用意した派生（`-sm` / `-lg` / 状態変化）が壊れる。

18. **トークンの値を変えるたびに、変わった値だけを手で更新し、依存する他のペアを再計算しなかった**。パレットを複数回変更する過程で、設計書に古い値・誤った値が広範に残った。§2-1「鮮色同士の隣接禁止」表や §2 トークン表の複数箇所が旧値のままになっていた。

    幸い**判定（3:1 未達 / AA 未達）と結論はいずれも変わらず**、規約・設計判断への影響はなかった。しかし数値を根拠として設計判断を書いている以上、根拠の側が間違っていれば判断の再検証ができない。

    原因は §7-15（種別タグ廃止時の点検漏れ）と同じ構造である。ただし §7-15 が「文章の波及」を追わなかったのに対し、今回は**「計算結果の波及」を追わなかった**。1 つのトークンの値を変えると、そのトークンが関わる全ペアのコントラスト比と ΔE が変わる。人手で一部だけ更新すると、残りは静かに古いまま残る。しかも数値は文章と違って読んでも矛盾に気づきにくい。

    → **規則を追加**する：**「トークンの値を 1 つでも変えたら、そのトークンが関わる全ペアを機械的に再計算し、表ごと差し替える。個別の数値を手で書き換えない」**。

    **構造上の課題（未対応）**: 同じ数値が §2・§2-1・§3・§4-4・§5-7・§7 の複数箇所に重複して書かれていること自体が、この失敗を起きやすくしている。本来は §2 を数値の単一情報源とし、他節は参照にとどめるべきである。今回は改稿範囲を広げすぎないため見送り、課題として記録する。

### 候補外だった選択肢（新方向で）

- Primary red-yellow-blue のカラフル配色 — 子供向けアプリになる

#### 8-1-1. DashboardController の変更内容

**既存クエリはそのまま使える。変更するのは取得後にビューへ渡すデータ構造だけ**。

現状の `index()` は以下のクエリで既にセッションカード・フィードに必要な情報を全て取得している：

```php
auth('client')->user()
    ->trainingRecords()
    ->with(['trainer1', 'trainer2', 'mediaRecords'])
    ->withCount('mediaRecords')
    ->orderByDesc('training_date')
    ->get();
```

- **eager load のセット**（trainer1, trainer2, mediaRecords）は既に存在する。N+1 は発生していない
- **`training_date` 降順ソート**も既に存在する
- **`withCount('mediaRecords')` は現状のまま残す**。`mediaRecords` が eager load 済みのため `$record->mediaRecords->count()` でも件数は取れるが、今回の目的はデザイン改良でありコントローラの整理ではない。差分を増やさない
- **クエリの起点は `TrainingRecord::` の静的呼び出しではなく `Client` の HasMany 経由**（`Client.php:142-145` に `trainingRecords(): HasMany` が定義されている）

##### 変更 1: `$mediaItems` を「平坦化」から「記録ごとの入れ子」へ組み替える

現状の `$mediaItems` は「記録×メディア」の**平坦配列**として組み立てられており、記録との紐付けが失われている。カード内スクロール廃止・記録単位表示のために、これを**記録ごとに入れ子の構造**に組み替える。

**「廃止する」のではなく、構造を変える**。理由：現状の `$mediaItems` 構築ループの過程で、各メディアについて以下の値がコントローラ側で生成されている。これらは Blade からモデルを辿るだけでは取得できないか、または Blade で呼ぶべきでない：

- `thumbnailUrl`: `$m->temporaryThumbnailUrl($thumbnailExpiresAt)` — **署名付き URL**。有効期限を渡して都度生成する必要があり、Blade ではなくコントローラで一括生成する
- `conversionStatus`: 「準備中です」表示（§6 文言書き換え表）の判定に必要
- `displayTitle`: `title` が空のとき `original_filename` にフォールバックするアクセサ値
- `type`: `photo` / `video` の分岐

これらは**引き続きコントローラで生成する**。有効期限の算出（現状の `$thumbnailExpiresAt`）もそのまま維持する。

概念的な返却構造（変数名・型は実装時に調整可）：

```
$sessions = [
  [
    'record' => $rec,          // TrainingRecord モデル（そのまま渡す）
    'media'  => [               // その記録のメディア配列（平坦化はしない）
      ['id' => ..., 'type' => ..., 'thumbnailUrl' => ...,
       'conversionStatus' => ..., 'displayTitle' => ...],
      ...
    ],
  ],
  ...
];
```

hero と feed への分割は、この `$sessions` を Blade 側で `first()` / `skip(1)` するか、コントローラで `$hero` / `$feed` として先に分けてから渡すか、いずれでもよい。実装時に判断する。

##### 変更 2: ノート表示に使うフィールドは `record_content` に確定する

`TrainingRecord` には `record_content` と `impression` の 2 つのテキストフィールドがある（`$fillable` で確認）。**セッションカードのノート冒頭（§4-2）と詳細画面のノート本体（§4-4）に使うのは `record_content` のみ**。

根拠：

1. **クライアント側 `client/training-records/show.blade.php` は現在 `record_content` を表示している**（line 76-77 該当行引用）：
   ```blade
   @if($trainingRecord->record_content)
       <div>{!! nl2br(e($trainingRecord->record_content)) !!}</div>
   ```
2. **`impression` はクライアント側のいずれの画面にも表示されていない**（`resources/views/client/` 配下を grep 済、0 件）。トレーナー側の登録・編集フォーム（`training-records/_form.blade.php`）と、トレーナー側詳細（`training-records/show.blade.php` の `section-impression` 折りたたみ）でのみ表示される
3. **決定的な根拠**: `src/app/Http/Controllers/Client/TrainingRecordController.php:16` のクラスコメントに以下の宣言がある：
   > 所感（impression）・最終更新者などクライアント非開示情報は

つまり `impression` は**設計上クライアント非開示のフィールド**。トレーナーの内部所見であり、飼い主に見せる判断は本プランの範囲外。

**禁止事項（明文化）**：

- セッションカードのノート冒頭・詳細画面のノート本体は **`record_content` のみを使用**する。`impression` を代替として使わない
- **現状クライアント側に表示していないフィールド（`impression`, `updated_by` 等）を、今回の再構成で新たに露出させない**。表示可否の判断は本プランの範囲外であり、必要になれば別プランで扱う

##### メディアが多対多である事実（実装者向けの注意）

`TrainingRecord::mediaRecords()` は **`belongsToMany`** であり、中間テーブル `media_record_training_record` を介する（`withPivot('sort_order')` / `orderByPivot('sort_order')`）。逆方向 `MediaRecord::trainingRecords()` も `belongsToMany`。

DashboardController.php:33 の既存コメントにあるとおり、**同じメディアが複数のトレーニング記録に紐づく場合がある**。フィード形式では**同じ写真が複数のセッションカードに現れ得る**。

これは仕様通りの挙動であり、今回の設計変更で対処すべき問題ではない。ただし実装者が「重複表示のバグ」と誤解して重複排除を入れてしまわないよう、事実として明示しておく。

#### 8-1-2. vite.config.js 変更の副作用と確認手順

- `public/build/manifest.json` は Vite が全エントリを一括管理する**単一ファイル**であり、トレーナー側の `app.blade.php`（`@vite(['resources/sass/app.scss', 'resources/js/app.js'])`）とクライアント側の `client.blade.php` などが**同じ manifest を参照**する
- エントリを追加すると manifest が**再生成される**。Hash 付きファイル名も変わり得る
- `public/build/` は Git 管理対象のため、**ビルド成果物を同一コミットに含める**こと。ビルドし忘れの状態を push すると本番でアセットの 404 が発生する
- 実装後、以下を必ず確認：
  1. `npm run build` を実行
  2. `public/build/manifest.json` の差分に `client.scss` エントリが追加され、既存の `app.scss` / `app.js` エントリのハッシュも同時に更新されていることを目視

### 9-1. プロダクト名

- 現時点で未確定。「しっぽ帳」は仮案であり本文の暫定表記としてのみ使う
- **Blade にベタ書きしない**。`config('app.client_portal_name')`（またはそれに準ずる config キー）を経由して供給する前提
- `config('app.client_portal_name')` の用途は以下の 3 箇所：
  - **ワードマーク**: ログイン画面・初回設定画面・メールアドレス登録画面・無効トークン画面の `<h1 class="c-login-wordmark">`
  - **navbar-brand**: `layouts/client`（認証後ヘッダー）のブランド表示。ダッシュボードへのリンク（`<a>`）として実装する（§4-0）
  - **ブラウザタイトルのサフィックス**: `layouts/client`・`layouts/client-public` が `<title>` 末尾に付与する（画面設計書 §2-3「ブラウザタイトル」を参照）
- **ワードマーク（ログイン画面ヘッダー）は文字数で組みが変わる**ため、以下の想定範囲で成立させる：
  - 想定文字数: **3〜7 文字（日本語・漢字/ひらがな混在）**
  - システムサンス（ウェイト 700、色 brand-deep）で 2.75rem 前後を基準に、7 文字までは 1 行、5 文字以下ではさらに大きく組む
  - Latin 表記が入る可能性（例: 英字プロダクト名）は当面想定しないが、混在時の縮約規則はフォールバックとして CSS の `max-width` + `text-wrap: balance` で吸収する
- 確定するまでは config 側にプレースホルダ値（例: `"クライアントポータル"`）を入れておき、Blade からは常に読み込む
