## 4. システム概要

### 4-1. システムの全体像

本システムは、トレーニング機関における会員情報とトレーニング記録を一元管理するためのWebアプリケーションです。
ブラウザから利用でき、会員情報の管理、トレーニング記録の作成・参照、トレーナー間での情報共有を行えます。

また、本システムは会員（飼い主）向けの閲覧機能を備えています。
トレーナーが登録したトレーニング記録やメディア（写真・動画）を、会員自身がメールアドレスとパスワードでログインして閲覧できます。
この閲覧機能はトレーナー向けの管理機能とは独立しており、会員は自分に紐づく情報の閲覧のみが可能です（新規作成・編集・削除はできません）。

### 4-2. 利用環境

**推奨環境**
- **ブラウザ**：Google Chrome、Microsoft Edge（いずれも最新版）
  - 動作保証外：Firefox、Safari など
  - 非対応：Internet Explorer
- **ネットワーク**：インターネット接続必須
- **マイク**：録音機能を使用する場合はマイク（内蔵または外付け）が必要。ブラウザからマイクへのアクセス許可が必要

**※環境維持のためのお願い**
- OSとブラウザを常に最新版に保ってください。
- 安定したインターネット接続環境を維持してください。
- 各PCにウイルス対策ソフトを導入することを推奨します。

**動作イメージ**

```
サーバー
├─ MySQLデータベース
├─ Laravelアプリケーション
└─ HTTPS（SSL/TLS）

PC1 ───┐
PC2 ───┤
PC3 ───┼─ サーバーにアクセス
PC4 ───┘
```

### 4-3. 技術構成

本システムは以下の技術で構築されます。

| 要素 | 技術 | 説明 |
|---|---|---|
| データベース | MySQL 8.0 | 会員情報、トレーニング記録などを保存 |
| サーバー側 | Laravel 12.x（PHPフレームワーク） | データ処理、画面表示を制御 |
| 画面表示 | Blade + Bootstrap 5 | ブラウザで表示される画面 |
| 外部通信 | HTTPS（SSL/TLS） | インターネット経由での安全な通信 |
| 文字起こしAPI | OpenAI Whisper API | 音声ファイルの文字起こし |
| 要約API | Claude API | 文字起こしテキストの要約 |
| 処理実行 | Laravel のキュー（本番は database ＋ 常駐のワーカー） | 文字起こし・要約・トレーニング記録の自動作成・メディアの変換を後ろで実行（**2026-10 変更**。以前は同期実行） |

※技術的な詳細は開発事業者が管理し、利用者は通常のWebサイトと同様にブラウザで操作します。

### 4-4. 利用想定

**想定規模**
- 同時利用トレーナー数：最大10名
- 管理会員数：
  - 支援中：約100名
  - 累計（過去含む）：約1,000名
- トレーニング記録数：会員1名あたり平均200件程度（長期支援の場合は500件を超えることもある）

**同時編集の動作**
- 同一会員情報を複数のトレーナーが同時編集することは可能です
- 後から保存したデータが優先されます（先に保存した編集内容は上書きされる場合があります）

### 4-5. データの所有権

- データの所有権は、貴機関に帰属します。
- システム開発事業者は、貴機関からの依頼または同意のもとに限り、データにアクセスします。

## 5. 利用者と権限

### 5-1. 権限一覧

本システムでは、以下の権限レベルを設定します。

| 権限 | ①業務機能 | ②業務管理機能 | ③システム管理機能 | ④コマンド実行 | 備考 |
|---|:---:|:---:|:---:|:---:|---|
| 一般 | 〇 | × | × | × | 通常の業務操作のみ |
| 管理者 | 〇 | 〇 | × | × | 現場の管理者 |
| システム管理者 | × | △ | 〇 | × | 保守・緊急対応で使用。②はトレーナー管理のみ操作可。無効化・削除不可。ロック対象外（詳細は11-2-2参照） |
| システム | × | × | × | 〇 | サーバー上で実行されるコマンド処理。自動実行と、開発事業者がサーバーに直接接続（SSH）して手動実行する場合の両方を含む。Webログインによる権限ではない |

- **①業務機能**：会員管理やトレーニング記録の作成・閲覧などのトレーナーの日常業務。
- **②業務管理機能**：日常業務を運用するための管理業務。トレーナー管理、マスタ管理、レポートなど。
- **③システム管理機能**：システムを円滑に運用するためのシステム管理業務。IPアドレス制限の設定、サーバーの容量管理など
- **④コマンド実行**：サーバー上でのコマンド実行（バッチ処理など）。

#### 会員（閲覧利用者）

上記の権限は、システムを操作するトレーナーの区分である。これとは別に、会員（飼い主）は自分に紐づく情報を閲覧するための利用者として扱う。
会員はトレーナーの権限体系とは独立しており、メールアドレスとパスワードでログインし、自分に紐づくトレーニング記録・メディアの閲覧を中心に行える（例外として、トレーニーの写真の登録・削除〔6-15-15〕と、愛犬の基本情報〔名前・犬種・性別・誕生日・去勢・避妊〕の変更〔6-15-20。**2026-10-18 追加**〕だけは行える）。それ以外の新規作成・編集・削除、および他の会員の情報へのアクセスはできない。受付アンケート（6-15-17）はログインせずに答えるもので、会員の権限には含めない（認証不要として扱う）。
会員の閲覧機能は、トレーナーが対象会員に対してマイページ登録案内を発行し、会員自身がメールアドレスの登録と初回設定を完了することで利用可能となる（詳細は 6-3-6・6-15-4・6-15-5）。この閲覧機能はお客様向けには「マイページ」と呼ぶ（プロダクト名とは別の呼称。用語集参照）。

#### 情報共有の方針

担当トレーナー不在時の対応、チーム全体での支援のため、すべてのトレーナーがすべての会員情報・トレーニング記録（担当以外も含めて）を閲覧・編集可能。

### 5-2. 初期アカウント

システム導入時に、以下のアカウントを作成します。

- **管理者（admin）**：1名（**トレーナー本人のアカウント**として使い続ける。`login_id` と氏名は本人のものを設定する。初期構築用の一時アカウントではないため、後から削除しない）
- **システム管理者（system_admin）**：1名

**※管理者アカウントのパスワード運用**
管理者アカウントのパスワードはシーダーで**ランダム生成**されるため、誰も値を知らない状態でシステムが立ち上がる。運用開始時にはシステム管理者がトレーナー管理画面のパスワードリセット機能から新しいパスワードを設定し、管理者本人に伝える（リセット時に `must_change_password` が自動で `true` になるため、本人は初回ログイン時にパスワード変更を求められる）。

**※業務で使用するトレーナーの登録について**
運用開始後にトレーナーが増える場合は、管理者アカウントでログインしてトレーナー管理画面から追加する。

### 6-1. 認証

#### 6-1-1. ログイン
- **概要**：システムにログインする
- **入力**：
  - ログインID
  - パスワード
- **動作**：
  - ログイン成功後、ダッシュボード画面に遷移
  - 連続してログインに失敗するとアカウントがロックされる（詳細は11-2-2参照）
- **利用権限**：認証不要（未ログイン状態）

#### 6-1-2. 強制パスワード変更
- **概要**：初回ログイン時、または管理者によるパスワードリセット直後のトレーナーに対し、パスワード変更を強制する
- **入力**：
  - 新しいパスワード（必須。詳細は11-2-1参照）
  - 新しいパスワード（確認）（必須、新しいパスワードと一致すること）
- **動作**：
  - パスワード変更が必要なトレーナーは、ログイン直後に強制パスワード変更画面へ自動遷移
  - パスワード変更完了後、ダッシュボード画面に遷移
- **利用権限**：一般、管理者、システム管理者

#### 6-1-3. ログアウト
- **概要**：システムからログアウトする
- **動作**：ログイン画面に戻る
- **利用権限**：一般、管理者、システム管理者

#### 6-1-4. セッション期限切れエラー表示
- **概要**：セッションが切れた状態でリクエストが発生した場合に、エラーページを表示する
- **条件**：
  - セッションタイムアウト後の操作
  - CSRFトークン不一致（フォーム送信時のセキュリティ検証失敗）
- **動作**：
  - エラーページを表示し、ユーザーに状況を伝える
- **利用権限**：認証状態を問わず

#### 6-1-5. アクセス禁止エラー表示
- **概要**：許可されていないリソースへのアクセス時に、エラーページを表示する
- **条件**：
  - 権限のないリソースへのアクセス（管理者専用機能への一般トレーナーからのアクセスなど）
  - IPアドレス制限対象からのアクセス
- **動作**：
  - エラーページを表示し、ユーザーに状況を伝える
- **利用権限**：認証状態を問わず


### 6-2. ダッシュボード

#### 6-2-1. ダッシュボード表示
- **概要**：ログイン後の起点となる
- **機能**：
  - **最近のトレーニング記録**（**2026-09 追加**）：**過去 1 週間**（今日を含む 7 日間、未来日は含めない）に実施されたトレーニング記録を、トレーニング日の新しい順で一覧表示する（ページングなし）。見出しの右に「すべて表示」（トレーニング記録一覧 S-0402 へ）、行の右端に絞り込みセレクト（「すべて」「主担当のみ」、既定は「すべて」）を置き、変更すると自動で再読み込みする。「主担当のみ」は**会員の主担当**（`clients.primary_trainer_id`）がログイン中のトレーナーである記録に絞る（担当1・担当2 で絞るのではない）。行クリックでトレーニング記録詳細（S-0403）へ遷移する
    - 表示項目：内部ID、名前、トレーニー、トレーニング日、担当1、担当2、メディア（**2026-09 変更**、トレーニング記録一覧 S-0402 と同じ列構成に揃えた。詳細は screen-design.md S-0201 設計方針「列の構成も S-0402 と揃える」参照）。トレーニー列の名前が未登録のときは 6-16「名前が未登録のときの表示」に従う
    - 0 件時は「過去1週間のトレーニング記録はありません。」を表示
    - 詳細と設計方針は screen-design.md S-0201 参照
  - **削除した機能**（**2026-09**）：従来の「主担当の会員一覧」ブロック（ログイン中のトレーナーが主担当の会員を最終トレーニング日の新しい順に最大 10 件表示）は撤去した。「最近のトレーニング記録」に「主担当のみ」の絞り込みがあり、主担当の会員の動きはそちらで追えるようになったため（詳細は screen-design.md S-0201 設計方針「『主担当の会員一覧』ブロックを削除」参照）
- **利用権限**：一般、管理者


### 6-3. 会員管理

#### 6-3-1. 会員登録
- **概要**：会員情報を登録する
- **入力**：
  - 「9. データ項目一覧」参照
  - 必須項目：初回日、姓  - その他の項目は任意
- **利用権限**：一般、管理者

#### 6-3-2. 会員一覧
- **概要**：会員を一覧表示し、条件を指定して絞り込みや並び替えができる
- **検索条件**：内部ID、名前（姓名・かな）、最終トレーニング日、主担当トレーナー
- **並び替え**：内部ID、名前、初回日（初期は初回日の新しい順。同じ初回日は登録の新しい順）
- **表示内容**：
  - 列構成（**2026-09 変更**）：**内部ID / 名前 / トレーニー / 初回日 / 主担当 / メールアドレス / 最終トレーニング日 / ご利用回数** の 8 列。会員を特定する情報を左、担当・状態・最近の動きを右に置く並び。詳細は screen-design.md S-0304 設計方針「列の並べ替えと『初回日』の追加」参照（ご利用回数列は 6-17-7 で追加）
  - 会員一覧の各行に**状態**（メールアドレスなし／メールアドレス登録待ち／初回設定待ち／利用中）を表示する。状態は「マイページ」列に**バッジ**で表示し（**2026-10 変更**：列見出しを「メールアドレス」から「マイページ」にした）、絞り込み・並び替えの対象にはしない（今回は列の表示のみ）
  - **トレーニー列**（**2026-09 追加**）：会員に紐づくトレーニーを「名前（犬種、性別）」の形で表示（複数頭は「／」区切り、犬種・性別が未登録なら括弧を省略、0 頭は空欄。名前が未登録のときは 6-16「名前が未登録のときの表示」に従う）。会員一覧でどの犬の飼い主か分かるようにするため。詳細は screen-design.md S-0304 参照。従来あった**かな列は同時に廃止**（かなでの探索は名前検索欄が対応するため一覧列としては不要と判断。screen-design.md S-0304 設計方針参照）
  - **初回日列**（**2026-09 追加**）：会員の初回来所日（`clients.initial_consultation_date`）を `Y/m/d` 形式で表示。一覧で「いつからの会員か」を分かるようにするため
  - **ご利用回数列**：会員ごとの残り回数を「あと n回」の形で表示する。並び替え・検索条件の対象にはしない。詳細は 6-17-7 参照
- **利用権限**：一般、管理者

#### 6-3-3. 会員詳細
- **概要**：会員情報とトレーニング記録履歴、トレーニー（会員に紐づくトレーニング対象。用語集 No.23）の一覧を表示する
- **表示内容**：
  - 「9. データ項目一覧」参照
  - トレーニング記録一覧（日付の新しい順）
  - **トレーニー一覧**（登録順・`id` 昇順）。各トレーニーに**写真**（小さく。写真がないときは同じ大きさの枠に「写真なし」と出す。どちらも押すとトレーニー詳細を開く）を添える。件数と「トレーニーを追加」への遷移導線（カード下部・右寄せ）を含む。詳細は 6-16 トレーニー管理を参照
    - 各トレーニーカードには、**年齢**（6-16「年齢の表示規則」）、**去勢・避妊**、**受付アンケートの操作**（6-16-8 の状態表。状態は出ているボタンで分かるため、状態の文字・日付は出さない）、**愛犬性格診断の行**（いつも出す「愛犬性格診断」のリンクと、行の右の愛犬性格診断の案内の操作。6-16-11 の状態表。**2026-10 追加**）を出す。名前が未登録なら 6-16「名前が未登録のときの表示」に従う
  - 会員の**状態**（メールアドレスなし／メールアドレス登録待ち／初回設定待ち／利用中）をヘッダー部にバッジで表示する。有効期限が切れている場合は「（期限切れ）」を添える
  - **ご利用回数**（「回数」カードの見出し。残り回数を「あと n回」の形で出す）と、**契約・利用の一覧**（回数券型の表示）。契約・利用の登録・編集・削除もこの画面から行う。詳細は 6-17 回数管理を参照
- **利用権限**：一般、管理者

#### 6-3-4. 会員編集
- **概要**：会員情報を編集する
- **入力**：
  - 「9. データ項目一覧」参照
  - 必須項目：初回日、姓  - その他の項目は任意
- **利用権限**：一般、管理者

#### 6-3-5. 会員削除
- **概要**：会員情報を、確認の上で削除する
- **条件**：いずれかに該当する会員は削除できない。確認ダイアログの手前で「この会員には○○が登録されているため削除できません。」を提示し、削除処理には進まない（判定は画面とサーバの両方で行う）
  - トレーニング記録が登録されている（DB 側の外部キーは CASCADE、アプリ側で拒否する二層構え）
  - **トレーニーが登録されている**（DB 側の外部キーは CASCADE、アプリ側で拒否する二層構え。トレーニー削除後に会員削除する二段構えの運用を促す。詳細は 6-16 トレーニー管理を参照）
  - **音声記録が登録されている**（**2026-10 追加**。DB 側の外部キーは RESTRICT。音声記録には文字起こし・要約〔記録の元になる内容〕が残っているため、会員と一緒に消すより止めるほうが安全。本番で音声記録のある会員の削除が外部キーに断られてサーバーエラー（500）になった事例の恒久対策）
- **契約・利用は削除を拒否する条件にしない**：契約（D-0900）・利用（D-1000）が登録されていても会員は削除でき、DB の外部キー（CASCADE）で一緒に削除される。トレーニーの「登録されていれば拒否」とは扱いが違う（詳細は 6-17 回数管理を参照）
- **最後の守り**：画面の確かめをすり抜けて DB の外部キーに断られた場合（外部キー違反、SQLSTATE 23000・エラー番号 1451）も、サーバーエラー（500）にせず、会員詳細に戻して「この会員には関連するデータが登録されているため削除できません。」を提示する。ログには会員 ID と例外クラス名を残す
- **利用権限**：管理者

#### 6-3-6. マイページ登録案内の発行
- **概要**：トレーナーが会員に渡すためのマイページ登録案内（QR コード・URL・手順・有効期限を載せた紙面／画面）を発行する。会員はこの案内に載る URL からマイページに登録する。「マイページ」はお客様向けの呼称で、内部的にはトークン（「メールアドレス登録用 URL」、DB 上は `client_email_registration_tokens`）を作る
- **動作**：
  - 会員詳細画面の「マイページ登録の案内を発行」ボタンから発行する（**状態が「メールアドレスなし」または「メールアドレス登録待ち（期限切れ）」のときだけ**このボタンが出る。画面上の配置は 3 段目のメールアドレス列の状態バッジの右隣。screen-design.md S-0305「操作ボタンの配置」参照）
  - 押下するとその場で有効期限 3 日のワンタイム URL を発行し、**会員詳細に戻る**（**2026-10-17 変更**。理由は備考「発行のあとの戻り先」）（**この期限が初回設定完了までの全体の期限になる**。ログイン用リンクは対応するメールアドレス登録用 URL の期限を引き継ぐため、独立した期限は持たない）
  - 会員詳細の上に完了メッセージ「**マイページ登録の案内を発行しました。**」を出す（ほかの完了メッセージと同じ出し方）。ボタンは「マイページ登録の案内を表示」「取消」に入れ替わっている。案内は［マイページ登録の案内を表示］から S-0307 を開いて見る
  - **有効な案内がすでにある**とき（二重送信・古い画面から押し直したなど）は、新しく発行せず、完了メッセージも出さずに会員詳細に戻る（会員詳細は新しい状態で開くので、ボタンは［…を表示］［取消］になっている）
  - 発行済みの案内は、**S-0307 メールアドレス登録用 URL 印刷画面**で確認する。QR コード・URL 文字列・有効期限・手順は当画面に集約する（画面名は設計書上の呼称として維持）
  - 案内を**紙で渡すだけでなく、メール／LINE でも送れる**ようにする。S-0307 画面の「**文面をコピー**」ボタンでメール／LINE 用に整えた案内文面をクリップボードにコピーし、トレーナーが自分のメールソフト・LINE トークに貼り付けて送る（本システムはメール送信や LINE 連携を持たず、コピー機能だけを提供する。文面と決め事は screen-design.md S-0307「案内文面のコピー」参照）
  - 状態が「メールアドレス登録待ち（期限内）」のときは、詳細画面の操作ボタンとして「**マイページ登録の案内を表示**」（と「取消」）が出る（発行し直しのボタンは出ない）。押下で S-0307 を**同じタブで開く**。**このボタン名にした理由**：押す目的が「お客様に渡すものを出す」ことであり、開いた先の見出し「マイページ登録のご案内」と一致させるため（QR コードだけを見せて渡すこともあるので、「印刷」という言葉は実態から外れる）。**ボタン名**（**2026-10 変更**）：マイページ登録案内のボタンも「マイページ登録の案内を…」として、何の案内かをボタンの文字だけで分かるようにする（受付アンケートの案内のボタンと見分けるため）。取消は隣の［マイページ登録の案内を表示］と確認（S-0305-M03）の文言で対象が分かるので「取消」にする（screen-design.md S-0305「操作ボタンの配置」参照）
- **条件**：
  - 会員のメールアドレスの登録有無を問わず、状態が「メールアドレスなし」または「メールアドレス登録待ち（期限切れ）」のときに発行できる
- **備考**：
  - 発行された URL は初回設定が完了するまで有効。会員は同じ URL から何度でもメールアドレスを入力し直せる。会員の入力し直しでは、送信済みのログイン用リンクが差し替わるだけで、**メールアドレス登録用 URL 自体は無効にならない**
  - **期限内に発行し直す機能は用意しない**：URL がまだ使えるので、もう一度渡せば足りるため。「発行し直す」の操作は詳細画面のボタン群には出さない。渡し直したいときは「マイページ登録の案内を表示」から URL や QR コードを再度確認する
  - **期限切れの URL はトレーナー側の詳細画面に表示しない**：期限切れの URL はもう使えず、トレーナーが確認する意味がないため、**未発行と同じ扱い**にする。状態が「メールアドレス登録待ち（期限切れ）」の場合、詳細画面のボタン群には「マイページ登録の案内を発行」だけが出て、押下でその場で新規の URL を発行する
  - **マイページ登録案内（＝メールアドレス登録用 URL のトークン）を無効にできるのはトレーナーだけ**（このセクションの発行操作、6-3-7 マイページ登録案内の取消、または 6-3-8 メールアドレスの削除）
  - QR コードは面談中にネット接続が不安定でも表示できるよう、ビルドに含める JS ライブラリで生成する（外部 CDN からの読み込みはしない）
  - 印刷用の案内シートに**お客様の氏名は載せない**（紛失時に氏名と URL が同時に漏れることを避けるため）
  - **「マイページ登録案内」と「メールアドレス登録用 URL」の使い分け**：お客様やトレーナーがふだん扱う対象（QR や紙面）を指すときは「マイページ登録案内」、DB のトークン・設計書内の識別としては「メールアドレス登録用 URL」を使う。両者は同じ実体を指し、呼称の使い分けだけの違い
  - **発行のあとの戻り先**（**2026-10-17 変更**。マイページ登録案内・受付アンケート案内・愛犬性格診断の案内で共通）：発行のあとは**会員詳細に戻り**、上に完了メッセージを出す。案内の画面（S-0307・S-0311・S-0312）は自動では開かず、必要なときに［…の案内を表示］から開く
    - 理由：2026-10-17 のユーザーレビューで、発行のあとに自動で案内の画面を開く機能は要らないとわかった。案内は、メール・LINE で文面を送るか、QR コードを読み取ってもらうときに［…の案内を表示］から開けば足りる
    - 戻る位置はページの上（トレーニーの欄の位置には移さない）。完了メッセージはページの上に出るため、トレーニーの欄まで移るとメッセージが見えなくなる
    - 案内の画面の操作エリアには［戻る］を置く。押すと、その会員の会員詳細に移る（ふつうのリンク。screen-design.md S-0307 備考「操作エリアのまとめ方」）
    - 発行の URL が GET で開かれたとき（古いタブ・読み込み直し・履歴など）は、エラー画面（405）を出さず、発行もせずに会員詳細に移す（api-design.md「発行の URL を GET で開いたとき」）
    - **経緯**：2026-10 に、発行のあとに案内の画面を開く作りにした（発行のあとの次の作業は案内を見せる・文面を送ることなので、［…の案内を表示］を押し直す手間をなくすため）。最初は別のタブで開く作りにしていた（発行のフォームに `target="_blank"` を付けてクリックそのもので新しいタブに送り、元のタブはトレーナーが戻ってきたとき〔`visibilitychange`〕に開き直す。案内の画面には、タブを閉じて元のタブに戻る［閉じる］を置く）。その前に試した 2 つの形の問題（同じタブで開いて戻ると古い会員詳細が出て「発行できていない」と誤解された／会員詳細に戻したあとに `window.open` で開くとポップアップブロックにかかった）を避けるためだった。**別のタブをやめた理由**（2026-10-17）：本番で、Android のタブレットの Chrome で発行のボタンを押すと、新しいタブが送信の中身を持たずに発行の URL を GET で開き、405 のエラー画面になって案内も発行されなかった。また、案内は印刷して渡すのではなく、メール・LINE で文面を送るか、画面の QR コードを読み取ってもらうのが主な使い方とわかり、別のタブで開く意味が薄かった。同じ 2026-10-17 に同じタブで開く作りに直したあと、上のユーザーレビューで、発行のあとは会員詳細に戻す形にした。ブラウザの［戻る］で古い会員詳細が出て、古い見た目のまま発行を押しても、有効な案内がすでにあれば新しく発行しないので、二重には発行されない
- **利用権限**：一般、管理者

#### 6-3-7. マイページ登録案内の取消
- **概要**：トレーナーが発行済みのマイページ登録案内を取り消す。**間違った会員に発行した**、あるいは**発行を取りやめたい**ときに、発行前の状態に戻す
- **動作**：
  - 会員詳細画面の「取消」ボタン（マイページ登録の案内の取消）から実行する（状態が「メールアドレス登録待ち（期限内）」のときだけ表示される。画面上の配置は 3 段目のメールアドレス列の状態バッジの右隣。screen-design.md S-0305「操作ボタンの配置」参照）
  - 押すと確認モーダルを開き、「**発行済みのマイページ登録案内が使えなくなります。すでにお渡しした案内からは登録できなくなります。**」を提示する。承諾したときのみ実行する
  - 対象会員の**未使用のメールアドレス登録用トークンを物理削除する**（送信済みのマイページ登録案内はその時点で無効になる）
  - **会員情報とトレーニング記録には触らない**
  - 完了後は詳細画面に戻り、「マイページ登録案内を取り消しました。」の完了メッセージを表示する（完了メッセージ本体の文言は変更なし）。状態は「メールアドレスなし」に戻り、詳細画面のバッジ隣のボタンは「マイページ登録の案内を発行」に入れ替わる
- **条件**：
  - 状態が**「メールアドレス登録待ち（期限内）」のときだけ**行える
  - **期限切れのときは取り消せない**：期限切れの案内はもう使えず、取り消す意味がない（詳細画面のバッジ隣のボタンは「マイページ登録の案内を発行」だけが出て、押下でその場で新規発行する — 6-3-6 と同じ扱い）
- **備考**：
  - 発行と取消は同じ画面（S-0305）から扱う。**取消ボタンがあること自体が「発行済みである」ことの手がかり**になり、発行後の変化に気づきやすくなる
  - 状態「メールアドレス登録待ち（期限内）」では、詳細画面の操作ボタンとして「マイページ登録の案内を表示」と「取消」が**並んで表示される**（3 段目のメールアドレス列の状態バッジ右隣。詳細は screen-design.md S-0305「操作ボタンの配置」）。両者は性質が異なる操作（渡す／やめる）で、どちらも必要
  - この状態では**お客様がまだメールアドレスを登録していない**ため、対応する `client_login_link_tokens`（ログイン用リンク）は通常存在しない。仮に未使用のログイン用リンクが残っていた場合は、整合性を保つため一緒に物理削除する（発行時 6-3-6・削除時 6-3-8 と同じ扱い）
- **利用権限**：一般、管理者

#### 6-3-8. メールアドレスの削除
- **概要**：
  - **利用中のお客様**が「利用をやめたい」と連絡してきたときに、閲覧機能を止める
  - **初回設定待ちのお客様**（お客様がメールアドレスを登録したがパスワードをまだ設定していない状態）で、**間違ったメールアドレスが登録された場合に登録をやり直せる**ようにする
- **動作**：
  - 会員詳細画面の右上のボタンの並び（「会員一覧に戻る」の右）の「マイページ登録を削除」ボタンを押す（**2026-10 変更**）。マイページ登録の削除は、案内の発行・取消とは違い、会員のアカウントに対する操作なので、会員の編集・削除と同じ右上の並びに置く。名前は「マイページ登録を削除」として、会員の［削除］と区別する（screen-design.md S-0305「操作ボタンの配置」参照。**機能名としての「メールアドレスの削除」は見出しどおり維持**する）
  - 確認画面で「登録されたメールアドレスが削除され、マイページを使えなくなります。会員情報とトレーニング記録は残ります」と表示し、承諾したときのみ実行する
  - メールアドレスを消す（利用中の場合はパスワードも一緒に消す）
  - 送信済みのメールアドレス登録用 URL・ログイン用リンクを無効にする
- **条件**：
  - 状態が「利用中」または「初回設定待ち」（**メールアドレスが登録済み**）のときに行える
  - 初回設定待ちは**期限内・期限切れの両方**を含む
- **備考**：
  - 会員情報とトレーニング記録は残る。以降、必要になれば 6-3-6 マイページ登録案内の発行から再度案内できる
  - **初回設定待ちにも広げた理由**：この状態はトレーナーに操作の手段がなく、お客様が間違ったメールアドレスを登録した場合に**行き止まり**になっていた。削除できれば「メールアドレスなし」に戻り、発行し直せる（詳細は screen-design.md S-0305「操作ボタンの配置」）
  - **期限内・期限切れの両方で出す理由**：期限切れの方がむしろ削除したい場面が多い
  - **確認画面の文言を状態で分岐させない理由**：初回設定待ちのお客様はまだログインしたことがないため旧文言「このお客様はログインできなくなります」は当てはまらない。分岐を増やすと保守対象が増えるので、両方の状態に当てはまる一つの文言にする
- **利用権限**：一般、管理者

### 6-4. トレーニング記録管理

#### 6-4-1. トレーニング記録登録
- **概要**：トレーニング記録を登録する
- **入力**：
  - 「9. データ項目一覧」参照
  - 必須項目：トレーニング日、会員、担当1
  - その他の項目は任意
- **動作**：
  - 登録済みのメディアを、トレーニング記録に紐づける（追加・解除）。同一のメディアを複数のトレーニング記録に紐づけできる。紐づけを解除してもメディア自体は削除されない
  - 過去の音声要約をトレーニング記録欄に読み込める（読み込み後は手動編集可能）
- **利用権限**：一般、管理者

#### 6-4-2. 録音からのトレーニング記録登録
- **概要**：トレーニングの録音から、文字起こし・要約を経てトレーニング記録を登録する
- **入力**：
  - 会員（必須、6-5-1 の録音時に選択）
- **動作**：
  - 録音完了後、追加項目（担当2）をトレーナーが入力する
  - 入力完了後、文字起こし（6-6-1）→ 要約（6-6-2）→ トレーニング記録登録（6-4-1）が順に自動実行される
  - 文字起こしまたは要約でエラーが発生した場合、後続処理は中止される
- **自動設定項目**：
  - トレーニング日：当日の日付
  - 時刻：録音開始時刻
  - 会員：録音時に選択した会員
  - 担当1：録音したトレーナー
  - トレーニング記録欄：生成された要約テキスト
- **情報漏洩防止**：
  - 録音実行中は会員名を表示しない（画面録画等による情報漏洩防止）
- **利用権限**：一般、管理者

#### 6-4-3. トレーニング記録一覧
- **概要**：トレーニング記録を一覧表示し、条件を指定して絞り込みや並び替えができる
- **検索条件**：内部ID、名前（姓名・かな）、トレーニング日、担当トレーナー、キーワード（トレーニング記録・所感内の全文検索）
- **並び替え**：内部ID、名前、トレーニング日（初期は新しい順）
- **表示内容**：
  - **トレーニー列**（**2026-09 追加**）：会員に紐づくトレーニーを「名前（犬種、性別）」の形で表示（複数頭は「／」区切り、犬種・性別が未登録なら括弧を省略、0 頭は空欄。名前が未登録のときは 6-16「名前が未登録のときの表示」に従う）。一覧でどの犬に対する記録か分かるようにするため。会員一覧（6-3-2）と同じ表示形式に揃える。詳細は screen-design.md S-0402 参照
- **利用権限**：一般、管理者

#### 6-4-4. トレーニング記録詳細
- **概要**：トレーニング記録の情報を表示する
- **表示内容**：「9. データ項目一覧」参照
- **動作**：トレーニング記録に紐づいたメディアを一覧表示し、閲覧（写真は拡大表示、動画は再生）できる
- **利用権限**：一般、管理者

#### 6-4-5. トレーニング記録編集
- **概要**：トレーニング記録を編集する
- **入力**：
  - 「9. データ項目一覧」参照
  - 必須項目：トレーニング日、会員、担当1
  - その他の項目は任意
- **動作**：
  - 登録済みのメディアを、トレーニング記録に紐づける（追加・解除）。同一のメディアを複数のトレーニング記録に紐づけできる。紐づけを解除してもメディア自体は削除されない
  - 過去の音声要約をトレーニング記録欄に読み込める（読み込み後は手動編集可能）
- **利用権限**：一般、管理者

#### 6-4-6. トレーニング記録削除

- **利用権限**：管理者

### 6-5. 音声記録管理

#### 6-5-1. 音声記録登録（録音）
- **概要**：トレーニングを録音して、音声記録を登録する
- **入力**：
  - 会員（必須）
- **自動設定項目**：
  - 表示名：録音停止時の日時（YYYYMMDD_HHMM_トレーナーのログインID 形式）
  - 登録者：ログイン中のトレーナー
  - 状態：「文字起こし待ち」
- **音質と録音時間**：
  - ビットレートは 64 kbps を指定する。話し声の聞き取りと文字起こしに十分な音質を維持しつつ、ファイルの大きさを抑える（60 分の録音でおおよそ 30〜45MB。ブラウザにより異なる）。
  - 録音時間の上限は設けない。ファイルサイズの上限は 100MB（6-5-2 のアップロードと共通）で、64 kbps の録音では数時間分に相当する。
- **長時間の録音で文字起こしに失敗した場合の運用**：
  - 音声記録一覧（S-0505）から録音を再生し、ブラウザの機能で録音ファイルをダウンロードして、本システムの外のツールで文字起こしする。
  - 録音ファイルは登録から一定期間（既定 7 日。6-7-2 音声ファイル自動削除）で削除されるため、削除される前にダウンロードすること。
  - iOS / iPadOS Safari など、`<audio>` 要素からのダウンロードに対応していない環境では、PC のブラウザで一覧を開いてダウンロードする。
- **情報漏洩防止**：
  - 録音中はブラウザの戻るボタンと画面遷移を無効化
  - 録音完了後は自動ログアウト（会員が他の会員情報を閲覧することを防ぐため）
- **録音のあとのトレーニング記録の作成**（**2026-10 変更**）：
  - 録音のあと、トレーニング記録を作る場合は、担当1・担当2 を選んで「作成する」を押す。システムは「文字起こし → 要約 → トレーニング記録の作成」をひとつながりで受け付け、**後ろで進める**。画面は受け付けたら「作成を開始しました。」「再度ログインして、文字起こし・要約の結果を確認してください。」の 2 行を出して、待たずにログアウトする（以前は、3 つが終わるまで処理中の画面で数分待っていた）。
  - 途中で失敗したら、そこで止まり、次の段階には進まない（文字起こしが失敗したら、要約も記録の作成もしない）。音声記録の処理状況を「エラー」にし、音声記録一覧で分かるようにする。やり直しは、音声記録一覧の「文字起こし」「要約」と、トレーニング記録の登録の「音声記録の要約から入力」で、手で行う。
  - トレーニング記録を作らない（「いいえ」）ときは、音声だけを保存してログアウトする（文字起こしもしない）。
- **利用権限**：一般、管理者

#### 6-5-2. 音声記録登録（音声ファイルのアップロード）
- **概要**：音声ファイルをアップロードして、音声記録を登録する
- **入力**：
  - 会員（必須）
  - 音声ファイル（必須）
    - 対応形式：mp3、m4a、wav、mp4、webm
    - 最大サイズ：100MB
      - WAV（無圧縮）の場合、100MB では 16bit / 44.1kHz でモノラル約 19 分、ステレオ約 9 分までが上限に収まる。
- **自動設定項目**：
  - 表示名：アップロードしたファイル名（拡張子を除く）
  - 登録者：ログイン中のトレーナー
  - 状態：「文字起こし待ち」
- **利用権限**：一般、管理者

#### 6-5-3. 音声記録登録（文字起こしテキスト）
- **概要**：文字起こし済みのテキストを直接入力して、音声記録（音声ファイルなし）を登録する

  - 表示名（必須、デフォルト値：作成時の日時 YYYYMMDD_HHMM 形式、編集可能）

  - 状態：「要約待ち」
- **利用権限**：一般、管理者

#### 6-5-4. 音声記録一覧

### 6-6. 文字起こし・要約

#### 6-6-1. 文字起こし
- **概要**：音声ファイルを文字起こしする
- **条件**：音声ファイルが存在する
- **動作**：
  - 状態遷移：「文字起こし待ち」→「文字起こし中」→「要約待ち」（または「エラー」）
  - 後ろで実行する（**2026-10 変更**）：音声記録一覧で「文字起こし」を押すと、システムは受け付けて後ろで進める。画面は処理中の表示のまま、終わるのを待って結果を表示する（30 分を超えて終わらないときは「処理に時間がかかっています。しばらくしてから一覧を読み込み直してください。」）。
  - 大きい音声ファイル（24MB 超）は、外部 API に送る前にサーバー側で小さく変換する（モノラル・16kHz・Opus 24 kbps 固定の Ogg。60 分で約 11MB、約 2 時間 10 分までが上限に収まる）。変換したファイルは送信後に削除し、元の音声ファイルは変更・削除しない。
  - 変換後も上限を超える場合（約 2 時間 10 分を超える録音）は、外部 API に送らずエラー状態に遷移する。利用者には「録音が長すぎるため、文字起こしできません。音声記録一覧から録音をダウンロードして、外部のツールで文字起こししてください。」を表示する。
  - 自動リトライ：しない（1 回だけ試行し、失敗したらエラー状態に遷移する。**2026-10 変更**。以前は最大 3 回。外部の API を何度も呼ぶと費用がかかるため）
  - 再実行：文字起こし済み・要約完了後でも再実行可能。再実行時は、確認の上で既存のテキストを上書きする
  - 中断された処理のやり直し：「文字起こし中」（または「要約中」）のまま 30 分以上経過している記録は、処理が中断されたとみなしてやり直しを受け付ける（画面にボタンと「処理が中断された可能性があります。もう一度実行してください。」の案内を再表示する）。30 分に満たない処理中の記録には、二重実行を防ぐためやり直しの依頼を受け付けない（同じ記録の別の処理（文字起こし中の要約、要約中の文字起こし）も同様に断る）。30 分の根拠は、FFmpeg のタイムアウト（600 秒）と外部 API の応答上限（300 秒）を足した 900 秒 = 15 分に、後ろで実行するときに順番を待つ時間を加えたもの（**2026-10 変更**。以前は 15 分）。
  - 処理中の記録は表示名・テキストの編集を受け付けない（判定に使う `updated_at` を上書きしないため。処理完了後に編集可能）。
- **利用権限**：一般、管理者

#### 6-6-2. 要約
- **概要**：文字起こしテキストを要約する
- **条件**：文字起こしテキストが存在する（音声ファイルの有無は問わない）
- **動作**：
  - 状態遷移：「要約待ち」→「要約中」→「要約完了」（または「エラー」）
  - 後ろで実行する（**2026-10 変更**）：文字起こしと同じ（6-6-1 参照）
  - 自動リトライ：しない（1 回だけ試行し、失敗したらエラー状態に遷移する。**2026-10 変更**。以前は最大 3 回）
  - 再実行：要約完了後でも再実行可能。再実行時は、確認の上で既存のテキストを上書きする
  - 中断された処理のやり直し：文字起こしと同じ扱い（6-6-1 参照）。
- **利用権限**：一般、管理者

#### 6-6-3. 要約プロンプト設定

- **機能**：
  - プロンプトの編集
- **利用権限**：管理者

### 6-11. レポート

#### 6-11-1. トレーニング記録数推移

#### 6-15-10. メールアドレスの変更
- **概要**：ログイン中のお客様が、メールアドレス変更画面（S-1409）から自分のログイン用メールアドレスを変更する
- **入力**：
  - 現在のパスワード
  - 新しいメールアドレス
- **動作**：
  - 現在のパスワードと新しいメールアドレスを送信すると、**新しいアドレス宛にメールアドレス確認リンクを送る**（有効期限 3 日）
  - 発行時点で、それまでお客様が申し込んで送信済みだった**未使用の確認リンクは無効**になる（**同時に有効な確認リンクは常に 1 本だけ**）
  - お客様がリンクを開いた時点でメールアドレスを切り替え、続けて**ログアウトさせ、ログイン画面（S-1401）へ遷移する**。ログイン画面には「メールアドレスを変更しました。新しいメールアドレスでログインしてください」と表示する
  - 切り替えの直前に**重複を再確認する**（申し込みから確認までの間に他の会員が同じアドレスを登録している可能性があるため）
  - 切り替え直後に、**古いアドレスへ通知メールを送る**（本文は「メールアドレスを変更しました。／変更日時：Y年n月j日 H:i／心当たりがない場合は、担当のトレーナーにご連絡ください」の 3 パーツ構成。**変更日時を載せる**ことでお客様が身に覚えを確認できるようにする。件名「メールアドレスを変更しました」。件名・本文の形は client-portal-design-plan.md §6-1 / §6-2 参照）
  - 確認リンクが開かれるまでは、古いアドレスのままログインできる
- **条件**：
  - すでに他の会員で使われているメールアドレスには変更できない
  - 現在のパスワードが一致しない場合は変更できない
  - リンクが無効・期限切れ・使用済みの場合は、その旨を表示し切り替えない
- **備考**：
  - 「メールアドレス確認リンク」は**メールアドレスを切り替えるだけの役割**であり、ログイン用リンク（6-15-4／6-15-5 で扱うもの）とは性質が異なる（ログインさせる働きは持たない）
  - メールアドレス確認リンクは、他のトークン（メールアドレス登録用 URL・ログイン用リンク）とは**無関係に発行される**ため、独立した有効期限を持つ
  - **同時に有効な確認リンクを 1 本に制限する理由**：最後に申し込んだアドレスが正しいと考えられるため。複数のリンクが同時に有効だと、古いリンクを誤って開いたときに意図しないアドレスに切り替わる。これは 6-3-6 マイページ登録案内を発行し直したときに、それまでのログイン用リンクが無効になるのと同じ考え方
  - **確認リンクの本人性の考え方**：リンクを開く側では追加の確認（パスワードの再入力など）を求めない。理由は次の三重の防御が働くため：
    1. 確認リンクは**新しいメールアドレス**に届く。第三者がリンクを使うには新しいアドレスのメールを読める必要がある
    2. 申し込みの時点で**現在のパスワードの入力を求めている**。第三者が自分のアドレスを新しいアドレスとして申し込むにはパスワードを知っている必要がある。パスワードを知られている状態なら、確認リンクを使わずに直接ログインできてしまうため、この経路が新たな弱点を作るわけではない
    3. 切り替わった時点で**古いアドレスに通知メールを送る**。第三者に変更された場合、本人はここで気づける
  - 以上より、「新しいアドレスのメールを受信できることをもって本人性を確かめる」という考え方を採る
- **利用権限**：会員（申し込み時にログイン中）／認証不要（メールアドレス確認リンクを開くとき）

#### 6-15-11. パスワードの変更
- **概要**：ログイン中のお客様が、パスワード変更画面（S-1410）から自分のパスワードを変更する
- **入力**：
  - 現在のパスワード
  - 新しいパスワード
  - 新しいパスワード（確認）
- **動作**：
  - 変更内容を確定するとその場でパスワードを更新し、同じ画面に戻して完了メッセージを表示する
  - **変更してもログアウトさせない**（画面内で完結し、メールのリンクを経由しないため）
  - 変更後に、登録済みのメールアドレスへ**通知メールを送る**（本文は「パスワードを変更しました。／変更日時：Y年n月j日 H:i／心当たりがない場合は、担当のトレーナーにご連絡ください」の 3 パーツ構成。**変更日時を載せる**ことでお客様が身に覚えを確認できるようにする。件名「パスワードを変更しました」。件名・本文の形は client-portal-design-plan.md §6-1 / §6-2 参照）
- **条件**：
  - 現在のパスワードが一致しない場合は変更できない
  - 新しいパスワードは初回設定（6-15-5）と同じ強度要件を満たすこと
- **利用権限**：会員

#### 6-15-12. パスワードの再設定
- **概要**：パスワードを忘れてログインできなくなったお客様が、ログイン画面（S-1401）の「パスワードを忘れた方」から、自分でパスワードを再設定する
- **入力**（申し込み）：
  - メールアドレス
- **入力**（再設定）：
  - 新しいパスワード
  - 新しいパスワード（確認）
- **動作**：
  - ログイン画面から「パスワードを忘れた方」を押すと、パスワード再設定申し込み画面（S-1407）が開く
  - メールアドレスを入力して送信すると、「登録されている場合は再設定のメールを送りました」という**登録の有無が分からない文言**を同画面に表示する
  - 該当するお客様の状態が**「利用中」**（メールアドレスとパスワードの両方が登録済み）の場合のみ、当該アドレス宛に**パスワード再設定リンク**を送る（有効期限 3 日）
  - 発行時点で、それまで送信済みだった未使用の再設定リンクは無効になる（**同時に有効な再設定リンクは常に 1 本だけ**）
  - お客様が再設定リンクを開くと、パスワード再設定画面（S-1408）が開く
  - 新しいパスワードを設定するとログイン画面（S-1401）へ戻し、「パスワードを再設定しました。新しいパスワードでログインしてください」を表示する
  - **申し込み時に現在のパスワードは求めない**（忘れているため）
- **条件**：
  - 状態が「利用中」でないお客様（メールアドレス未登録・初回設定未完了・メールアドレスなど）には再設定リンクを送らない。ただし**画面の表示は同じ**にする（第三者に登録の有無を露呈させないため）
  - リンクが無効・期限切れ・使用済みの場合は、その旨を表示し設定できない
- **備考**：
  - **「登録の有無を画面に出さない」理由**：第三者が特定のメールアドレスを入力して「登録されています」の表示を得ることで、当該アドレスがこの訓練所のお客様かどうかを調べられる状況を作らないため
  - **設定後にそのままログインさせず、ログイン画面へ戻す理由**：パスワード再設定は「忘れたものを直す」操作であり、直したうえで改めてログインしてもらう方が流れとして自然。また新しいパスワードで実際にログインできることをその場で確かめられる。初回設定（6-15-5）でリンクを開いた時点でログインさせているのは「アカウントを作る」流れの一部で続けて基本情報の入力を求めるためであり、性質が異なる
  - **再設定の完了を通知するメールは送らない**：再設定リンク自体が登録アドレスに届いており、本人はすでにそのメールを受け取っている。改めて完了通知を送っても新たな防御にならない
  - 「パスワード再設定リンク」は**新しいパスワードを設定するためのリンク**であり、ログイン用リンク（6-15-4／6-15-5 で扱うもの）とも、メールアドレス確認リンク（6-15-10）とも性質が異なる（ログインさせる働きは持たない、メールアドレスも変えない）
  - 再設定リンクは、他のトークン（メールアドレス登録用 URL・ログイン用リンク・メールアドレス確認リンク）とは**無関係に発行される**ため、独立した有効期限を持つ
  - **ログイン中に再設定リンクを開いた場合の扱い**：**ログアウトさせない**。リンクを開いた時点でも、設定を終えた時点でも、ログイン状態は維持する。設定後はログイン画面（S-1401）へ遷移するが、すでにログイン中であればそのままダッシュボード（S-1402）へ移る。理由：パスワードを変えてもログイン中のセッションは生き続けるため、お客様が困る場面がない。加えて、パスワード変更画面（S-1410、6-15-11）からパスワードを変える場合もログアウトさせないと決めており、同じ「パスワードを変える」操作で経路によって挙動が変わるのは一貫しないため
  - **利用中でないお客様がパスワード再設定を申し込んだ場合の救済**：状態が「利用中」でないお客様（初回設定未完了・メールアドレスなど）には再設定メールが届かず、登録の有無を画面に出さないためお客様は「メールが来ない」ことで気づくしかない。お客様から「メールが届かない」と連絡があった場合、トレーナーは会員詳細画面（S-0305）で**状態を確認する**（段階 4-2 で追加した状態表示を使う）
    - **状態が「利用中」でない**場合、まだログインできる状態になっていない。トレーナーが**マイページ登録案内を発行し直し**（6-3-6）、最初から案内する
    - **状態が「利用中」である**場合、メールアドレスの誤りやメールの不着が考えられる。必要ならトレーナーが**メールアドレスを削除**し（6-3-8）、マイページ登録案内の発行からやり直す
- **利用権限**：認証不要（申し込み・パスワード再設定リンクを開くとき）

#### 6-15-13. プライバシーポリシー同意の表示
- **概要**：お客様が**最初に個人情報を預ける画面**（メールアドレス登録・初回設定・受付アンケート）で、送信ボタンの手前に「送信することにより、お客様はプライバシーポリシーに従って個人データを取り扱うことに同意したものとします。」の同意文とリンクを表示する
- **動作**：
  - **表示する画面**：メールアドレス登録画面（S-1405、6-15-4）、初回設定画面（S-1403、6-15-5）、受付アンケート回答画面（S-1413、6-15-17）の 3 画面
  - ログイン画面・登録情報画面（S-1406）や各変更画面（S-1409/1410/1411）など、既に同意済みのお客様が使う画面には表示しない
  - 受付アンケート回答画面では、お客様がマイページに登録済みかどうかにかかわらず**常に**表示する（ログインしない画面で相手を判定しないため。また、愛犬の健康状態を新たに預かる場面のため）
  - リンクは**別タブで開く**（入力中の内容が消えないようにするため）
  - 表示は控えめ（本文より小さな文字・薄めの色）にして、入力の主役を邪魔しない
- **条件**：
  - **プライバシーポリシー文書の URL が設定されているとき**だけ表示する（設定値 `config('app.client_portal_privacy_url')`、環境変数 `CLIENT_PORTAL_PRIVACY_URL`）
  - **URL が未設定のときは、同意文のブロックごと出力しない**（現在の画面と一切変わらない）
- **備考**：
  - **なぜ必要か**：マイページはお客様の個人情報（メールアドレス・電話番号・住所・犬の記録と写真）を扱うため、預ける前に同意の位置づけを示す必要がある。他サービス（Booking.com 等）のログイン画面と同じ扱い。受付アンケート（6-15-17）では、マイページの利用の有無にかかわらず、愛犬の健康状態などを新たに預かるため、同じく預ける前に示す
  - **URL が空になっている理由**：訓練所側でホームページ制作中で、そこにプライバシーポリシーを掲載する方針。URL が確定した時点で env に設定するだけで表示に切り替わる
  - **利用規約は今回の対象外**：利用規約を作るかどうかは訓練所の判断待ち。将来必要になった場合は、`client_portal_privacy_url` と並べて `client_portal_terms_url` 等の設定値を追加し、同じ形（設定値の有無で表示切替、別タブで開く）で扱う
- **利用権限**：認証不要（メールアドレス登録用 URL）／会員（初回設定は自動ログイン後）／認証不要（受付アンケート案内）

#### 6-15-14. トレーニーの体重推移閲覧
- **概要**：会員が自分のトレーニーの体重推移をグラフで閲覧する。**ダッシュボード（S-1402）の「最新の記録」ブロックの上に直接表示する**（独立画面は作らない。ダッシュボードは元々 1 画面に収まる情報量のため、体重推移を同居させても縦に伸びすぎない）。閲覧のみで、会員は入力しない
- **表示内容**：
  - 会員に紐づくトレーニーごとに、計測値（体重・日時）を折れ線グラフで時系列に表示する
  - 横軸は**時間軸**（計測日時 = 計測日 + 計測時刻）で、間隔は実距離で反映される。**同日の朝・夕の 2 回計測も時刻分だけ離れて表示される**
  - **線は 1 本の連続した折れ線**で結ぶ（期間の長短にかかわらず分割しない）
  - 横軸の目盛りは**日単位に固定**。表示形式は、**すべての目盛りが日付**（`M/d`。「9/15」の 1 行目）で、**左端の目盛りと、年が変わってから最初の目盛りだけ、2 行目に年**（`yyyy`。「2026」）を添える（例：「9/21 9/28 … 12/28 1/4 1/11」の下に、9/21 と 1/4 にだけ「2026」「2027」）。年をまたがない期間なら、年は左端の 1 か所だけ。日付はすべて同じ高さ（1 行目）にそろう。**年を付けるかどうかは、目盛りを自動で間引いた〔`autoSkip`〕あとの、画面に出ている目盛りで決める**（画面に出ているいちばん左と、画面に出ているひとつ左の目盛りと年が違うもの）。間引く前の目盛りで決めると、年が変わった日〔1/1 など〕の目盛りが間引かれたときに年が出なくなったり、見えない目盛りに年が付いたりするため（**2026-10 変更**：年をまたぐ期間の計測値で、どの年か分かるようにするため。その直前は、最初の目盛りも含めてすべて日付だけ〔`M/d`〕にしていた。さらに前は、目盛りが 1 日の始まり〔0:00〕を指すことを示すため、最初の目盛り〔左端〕だけ 2 行目に時刻〔「0:00」〕を出していた。トレーナー側のトレーニー詳細 S-0309 も同じ JS〔`measurement-chart.js`〕を使うので、同じ書式になる）。**点の位置は時刻まで反映される**ため、同じ日に朝・夕の 2 回計測した 2 点は目盛りが日単位でも横位置が分かれる（自動選定に任せる方針だったが、データ点が少ないと時単位が選ばれて日付が読めなくなったため日単位に固定。当初は「9/15」だけの書式だったが、目盛りが 1 日のどこを指すか分からなかったため時刻を追加。時刻を含めると 1 行が長く読みにくかったため 2 行に分け、さらに時刻を左端のみに絞った。詳細は screen-design.md S-1402「横軸の目盛りを日単位に固定した経緯」参照）
  - 複数トレーニーがいる場合はグラフを縦に並べる（複数頭は稀）
  - 会員にトレーニーが 1 頭もいない場合は**グラフのブロックごと表示しない**（ダッシュボード上でセクションを丸ごと非表示にする）。初回設定でトレーニーを作らなくなったため（6-15-5、2026-10 変更）、トレーニーが 0 頭の会員は普通に存在する
  - トレーニーの名前が未登録のときは「愛犬」と出し、「ちゃん」を付けない（6-16「名前が未登録のときの表示」）
  - 登録されたトレーニーがいて計測値が 0 件の場合は、**そのトレーニーのカードを表示し、グラフ領域内に「まだ計測値がありません」と表示する**（空のグラフは描かない。詳細は screen-design.md S-1402「体重推移」設計方針参照。2026-09 変更）
- **経緯**（**2026-09 変更**）：当初は「計測があった日付のみをカテゴリとして等間隔で並べ、一定日数以上空いたら線を分割する」方式だった（コース〔預かり期間〕をエンティティとして持たない代替措置。用語集 No.25 参照）。しかし**間隔が違う計測点が横軸上で同じ幅になる**問題のほうが重大だったため、時間軸に変更した。コース間が空くケースでは横軸に空白ができるが、それは事実として受け入れる（詳細は screen-design.md S-1402「横軸を時間軸に変更した経緯」参照）
- **利用権限**：会員

#### 6-15-15. トレーニー写真の登録・削除
- **概要**：会員がダッシュボード（S-1402）から自分のトレーニーの写真を登録・差し替え・削除する（**2026-09 追加**、トレーナーさんからの要望）。**写真はトレーニーに 1 枚**（複数枚は持たない）。トレーニーカード内の体重推移グラフの左に写真枠を置き、そこから直接操作する。詳細は screen-design.md S-1402 参照
- **入力**：
  - 画像ファイル（JPEG / PNG / HEIC / HEIF、上限は既存メディアの写真上限に揃える）
- **動作**：
  - **アップロード（新規登録・差し替え）**：ダッシュボードの写真枠をクリックすると、写真の有無で挙動が分かれる（**2026-09 変更**、下記「備考」参照）。**写真なし**の場合は直接ファイル選択ダイアログが開く。**写真あり**の場合は操作モーダル（「変更」「削除」「キャンセル」）が開き、「変更」を選ぶとファイル選択ダイアログが開く。ファイルを選ぶとサーバへ multipart POST で送信し、サーバ側で**長辺 400px にリサイズ・JPEG 変換**して保存する（原寸・サムネイルは持たない。詳細は screen-design.md S-1402「トレーニー写真」設計方針参照）。既存の写真がある場合は**上書き**する（旧ファイルはストレージから削除する）
  - **削除**：写真枠をクリックして開く操作モーダルから「削除」を選ぶと、**追加の確認ダイアログを出さずに即削除**する（モーダルで「削除」を選ぶこと自体が意思確認の役割を果たすため）。DB の `photo_path` を NULL に戻し、実ファイルもストレージから削除する
- **条件**：
  - 対象のトレーニーがログイン中の会員に紐づくこと（`trainees.client_id = auth('client')->id()`）。他人のトレーニーの写真は登録・削除できない
- **備考**：
  - **アップロードはサーバ経由**（署名付き URL の直アップロードは使わない）。写真 1 枚（リサイズ前でも数 MB 程度）ならサーバ経由で足り、実装が単純になり、バケットの CORS 設定変更も不要になる（screen-design.md S-1402「検討して採らなかった案」#2 参照）
  - **画像の縦横比は保つ**。切り抜きはしない（横長は上下に、縦長は左右に余白ができる）
  - **既存のメディア機能（`media_records`）とは別の仕組み**（`media_records` はライブラリ型でトレーニング記録に紐づく設計、今回はトレーニーの属性として 1 対 1）
  - **操作モーダルにした経緯**（**2026-09 変更**）：当初は写真の下に「削除」リンクを常時表示していたが、押しやすい位置にあり誤操作の恐れがあるため、写真あり時のクリックで操作モーダル（「変更」「削除」「キャンセル」）を出す形に変えた。モーダルで「削除」を選ぶこと自体が意思確認の役割を果たすため、モーダル内の削除は追加の確認ダイアログを出さず即実行する（詳細は screen-design.md S-1402「操作モーダルの構成と経緯」参照）
- **利用権限**：会員

#### 6-15-16. ご利用回数の閲覧
- **概要**：会員が、自分の回数の契約と利用の状況（残りの回数、契約ごとのご利用）を**見るだけ**できる。トレーナー側の会員詳細（S-0305）の回数カード（6-17）と同じ内容を、会員向けの言葉づかいで表示する。ご利用回数の画面（S-1412）で表示し、会員側のナビゲーションの「**ご利用回数**」から入る（項目名だけで数字は出さない。どの画面を人に見せても回数が見えないようにするため。契約・利用の有無にかかわらず常に出す）。ダッシュボード（S-1402）には回数を出さない（6-15-3）
- **表示内容**：
  - 対象は**ログイン中の会員自身**の契約・利用だけ（URL に会員の id を取らない）
  - 上から次の順に表示する
    1. 見出し「ご利用回数」と、全体の数（「**あと n回**」を大きめに）
    2. 契約ごとのカード（**新しい契約が上**）。見出しは「{契約日} ご契約（N回）」＋有効期限があれば「有効期限 {日付}」＋状態（「あと n回」または「すべてご利用済み」）。その下に回数ぶんのマス（利用済みは利用日、未利用は「未利用」。利用日の昇順で左から）。有効期限を過ぎていて残りがある契約は、有効期限の日付を赤字にする（トレーナー側と同じ条件）
    3. 契約に割り当てていない利用があるときだけ、**一番下**に「**契約に含まれないご利用 n回**」のカード（利用日のマスを並べる）
  - **会員側の言葉づかい**（トレーナー側の事務的な表現ではなく、会員に伝わるやわらかい表現にする）：

    | 場所 | トレーナー側（参考） | 会員側 |
    |---|---|---|
    | 画面名・ナビの項目名 | ご利用回数 | ご利用回数 |
    | 全体の数 | ご利用回数　あと 24回 | あと 24回 |
    | 全体がマイナス | ご利用回数　契約 2回分不足（赤字） | ご契約の回数を 2回超えてご利用中です |
    | 契約ごとの状態 | あと 4回 | あと 4回 |

### 6-16. トレーニー管理

**位置づけ**：会員に紐づくトレーニング対象（当面は犬）を管理する。**独立したメニュー・一覧画面は作らず**、**会員詳細画面（S-0305）の中だけで**扱う（トレーナーからの要望が出たら独立メニューを検討する）。トレーニング記録（6-4）は会員単位で、トレーニー単位に分けない（用語集 No.20・23 参照）。実装は段階的に進める（① トレーニー CRUD → ② 計測値の登録・一覧 → ③ 会員向けマイページへの体重推移表示。③ は 6-15-14 参照）。

**会員による編集**：お客様がトレーニーの情報に関われるのは、**受付アンケートの回答（6-15-17）**と、会員による**写真の登録・削除（6-15-15）**、会員による**愛犬の基本情報（名前・犬種・性別・誕生日・去勢・避妊）の変更（6-15-20。登録情報〔S-1406〕から開く S-1417。2026-10-18 追加）**のときだけ。受付アンケートはログインせずに回答し、トレーナーが入れた値を初期値にした入力欄でお客様が直して送り、**回答の基本情報でトレーニーの値を上書きする**（空・未選択の項目は変えない。**2026-10 変更**：当初は空欄の項目だけに反映し、入力済みの値は書き換えないとしていた）。お客様がトレーニーを新しく作ることはない（トレーニーはトレーナーが登録し、その単位で受付アンケート案内を発行する）。写真は会員がダッシュボード（S-1402）から随時登録・差し替え・削除できる。それ以外の属性の修正はトレーナーに伝える運用（トレーナー側 S-0309／S-0310 でのみ編集可能）。トレーニー関連ルート（`trainees.*`）はトレーナー向け（`practitioners`）に限定し、会員には開放しない。受付アンケートの回答と、会員による写真の操作・愛犬の基本情報の変更は、それぞれ専用のエンドポイントで扱う（詳細は api-design.md 参照）

**年齢の表示規則**：トレーニーの年齢は、誕生日（年・月・日を別々に持つ。D-0700）から算出して表示する。年齢そのものは保存しない。入力中の年齢表示（受付アンケート・トレーニー登録・編集）と、保存後の各画面の表示は、**すべてこの規則に従う**（入力時と保存後で表示が食い違わないようにするため）

- 基準日は**表示するその日**
- 年・月・日がそろっている場合：満年齢と月数を出す（例：6歳7ヶ月）。誕生日ちょうどのときも月数を出す（例：6歳0ヶ月）
- 年・月まで：その月の1日生まれとみなして満年齢と月数を出す。誤差は1ヶ月未満。生まれ月ちょうどのときも月数を出す（例：6歳0ヶ月）
- 誕生日・生まれ月ちょうどのときも月数を出す理由（**2026-10 追加**）：月まで分かっていることを示すため、年だけのときの「約6歳」と見分けられるようにする
- 年だけ：基準日の年から生まれ年を引いた数に「約」を付ける（例：約6歳）。誤差は1歳近くありうるため
- 1歳未満（年・月まで以上）：月数だけ出す（例：10ヶ月）。今月生まれは「1ヶ月未満」
- 1歳未満（年だけ）：「1歳未満」
- 生まれた日がその月にない場合（**2026-10 追加**。PHP と JS で同じ結果を出すため）：月数は、生まれた日を各月の同じ日として数える。**その月に生まれた日がない場合は、その月の末日を生まれた日とみなす**。例：1月31日生まれは、2月28日（うるう年は29日）に1ヶ月になる。2月29日生まれは、うるう年でない年の2月28日に1歳になる
- 誕生日が未登録：何も出さない

誕生日と年齢を並べる形（会員詳細のトレーニーカード、トレーニー詳細）：

| 登録の状態 | 表示例（基準日 2026年10月20日） |
|---|---|
| 年・月・日（2020年3月15日） | 2020/03/15（6歳7ヶ月） |
| 年・月（2020年3月） | 2020年3月生まれ（6歳7ヶ月） |
| 年のみ（2020年） | 2020年生まれ（約6歳） |
| 未登録 | 空欄 |

**入力のルール**：

- 年・月・日はそれぞれ任意。分かるところまで入れる
- 月を入れるなら年が必須、日を入れるなら年・月が必須
- 3つそろったら実在する日付であること（2月30日などは不可）
- 未来でないこと。年だけなら今年以前、年・月までなら今月以前、年・月・日なら今日以前
- 年は**今年から30年前まで**（それより前は入力の誤りとみなす）
- 全角の数字は半角に直して受け付ける。前後の空白は取り除く（スマホの日本語入力のまま数字を打つお客様が多いため。**2026-10 追加**）。直したあとに数字でなければ、入力の誤りとする

**入力中の表示**：入力欄の右（または下）に、その時点の入力から算出した年齢を表示する。年齢は保存後の表示（「2020/03/15（6歳7ヶ月）」）にそろえて**全角のカッコで囲む**（例：（6歳7ヶ月）（約6歳）（10ヶ月）（1ヶ月未満）（1歳未満）。**2026-10 変更**）。入力がルールに合わないときは、年齢の代わりに次の案内を出す。**案内にはカッコを付けない**（年齢ではなくメッセージのため）。空欄なら何も出さない

| 状態 | 案内 |
|---|---|
| 数字でない文字が入っている | 数字で入力してください |
| 月が1〜12でない | 日付を確認してください |
| 年がなく、月または日が入っている | 年も入力してください |
| 年と日があり、月がない | 月も入力してください |
| 実在しない日付 | 日付を確認してください |
| 未来になっている | 未来の日付になっています |
| 30年より前の年 | 年を確認してください |

案内は入力の手助けで、送信時の検証はサーバー側で同じルールにより行う

- 入力中の案内の判定の順は、送信時の判定の順（screen-design.md §2-8・S-0308 の表）と同じにし、上の表の上から順に最初に当てはまった 1 つを出す。入力中の案内は**送信時の文言より短い**が、どの状態と判定するかは同じ（**2026-10 追加**。「数字でない」「月が1〜12でない」の 2 行も同じ時に加え、表の並びを判定の順にそろえた）

**名前が未登録のときの表示**：トレーニーの名前は任意（D-0700）。未登録のときは次のように表示する

- **トレーナー側**：未入力値の表示規約（screen-design.md §2-4）の例外として、空欄にせず「名前未登録」と出す（名前はそのトレーニーを指し示す目印のため。詳細は §2-4）。「名前（犬種、性別）」の形で出す箇所（会員一覧・トレーニング記録一覧・ダッシュボードのトレーニー列）は「名前未登録（トイプードル、男の子）」のように、括弧を重ねない
- **会員側・お客様側**（会員ダッシュボードなど）：「愛犬」と出す。名前のあとに「ちゃん」を付けている箇所は、未登録のときは「ちゃん」も付けない（「モモちゃん」／「愛犬」）
- **受付アンケート**（回答画面 S-1413・案内画面 S-0311・コピーする文面）：名前の有無にかかわらず、メッセージには名前を使わず常に「愛犬」と出す（6-15-17。**2026-10 変更**：当初は会員側と同じく「モモちゃん」／「愛犬」と出し分けていた）
- **愛犬性格診断**（**2026-10 追加**。回答画面 S-1415・案内画面 S-0312・コピーする文面・回答完了画面 S-1416）：受付アンケートと同じく、名前の有無にかかわらず、メッセージには名前を使わず常に「愛犬」と出す（6-15-18）

**愛犬性格診断の採点とタイプの判定**（**2026-10 追加**。6-15-18・6-16-13。トレーナーさんの今の GAS と同じ結果にする。中身は変えない）：

- **カテゴリの平均**：7カテゴリ（対人・対犬・所有欲・分離不安・恐怖心・訓練性能・興奮性。設問の割り当ては D-1200）ごとに、**「未経験」を除いた**回答の点数（0〜4）の平均を出す。そのカテゴリの全問が「未経験」なら、**点数なし**（`null`。画面では「—」）（**2026-10-18 変更**：トレーナーさんに確認して決めた。「未経験」は「その状況になったことがない＝わからない」なのに、0 点にすると「傾向がまったくない」と見間違えるため）。1 問でも「未経験」以外の答えがあれば今までどおり平均を出す（0 点の答えだけなら 0 点。0 点と点数なしは別のもの）
- **保存**：平均は小数第2位に丸めて保存する（四捨五入。ちょうど半分は切り上げ。今の GAS の `toFixed(2)` と同じ結果）
- **表示**：小数第1位で出す。画面では**保存の値（小数第2位）から四捨五入**して出す（ちょうど半分は切り上げ。2026-10 追加：採点はサーバーだけで行い、画面は保存した値を出すため）。問数は多くても 8 なので、平均（合計 ÷ 問数）を小数第2位で丸めてから第1位に丸めても、丸める前の値から第1位に丸めたとき（GAS の `toFixed(1)`）と必ず同じ結果になる（固定データの `display` で確かめている）
- **タイプの判定**：**丸める前の**7カテゴリの平均のうち、いちばん高いものでタイプを決める。いちばん高い平均が **1.5 未満**なら「のんびり・平和主義タイプ」。同点のときは、カテゴリの順（対人 → 対犬 → 所有欲 → 分離不安 → 恐怖心 → 訓練性能 → 興奮性）で先のカテゴリを取る

| いちばん高いカテゴリ | タイプ |
|---|---|
| 対人・対犬 | 慎重派・しっかり番犬タイプ |
| 所有欲・分離不安 | 愛情たっぷり・甘えん坊タイプ |
| 恐怖心 | 繊細・デリケートタイプ |
| 訓練性能 | 聡明・スマート優等生タイプ |
| 興奮性 | エネルギッシュ・アスリートタイプ |
| （いちばん高い平均が 1.5 未満） | のんびり・平和主義タイプ |
| （全カテゴリが点数なし。50問すべて「未経験」） | **判定なし**（`null`。画面では「判定なし」。**2026-10-18 追加**） |

- **点数なしのカテゴリはタイプの判定から外す**（**2026-10-18 追加**）：点数なしのカテゴリを除いた残りのカテゴリで、今までどおり判定する（いちばん高いもの、同点はカテゴリの順、いちばん高い平均が 1.5 未満なら「のんびり・平和主義タイプ」）。全カテゴリが点数なしのときは、タイプも**判定なし**にする
- **元の仕組み（GAS）との違い**（**2026-10-18 追加。意図した違い**）：元の仕組みでは、全問「未経験」のカテゴリの平均は 0、全問「未経験」のときのタイプは「のんびり・平和主義タイプ」になる。この仕組みでは、それぞれ**点数なし**・**判定なし**にする。ほかの場合（全問「未経験」のカテゴリがない回答）は、元の仕組みと同じ結果になる。突き合わせ用の固定データ（`tests/fixtures/personality-diagnosis-cases.json`）では、`all-na`（全問「未経験」）と `category-all-na`（分離不安だけ全問「未経験」）の期待する値を、新しい決まりの値にした
- **保存済みの結果の計算し直し**（**2026-10-18 追加**）：採点の決まりを変えたときは、保存してある 50 問の回答から点数とタイプを計算し直し、すべての結果を同じ決まりにそろえる（設問の版は変えない。D-1200「設問の版」）。一度だけ流す artisan コマンド `php artisan personality-diagnosis:rescore` で行う（`--dry-run` で変わる件数だけを確かめられる）

- **丸める前の値で判定する理由**：今の GAS は丸める前の値で比べている。丸めた値で比べると、同点の扱いが変わることがある（例：1.666… と 1.67）
- **訓練性能の向き**：訓練性能は点数が高いほどよい向きの設問だが、今の GAS ではほかのカテゴリと同じく「いちばん高いもの」としてタイプの判定に使っている。中身は変えない方針のため、そのまま移す
- **点数の向き（決定）**（**2026-10-18 追加**）：訓練性能は点数が高いほど良い（指示がよく通る）。ほかの 6 項目（対人・対犬・所有欲・分離不安・恐怖心・興奮性）は点数が高いほど気をつけたい傾向。参考にしている本などの向きに合わせ、向きは変えない（2026-10-18 にトレーナーさんに確認）。その代わり、レーダーチャートでは訓練性能の軸を真上に置き、ほかの項目と分けて見やすくする（screen-design.md S-0309「レーダーチャート」）
- **検証の方針**：トレーナーさんの過去の回答を、**名前などを除いた回答だけ**の「突き合わせ用の固定データ」にし、テストで今の GAS と同じ点数・タイプになることを確かめる（年齢の計算の固定データと同じ作り）。固定データは `tests/fixtures/personality-diagnosis-cases.json`（設問の版 `v1`）。中身は、トレーナーさんの**過去の回答 4 件**（`past-1`〜`past-4`。名前などを除いた回答だけ。期待値は当時の GAS の出力と一致することを確かめてある）と、**境目の回答 11 件**（全問 0・全問「未経験」・全問 4・いちばん高い平均がちょうど 1.5・1.5 未満・同点 3 通り・全問「未経験」のカテゴリ・丸め 2 通り）。各例に、7 カテゴリの保存の値（小数第2位の文字列）・表示の値（小数第1位の文字列）・タイプの値を期待値として持つ。採点はサーバーだけで行い（画面は保存した値を出す）、JS では採点しない

#### 6-16-4. トレーニー削除

- **条件**：計測値の有無に関わらず削除できる（計測値は日々増えるため削除拒否方式は採らない。DB 側の外部キーは CASCADE で計測値も一緒に削除される。受付アンケートの案内・回答と、愛犬性格診断の案内・結果も同じく一緒に削除される）
- **動作**：
  - 削除確認で**計測値の件数を表示する**（例：「このトレーニーには N 件の計測値が登録されています。トレーニーを削除すると計測値も一緒に削除されます。」）。承諾したときのみ実行する
  - 受付アンケートの回答・愛犬性格診断の結果、または未回答の案内がある場合は、計測値の件数の提示に続けて、次を加えて提示する（**2026-10 変更**：愛犬性格診断を足した）
    - 消えるもの：あるものだけを「と」でつないで「〜も一緒に削除されます。」（受付アンケートの回答だけ：「受付アンケートの回答も一緒に削除されます。」、愛犬性格診断の結果だけ：「愛犬性格診断の結果も一緒に削除されます。」、両方：「受付アンケートの回答と愛犬性格診断の結果も一緒に削除されます。」）
    - 使えなくなる未回答の案内：あるものだけを「と」でつないで「発行済みの〜も使えなくなります。」（受付アンケート案内だけ：「発行済みの受付アンケート案内も使えなくなります。」、愛犬性格診断の案内だけ：「発行済みの愛犬性格診断の案内も使えなくなります。」、両方：「発行済みの受付アンケート案内と愛犬性格診断の案内も使えなくなります。」）
    - 順は「消えるもの → 使えなくなる案内」。どちらの中も「受付アンケート → 愛犬性格診断」の順
- **備考**：
  - 受付アンケートに答え直してもらう必要があり、計測値や写真などの他のデータがまだない場合は、管理者がトレーニーを削除して登録し直し、新しい案内を発行する（第1段階では、回答済みのトレーニーに案内を発行し直す機能は持たない。6-16-8）。登録し直すとトレーニーの並び順（登録順）が変わるが、複数頭は稀なため許容する
- **利用権限**：管理者

#### 6-16-8. 受付アンケート案内の発行
- **概要**：トレーナーがお客様に渡すための受付アンケート案内（QR コード・URL・手順を載せた紙面／画面）を、トレーニーごとに発行する。お客様はこの案内の URL から受付アンケートに回答する（6-15-17）。「受付アンケート案内」はお客様・トレーナーが扱う対象（QR や紙面）の呼び名で、内部的にはトークン（「受付アンケート用 URL」）を作る
- **動作**：
  - 会員詳細画面（S-0305）のトレーニーカードの「**受付アンケートの案内を発行**」ボタン（状態が「未発行」のときだけ出る）で発行する。トレーニー登録（6-16-1）では発行しない（**2026-10 変更**。案内の発行は会員詳細の［受付アンケートの案内を発行］だけで行う。登録の画面では発行しない（操作を会員詳細に寄せるため。登録してすぐ渡したいときも、会員詳細に戻ってから発行する））
  - 発行すると、**会員詳細に戻り**、上に完了メッセージ「**{表示名}の受付アンケートの案内を発行しました。**」を出す（**2026-10-17 変更**。表示名は会員詳細のトレーニーの名前と同じ〔名前がなければ「名前未登録」〕。理由は 6-3-6 備考「発行のあとの戻り先」と同じ）。ボタンは「**受付アンケートの案内を表示**」「**取消**」に入れ替わっている
  - **有効な案内がすでにある**とき（二重送信・古い画面から押し直したなど）は、新しく発行せず、完了メッセージも出さずに会員詳細に戻る
  - 「受付アンケートの案内を表示」を押すと、**受付アンケート案内画面（S-0311）**を**同じタブで開く**。QR コード・URL 文字列・手順を当画面に集約する
  - 案内を紙で渡すだけでなく、メール／LINE でも送れるよう、S-0311 に「**文面をコピー**」ボタンを置く（マイページ登録案内〔6-3-6〕と同じ考え方。本システムはメール送信や LINE 連携を持たない）
- **状態**（トレーニーごと）：

  | 状態 | 意味 | 出す操作 |
  |---|---|---|
  | 未発行 | 有効な案内がなく、回答もない | 受付アンケートの案内を発行 |
  | 回答待ち | 有効な案内がある | 受付アンケートの案内を表示／取消 |
  | 回答済み | 回答がある | （操作なし。愛犬性格診断の行の下に「暮らしの様子」のリンク） |

  会員詳細画面（S-0305）のトレーニーカードでは、状態の文字・発行日・回答日時は出さず、出す操作（ボタン）だけで状態を伝える（**2026-10 変更**。状態はボタンで分かり、行を短くしてトレーニーの情報の邪魔をしないため）。トレーニー詳細（S-0309）にも状態・日付は出さない。発行日・回答日時はどの画面にも出さない（値は DB に残る）

- **状態の判定順**：回答がある → 「回答済み」、なければ有効な案内がある → 「回答待ち」、どちらもない → 「未発行」。回答が複数件あるとき（第2段階以降）は、S-0309 では新しい順に並べる
- **条件**：
  - 状態が「未発行」のときだけ発行できる（同じトレーニーに有効な案内は常に1つまで）
  - **回答済みのトレーニーには発行できない**（第1段階。答え直しは 6-16-4 備考、または第2段階）
- **備考**：
  - **有効期限は設けない**（理由は 6-15-17 備考）
  - **発行し直す機能は設けない**：期限がないので、渡し直したいときは「表示」で同じ URL・QR コードを出せば足りる。URL を差し替えたいとき（間違った相手に渡した等）は、取消（6-16-9）してから発行する
  - 案内シートに**お客様の氏名は載せない**（6-3-6 と同じ理由）。**愛犬の名前も載せない**（常に「愛犬」。6-15-17。**2026-10 変更**：当初は愛犬の名前は載せてよい〔未登録なら載せない〕としていた。トレーナーが電話などで聞いて入れた名前が間違っていると、お客様に間違った名前を見せることになるため）
  - QR コードは 6-3-6 と同じく、ビルドに含める JS ライブラリで生成する
  - 発行・取消は、トレーニーの他の操作と同じくアクセスログに記録する
  - **操作を会員詳細に寄せた理由**（**2026-10 変更**）：受付アンケート案内の発行・表示・取消は、会員詳細（S-0305）だけで行う。案内を渡す相手は会員で、マイページ登録案内も会員詳細でしか操作しないため。発行だけを外すと「取消はできるのに発行はできない」中途半端な形になるので、3 つともそろえてトレーニー詳細（S-0309）から外した。当初は S-0309 の受付アンケートの欄でも発行・表示・取消を行えるようにし、操作した画面に戻していた（戻り先は計測値の登録〔6-16-5〕と同じ仕組み）。S-0309 では回答の内容（「暮らしの様子」の欄）を表示するだけにした
  - **ボタン名**（**2026-10 変更**）：発行と表示のボタンは「受付アンケートの案内を…」として、何の案内かをボタンの文字だけで分かるようにする（マイページ登録案内のボタンと見分けるため。左にラベルを置かずに済む）。取消は隣の［受付アンケートの案内を表示］と確認（S-0305-M06）の文言で対象が分かるので「取消」のままにする。読み上げでは、まとまりの名前「{表示名}の受付アンケート」でどのトレーニーの操作かが伝わる
- **利用権限**：一般、管理者

#### 6-16-9. 受付アンケート案内の取消
- **概要**：トレーナーが発行済み（回答待ち）の受付アンケート案内を取り消す。**放置されている**、**間違った相手に渡した**、**URL を差し替えたい**ときに使う

  - 完了後は**会員詳細画面に戻り**、「受付アンケートの案内を取り消しました。」を表示する（2026-10 変更：当初は操作した画面に戻していた。会員詳細だけで操作する形にしたため。6-16-8 備考）

#### 6-16-10. 受付アンケートの回答の閲覧

- **動作**：
  - 会員詳細画面（S-0305）のトレーニーカードの「愛犬性格診断」の行の下（属性の並びの最後。**2026-10 変更**：当初は「最終計測」のすぐ下・「愛犬性格診断」の行の上。トレーニー詳細の欄の順にそろえた）の「**暮らしの様子**」のリンク（回答済みのときだけ出る）から、トレーニー詳細画面（S-0309）の暮らしの様子の欄を開く（**2026-10 変更**。回答済みになると案内の操作は終わり、あとは回答を読むだけになる。そのため操作のボタンとしてではなく、トレーニーの情報の1つとして、属性の並びの最後に「暮らしの様子」へのリンクを置く）

  - **回答日時は表示しない**（案内の状態は会員詳細のボタンで分かり、この欄は回答の中身を読むためのもの。回答日時は DB の `trainee_intake_survey_responses.answered_at` に残る。**2026-10 変更**）
  - 第1段階では1頭につき回答は1件で、最新の1件を出す。データは複数件持てる形にし、複数件ある場合は新しい順に並べる前提とする
  - 会員（マイページ）には回答を表示しない（第1段階）
- **利用権限**：一般、管理者

  | 回答待ち | 有効な案内がある | 案内を表示／取消 |

  受付アンケートと違い「回答済み」で止まらない（回答されたら、次の案内を発行できる。何回でも受けられるため）。会員詳細の「愛犬性格診断」の行では、状態の文字・案内の発行日は出さず、ボタンだけで案内の状態を伝える（受付アンケートと同じ）
- **最新の診断の日付**（**2026-10 追加**）：会員詳細の「愛犬性格診断」の行には、リンクとボタンの間に**最新の診断の回答日**（愛犬性格診断の結果〔6-16-13〕のうち、いちばん新しい回答日の結果。トレーニー詳細のグラフの「今回」と同じ回）を出す。結果がないときは「**診断なし**」と出す。出すのは**結果**の日付で、回答待ちの案内があっても案内の発行日は出さない。トレーニー詳細を開かなくても、いつ診断したかが分かるようにするため
- **条件**：
  - 状態が「未発行」のときだけ発行できる（同じトレーニーに有効な案内は常に1つまで）
  - 前の回答の有無にかかわらず発行できる
- **備考**：
  - **有効期限は設けない**（理由は 6-15-18 備考）
  - **発行し直す機能は設けない**：期限がないので、渡し直したいときは「表示」で同じ URL・QR コードを出せば足りる。URL を差し替えたいときは、取消（6-16-12）してから発行する（受付アンケートと同じ）
  - 案内シートに**お客様の氏名も愛犬の名前も載せない**（受付アンケート案内と同じ）
  - QR コードは 6-3-6 と同じく、ビルドに含める JS ライブラリで生成する
  - 発行・取消は、トレーニーの他の操作と同じくアクセスログに記録する
  - **操作は会員詳細だけで行う**：愛犬性格診断の案内の発行・表示・取消は会員詳細（S-0305）だけで行い、トレーニー詳細（S-0309）には置かない（受付アンケート案内と同じ。6-16-8 備考「操作を会員詳細に寄せた理由」）
  - **ボタン名を短くできる理由**：愛犬性格診断のボタンは「愛犬性格診断」の行の右に置き、行の左に「愛犬性格診断」の文字があるので、［案内を発行］［案内を表示］［取消］で何の案内かが分かる。受付アンケートのボタンは、名前の行の右に置き左に名前を置かないため「受付アンケートの案内を…」と長くしている（6-16-8 備考「ボタン名」）。置き場所が違うための違いで、食い違いではない。読み上げでは、まとまりの名前「{表示名}の愛犬性格診断」でどのトレーニーの操作かが伝わる
  - **受付アンケートのボタンは今の位置（名前の行の右）のまま**にする（受付アンケートは愛犬の名前などの大事な情報を含むため、目立つ位置に置く）
- **利用権限**：一般、管理者

### 6-17. 回数管理

**位置づけ**：トレーナーは会員と「4回コース」「8回コース」などの回数で契約し、トレーニングのたびに回数を使う。会員から「残り何回？」と聞かれたときにすぐ答えられるよう、会員ごとの**契約**（用語集 No.27）と**利用**（用語集 No.28）を登録し、**残り回数**（用語集 No.29）を表示する。**独立したメニュー・一覧画面は作らず**、会員詳細画面（S-0305）の中で扱う。

**基本方針**：
- **残り回数 ＝ 会員ごとの契約回数の合計 − 利用の件数**（**利用 1 件は 1 回分**）。**マイナスも許す**（利用の登録は止めない）
- 利用は、登録・編集のときに**どの契約の分かを選んで割り当てる**（現場の運用に合わせる）。選ばずに「契約なし」（未割り当て）にもできる。**契約ごとの残り ＝ 契約の回数 − その契約に割り当てた利用の件数**。残りのない契約には割り当てられない
- 利用は**トレーニング記録とひも付けない**（トレーニング記録の件数と利用の件数は一致しないため）
- 契約の**有効期限は、残り回数の計算にも割り当てのチェックにも使わない**（期限を過ぎた契約にも利用を割り当てられる）。有効期限を過ぎていて残りがある契約は、会員詳細の回数カードで有効期限の日付を赤字にする（有効期限の当日は赤字にしない。判定の「今日」はアプリのタイムゾーン〔`config('app.timezone')`〕での日付）
- 金額・支払いは持たない
- **預かりのコース（用語集 No.25）とは無関係**として扱う。回数の契約には「コース」という語を使わず「契約」と呼ぶ（「4回コース」などの呼び名は契約のメモに書く）
- 会員削除時は、契約・利用も一緒に削除される（会員削除を拒否する条件にはしない。6-3-5 参照）

#### 6-17-1. 契約の登録
- **概要**：会員と結んだ回数の契約を登録する
- **入力**：
  - 「9. データ項目一覧」D-0900 参照
  - 必須項目：契約日、回数
  - その他の項目（有効期限・メモ）は任意
- **初期値**：契約日は今日
- **動作**：
  - 会員詳細画面（S-0305）の「回数」カードの「契約を追加」ボタンからモーダルで登録する。登録後は会員詳細に戻る
- **条件**：
  - 回数は 1〜999 の整数
  - 有効期限は契約日以降の日付
- **利用権限**：一般、管理者

#### 6-17-2. 契約の編集
- **概要**：登録済みの契約を編集する
- **入力**：
  - 「9. データ項目一覧」D-0900 参照
  - 必須項目：契約日、回数
- **動作**：
  - 会員詳細画面（S-0305）の「回数」カードで、契約の見出しを押してモーダルで編集する。編集後は会員詳細に戻る
- **条件**：
  - 6-17-1 と同じ
  - **回数は、その契約に割り当て済みの利用の件数より少なくできない**（エラーにする）
- **利用権限**：一般、管理者

#### 6-17-3. 契約の削除
- **概要**：契約を、確認の上で削除する。**削除は物理削除**
- **動作**：
  - 契約の編集モーダルの削除ボタンから、確認ダイアログを挟んで削除する。削除後は会員詳細に戻る
  - **その契約に割り当てられていた利用は「契約なし」（未割り当て）になる**。利用そのものは消えない（会員の残り回数は、削除した契約の回数の分だけ減る）
  - 割り当てられた利用があるときは、確認ダイアログで「契約なし」になる利用の件数を示す
- **備考**：利用が「契約なし」になる処理は DB で行うため、アクセスログには契約の削除だけが記録され、利用ごとの記録は残らない
- **利用権限**：一般、管理者

#### 6-17-4. 利用の登録
- **概要**：契約回数のうち使った回数を登録する
- **入力**：
  - 「9. データ項目一覧」D-1000 参照
  - 必須項目：利用日
  - その他の項目（契約・メモ）は任意。契約は、この会員の契約から選ぶか「契約なし」にする
  - **回数は入力しない**（利用 1 件は 1 回分）
- **初期値**：利用日は今日、契約は**残りがある契約のうち一番古いもの**（残りのある契約がなければ「契約なし」）。「未利用」のマスから登録するときは、そのマスの契約
- **動作**：
  - 会員詳細画面（S-0305）の「回数」カードの「利用を追加」ボタンからモーダルで登録する。登録後は会員詳細に戻る
  - 契約の「未利用」のマスからも登録できる（そのマスの契約が選ばれた状態でモーダルが開く）
  - **利用 1 件は 1 回分**。2 回分使ったとき（例：トレーニー 2 頭）は、利用を 2 件登録する。1 件の利用は 1 つの契約にだけ割り当てる
  - 使い切った契約（残り 0）は選べない
  - **会員の残り回数がマイナスになる登録は止めない**（警告も出さない。「契約なし」の利用は契約の残りに関係なく登録できる）
- **条件**：
  - 契約は、この会員の契約であること
  - **残りのない契約への割り当てはエラーにする**（別の契約を選ぶか「契約なし」にする）
  - 契約日より前の日付の利用を割り当てることは止めない（先に使って後から契約する運用のため）。有効期限もチェックに使わない
- **利用権限**：一般、管理者

#### 6-17-5. 利用の編集
- **概要**：登録済みの利用を編集する
- **入力**：
  - 「9. データ項目一覧」D-1000 参照
  - 必須項目：利用日
- **動作**：
  - 会員詳細画面（S-0305）の「回数」カードで、利用日を表示したマスを押してモーダルで編集する。編集後は会員詳細に戻る
  - 契約の初期値は、その利用が今割り当てられている契約（未割り当てなら「契約なし」）。今割り当てられている契約は、残りが 0 でも選べる
  - 「契約なし」の利用を契約に割り当て直すのも、この編集で 1 件ずつ行う（まとめて割り当てる機能は作らない）
  - 会員の残り回数がマイナスになる編集は止めない（警告も出さない）
- **条件**：6-17-4 と同じ。ただし契約の残りは、その利用自身を除いて数える（同じ契約のままなら必ず通る）
- **利用権限**：一般、管理者

#### 6-17-6. 利用の削除
- **概要**：利用を、確認の上で削除する。**削除は物理削除**
- **動作**：
  - 利用の編集モーダルの削除ボタンから、確認ダイアログを挟んで削除する。削除後は会員詳細に戻る
- **利用権限**：一般、管理者

#### 6-17-7. 残り回数の表示
- **概要**：会員ごとの残り回数を、会員詳細と会員一覧に表示する
- **表示内容**：
  - **会員詳細（S-0305）**：「回数」カード（画面上の見出しは「ご利用回数」）の見出しに残り回数を表示する。あわせて同じカードに、契約ごとに契約の回数ぶんのマスを並べ、その契約に割り当てた利用の利用日で埋めていく形（回数券型。利用 1 件＝1 マス）で、契約・利用の履歴を表示する。契約に割り当てていない利用は「契約なし」の行に「未割り当て」として表示する
  - **会員一覧（S-0304）**：「ご利用回数」列を表示する。並び替え・検索条件の対象にはしない
- **表示の規則**：
  - 画面の言葉は会員側（6-15-16）にそろえる（トレーナーが会員に聞かれたとき、同じ言葉で答えられるようにするため。**2026-10 変更**）。値は「**あと n回**」（例：「あと 5回」「あと 0回」）、マイナスは赤字で「**契約 n回分不足**」（n は絶対値。例：-2 なら「契約 2回分不足」）。会員一覧は列見出し「ご利用回数」の下に値、会員詳細の見出しでは「ご利用回数　あと n回」（数字の部分だけを少し大きく表示する）。契約ごとの状態は「あと n回」、使い切った契約は「すべてご利用済み」
  - **契約も利用も 1 件もない会員は数字を表示しない**（会員一覧は空欄、会員詳細の見出しはラベル「ご利用回数」だけを出し、数字は空欄）。契約・利用が 1 件でも登録されていれば回数管理の対象の会員として数を出し、1 件もなければ出さない。回数契約をしていない会員と、使い切った会員〔「あと 0回」〕を見分けるため。契約がなく利用だけの会員は、計算どおりマイナス（「契約 n回分不足」）で表示する
- **集計条件**：残り回数 ＝ 契約回数の合計 − 利用の件数（未割り当ての利用も数える）。有効期限は計算に使わない
- **備考**：
  - 回数券型の表示は、利用に持たせた割り当て（どの契約か）のとおりに並べる。表示のときに自動で割り当てる処理は持たない。並べ方は screen-design.md S-0305 参照
  - 会員側では、ご利用回数の画面（S-1412、6-15-16）で**見るだけ**できる。言葉づかい（「あと n回」など）とマイナスの見せ方（赤字の数ではなく文で伝える）は会員向けに変える。契約・利用の**メモは会員には出さない**
- **利用権限**：一般、管理者

- **提供機能**（必須）: 画面が提供する機能（6章への参照）

**記載しない項目**（委譲先は doc-index.md 参照）：

- 画面レイアウト、ワイヤーフレーム、ボタン配置、モーダル構成
- 画面ID、URL、ルート定義、View名
- 入力項目の詳細、バリデーション、入力形式

#### 11-2-2. アカウントの管理

##### 無効化

退職・休職などにより業務を離れたトレーナーのログインを停止します。

- **操作**：管理者がトレーナー管理画面から無効化できます。
- **動作**：無効化されたアカウントはログイン不可となります。主担当の割り当てやトレーニング記録の担当者履歴はそのまま維持されます。
- **解除方法**：管理者がトレーナー管理画面から有効化できます。
- **対象外**：
  - システム管理者アカウント
  - ログイン中の自分自身
  - 最後の有効な管理者（管理者が1名のみの場合）

##### ロック

不正アクセスや長期未使用アカウントの悪用を防ぐため、以下の条件でアカウントをロックします。

- **条件**：
  - **長期間未ログイン**：30日間ログインがない場合（30日は初期値。`.env` で変えられる。6-8-10）
  - **未使用**：アカウント発行後、一度もログインがないまま7日が経過した場合（7日は初期値。`.env` で変えられる。6-8-11）
  - **連続ログイン失敗**：5回連続でログインに失敗した場合
- **動作**：ロックされたアカウントはログイン不可となります。主担当の割り当てやトレーニング記録の担当者履歴はそのまま維持されます。
- **解除方法**：管理者がトレーナー管理画面から解除できます。
- **対象外**：
  - システム管理者アカウント

#### 11-2-3. 時間経過によるログアウト

本システムでは、第三者の覗き見やなりすましを防ぐため、ログイン状態の有効期限を過ぎると自動的にログアウトします。有効期限は120分です。

## 14. 変更管理ルール

本章では、開発期間中（契約締結から本番稼働終了まで）に発生する仕様変更の取り扱いについて定めます。

### 14-1. 変更管理の目的

開発途中での仕様変更は、以下の影響を及ぼす可能性があります。

- 開発スケジュールの遅延
- 開発コストの増加
- システム品質への影響

これらのリスクを最小限に抑えるため、変更管理ルールを定めます。

### 14-2. 変更要求の手続き

#### 14-2-1. 変更要求の提出
- **提出方法**：書面（メール可）で変更内容を記載してください。
- **記載内容**：
  - 変更箇所（機能名、画面名）
  - 変更内容（現状 → 変更後）
  - 変更理由
  - 希望納期

#### 14-2-2. 影響調査
システム開発事業者は、変更要求を受け取り次第、以下を調査します。

- 影響範囲の特定（関連する機能、データ）
- 作業工数の見積もり
- スケジュールへの影響
- 追加費用の有無

#### 14-2-3. 見積もり提示
- 調査結果を書面で提示します。
- 変更内容、作業工数、追加費用、納期への影響を明記します。

#### 14-2-4. 承認・実施
- 貴機関が見積もりを承認した場合、変更作業を実施します。
- 承認されない場合、変更作業は実施しません。

### 14-3. 変更の分類と対応

開発途中に発生する仕様変更は、以下の3つに分類して対応します。

#### 14-3-1. 軽微な変更（無償対応）
表示文言の修正、画面レイアウトの微調整、要件定義書の修正など、軽微な内容は追加費用なしで対応します。

#### 14-3-2. 仕様変更（有償対応）
新しい機能の追加、項目の追加・削除、画面の大幅な変更など、要件定義書の範囲を超える変更は、別途見積もりを提示し、承認後に対応します。

#### 14-3-3. 大規模な変更（再見積もり）
システム全体の設計変更や、要件定義書の大幅な見直しなど、本開発全体の再検討が必要な変更は、別途協議のうえ、再契約となる可能性があります。

### 14-4. 変更による納期延長

- 変更作業により、当初の納期が守れない場合は、速やかに報告します。
- 新しい納期を協議の上、合意します。

## 16. 保守

本章では、本番稼働後の保守契約期間中の対応について定めます。

### 16-1. 保守の対象

システム開発事業者は、以下を保守の対象として対応します。

1. システムの不具合修正
2. 操作方法の問い合わせ対応
3. 軽微な機能改善
4. PC買い替え時のデータ移行サポート

- PCの設定・修理
- ネットワーク機器の設定・修理
- Windows OSの不具合対応
- 日常のデータ入力代行
- 運用開始後の外部データの取り込み・変換
- 他機関への導入・カスタマイズ

### 16-2. 有償対応

大幅な機能追加や仕様変更については、別途見積もりを提示し、承認後に対応します。

### 16-3. 保守期間と更新

保守の対象として対応する期間は、貴機関とシステム開発事業者の間で締結する保守契約の有効期間とします。

#### 契約期間
- **開始日**：初期サポート期間終了日の翌日
- **契約形態**：年間契約（更新可）
- 具体的な契約期間は、貴機関との保守契約書に明記します。

#### 更新
- 契約期間満了の1ヶ月前に、更新の意思確認を行います。
- 更新する場合は、新たな保守契約を締結します。

#### 契約終了後
保守契約を終了する場合、保守の対象としていた内容はすべて受けられなくなります。
